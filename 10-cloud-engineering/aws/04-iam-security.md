# IAM과 접근 제어 (IAM & Access Control)

> IAM의 네 가지 구성 요소가 각각 무엇을 담당하는지, 정책 문서가 어떤 순서로 평가되어 허용/거부가 결정되는지, 왜 액세스 키보다 역할(Role)이 안전한지, 그리고 최소 권한을 말이 아니라 절차로 실천하는 방법을 설명할 수 있게 된다.

## 학습 목표

- [ ] User, Group, Role, Policy의 역할을 구분해 설명할 수 있다
- [ ] 정책 문서의 Effect / Action / Resource / Condition을 읽고 쓸 수 있다
- [ ] 명시적 Deny가 왜 모든 것을 이기는지, 기본이 왜 Deny인지 설명할 수 있다
- [ ] Role + STS 임시 자격 증명이 장기 액세스 키보다 안전한 이유를 세 가지 이상 댈 수 있다
- [ ] S3 버킷 정책과 IAM 정책을 언제 각각 쓰는지 판단할 수 있다
- [ ] 최소 권한을 처음부터 완벽히 쓰는 대신, 좁혀 나가는 절차로 실천할 수 있다

## 1. 왜 필요한가

클라우드 이전의 권한 관리는 대체로 이랬다. 서버에 SSH 계정을 만들고, DB에 계정을 만들고, 파일 서버에 공유 폴더 권한을 준다. **경계가 물리적이었다.** 사무실 네트워크 안에 있으면 대체로 신뢰했다.

클라우드에서는 이 전제가 무너진다. API 하나만 호출하면 서버 100대를 만들 수 있고, 버킷 하나를 공개로 바꿀 수 있고, DB를 삭제할 수 있다. **모든 것이 API 호출이고, API는 세상 어디서든 호출된다.** 방화벽 안쪽에 있느냐는 더 이상 신뢰의 근거가 아니다.

그래서 필요한 것이 **"누가(Who) 무엇에(What) 어떤 동작을(Action) 어떤 조건에서(Condition) 할 수 있는가"를 코드로 표현하는 시스템**이다. 이것이 IAM(Identity and Access Management)이다.

실제로 클라우드 보안 사고의 대부분은 정교한 해킹이 아니다. **깃허브에 커밋된 액세스 키**, **모든 권한이 붙은 채로 방치된 역할**, **실수로 공개된 S3 버킷**. 셋 다 IAM 설계로 막을 수 있는 것들이다.

> **비유**: IAM은 회사 출입 카드 시스템이다. 사람(User)에게 카드를 주고, 부서(Group)별로 기본 권한을 묶고, 방문객에게는 유효 시간이 정해진 임시 카드(Role/STS)를 준다.
> **비유의 한계**: 실물 카드는 잃어버리면 재발급하면 그만이지만, **AWS 액세스 키는 유출되어도 아무 소리가 나지 않는다.** 누군가 쓰기 전까지는 유출됐는지조차 모른다. 그래서 애초에 "잃어버릴 수 있는 카드"를 안 만드는 방향으로 설계한다.

## 2. IAM의 네 가지 구성 요소

```
┌────────────────────────────── AWS 계정 ──────────────────────────────┐
│  [ 신원(Identity) ]                        [ 권한(Permission) ]       │
│                                                                       │
│   ┌────────┐      ┌────────┐                 ┌──────────────┐        │
│   │  User  │─────▶│ Group  │────┐            │    Policy    │        │
│   │ (사람) │      │ (묶음) │    ├───────────▶│  (JSON 문서) │        │
│   └───┬────┘      └────────┘    │            │  Effect      │        │
│       └─────────────────────────┤            │  Action      │        │
│   ┌────────┐                    │            │  Resource    │        │
│   │  Role  │────────────────────┘            │  Condition   │        │
│   │ (역할) │                                  └──────────────┘        │
│   └───┬────┘  누가 맡을 수 있나 = 신뢰 정책(Trust Policy)             │
│       ▼                                                               │
│   EC2 / Lambda / ECS Task / 다른 계정 / 외부 IdP                      │
└───────────────────────────────────────────────────────────────────────┘
```

**User(사용자)** 는 사람 또는 애플리케이션에 대응하는 영구 신원이다. 콘솔 비밀번호나 액세스 키 같은 **장기 자격 증명**을 가질 수 있다. 뒤에서 보겠지만, 실무의 방향은 User를 최소화하는 쪽이다.

**Group(그룹)** 은 User의 묶음이다. 권한을 사람마다 붙이면 인원이 늘 때 관리가 무너지므로, `Developers`, `Auditors` 같은 그룹에 정책을 붙이고 사람을 넣고 뺀다. 주의할 점: **Group은 신원이 아니다.** 그룹을 주체로 지정해 뭔가를 할 수는 없고, 오직 권한을 묶는 용도다.

**Role(역할)** 은 **누구든 잠시 맡을 수 있는 권한 꾸러미**다. 액세스 키가 없고, 대신 두 개의 정책을 갖는다.

- **신뢰 정책(Trust Policy)**: 누가 이 역할을 맡을 수 있는가 (`Principal`)
- **권한 정책(Permission Policy)**: 이 역할을 맡으면 무엇을 할 수 있는가

역할을 맡으면(`sts:AssumeRole`) **만료 시간이 있는 임시 자격 증명**을 받는다. EC2 인스턴스, Lambda 함수, ECS 태스크, 다른 AWS 계정, GitHub Actions 같은 외부 시스템이 모두 역할을 맡는 주체가 될 수 있다.

**Policy(정책)** 는 권한을 기술한 JSON 문서다. 붙는 위치에 따라 두 종류로 나뉜다.

| 종류 | 어디에 붙나 | `Principal` 항목 | 예 |
|---|---|---|---|
| 신원 기반 정책 (Identity-based) | User, Group, Role | 없음 (붙은 대상이 곧 주체) | "이 역할은 특정 버킷을 읽을 수 있다" |
| 리소스 기반 정책 (Resource-based) | S3 버킷, SQS 큐, KMS 키, Lambda 등 | **있음 (필수)** | "이 버킷은 저 계정의 접근을 허용한다" |

## 3. 정책 문서 읽고 쓰기

### 구조

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadUploadsOnly",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::my-app-uploads",
        "arn:aws:s3:::my-app-uploads/reports/*"
      ],
      "Condition": {
        "Bool": { "aws:SecureTransport": "true" }
      }
    }
  ]
}
```

각 요소를 정확히 이해하는 것이 중요하다.

- **`Version`**: 정책 문법 버전. `2012-10-17`이 현재 버전이며 그대로 쓴다. 날짜처럼 보이지만 **작성 날짜가 아니다.**
- **`Effect`**: `Allow` 또는 `Deny`.
- **`Action`**: `서비스:동작` 형식. `s3:GetObject`, `ec2:TerminateInstances`. 와일드카드(`s3:Get*`)를 쓸 수 있지만 좁힐수록 좋다.
- **`Resource`**: 대상의 ARN. 여기가 실무에서 가장 자주 틀리는 지점이다.
- **`Condition`**: 추가 조건. 없으면 항상 참.

### `Resource`에서 초심자가 반드시 넘어지는 지점

위 예제에서 `Resource`에 두 개의 ARN이 들어간 이유가 있다.

```
arn:aws:s3:::my-app-uploads          ← 버킷 자체.  ListBucket 등 "버킷에 대한" 동작
arn:aws:s3:::my-app-uploads/*        ← 버킷 안 객체. GetObject 등 "객체에 대한" 동작
```

**이 둘은 다른 리소스다.** `arn:aws:s3:::my-app-uploads/*`만 적고 `s3:ListBucket`을 허용하면, 객체는 읽히는데 목록 조회는 AccessDenied가 난다. 반대로 버킷 ARN만 적으면 목록은 보이는데 파일이 안 열린다. "권한을 줬는데 왜 안 되지?"의 절반은 이 문제다.

### `Condition`이 실제로 강력한 이유

조건은 "언제 이 권한이 유효한가"를 좁힌다. 대표적인 조건 키들이다.

| 조건 키 | 의미 | 쓰임새 |
|---|---|---|
| `aws:SecureTransport` | HTTPS로 접근했는가 | 평문 HTTP 접근 전면 차단 |
| `aws:SourceIp` | 요청 출발 IP | 사내 대역에서만 관리 작업 허용 |
| `aws:SourceVpce` | 특정 VPC Endpoint 경유인가 | 우리 VPC 밖에서는 버킷 접근 불가로 강제 |
| `aws:MultiFactorAuthPresent` | MFA 인증 세션인가 | 삭제 같은 위험 동작에 MFA 요구 |
| `aws:PrincipalOrgID` | 우리 조직(Organizations) 소속인가 | 조직 밖 계정 접근 차단 |
| `aws:RequestedRegion` | 어느 리전에 대한 요청인가 | 승인 리전 외 리소스 생성 금지 |

**결론: `Action`과 `Resource`로 범위를 좁히고, `Condition`으로 상황을 좁힌다.** 조건 없는 정책은 "언제 어디서든"이라는 뜻이다.

## 4. 평가 로직: 명시적 Deny가 모든 것을 이긴다

권한이 여러 곳에서 올 수 있다. 그룹에서, 역할에서, 버킷 정책에서, 조직 SCP에서. 이 모두를 합쳐 하나의 판정을 내리는 규칙이 정해져 있다.

```
                       API 요청 도착
                            │
                            ▼
   ┌──────────────────────────────────────────┐
   │ ① 어디에든 명시적 Deny가 있는가?           │── 예 ────▶ [ 거부 ]
   └────────────────────┬─────────────────────┘
                        │ 아니오
   ┌────────────────────▼─────────────────────┐
   │ ② SCP·권한 경계가 이 동작을 허용 범위에    │── 아니오 ─▶ [ 거부 ]
   │    두는가?                                │
   └────────────────────┬─────────────────────┘
                        │ 예
   ┌────────────────────▼─────────────────────┐
   │ ③ 신원 기반 또는 리소스 기반 정책에         │── 아니오 ─▶ [ 거부 (암묵적) ]
   │    Allow가 있는가?                        │
   └────────────────────┬─────────────────────┘
                        │ 예
                        ▼
                     [ 허용 ]
```

세 문장으로 요약할 수 있다.

1. **기본은 거부다.** 아무 정책도 없으면 아무것도 못 한다. 허용은 반드시 명시되어야 한다(암묵적 Deny).
2. **명시적 Deny는 어떤 Allow보다 강하다.** 다른 정책 열 개가 허용해도 하나의 Deny가 있으면 거부다.
3. **가드레일은 권한을 주지 않는다.** SCP나 권한 경계(Permissions Boundary)는 **상한선을 정할 뿐**, 그 자체로 무언가를 허용하지 않는다. "SCP에 허용했는데 왜 안 되죠?"는 잘못된 질문이다.

### 이 규칙의 실전 활용

명시적 Deny의 우선순위 덕분에, **"어떤 실수를 해도 절대 못 하는 것"** 을 만들 수 있다. 아래는 정책 문서의 `Statement` 배열에 들어가는 항목 하나다.

```json
{
  "Effect": "Deny",
  "Action": "s3:DeleteBucket",
  "Resource": "arn:aws:s3:::prod-*"
}
```

이 문장을 조직 SCP나 권한 경계에 걸어두면, 누군가 실수로 `AdministratorAccess`를 붙여도 운영 버킷은 삭제되지 않는다. **Allow를 촘촘히 관리하는 것보다 치명적 동작에 Deny를 박아두는 편이 실수에 훨씬 강하다.**

### 같은 계정 vs 다른 계정

정책이 두 군데(신원 기반 + 리소스 기반)에 있을 때 규칙이 다르다.

```
[ 같은 계정 ]                        [ 다른 계정 (크로스 계정) ]

 IAM 정책 Allow  ──┐                  IAM 정책 Allow  ──┐
                   ├─▶ 둘 중 하나면 OK                   ├─▶ 둘 다 있어야 OK
 버킷 정책 Allow ──┘                  버킷 정책 Allow ──┘
```

"협력사에 버킷 정책으로 권한을 줬는데 접근이 안 된다"는 문의의 원인은 대개 이것이다. **협력사 쪽에서도 자기 계정의 IAM 정책으로 그 버킷 접근을 허용해줘야 한다.**

## 5. Role과 STS: 왜 액세스 키보다 안전한가

### 액세스 키의 구조적 문제

액세스 키(`AKIA...` + 시크릿)는 **만료되지 않는 문자열**이다. 여기서 문제가 파생된다.

```
[ 액세스 키 방식 ]                    [ Role + STS 방식 ]

 콘솔에서 키를 발급                    EC2/Lambda가 자기 역할로 자동 수령
        ▼                                      ▼
 코드·설정·CI 시크릿에 저장            ┌──────────────────────┐
        ├─ 깃 저장소에 실수로 커밋      │ AccessKeyId          │
        ├─ 로컬 PC에 평문 보관         │ SecretAccessKey      │
        └─ 퇴사자 PC에 잔존            │ SessionToken (필수)  │
        ▼                             │ Expiration (만료 시각)│
 유출돼도 알림 없음 · 만료 없음         └──────────────────────┘
                                       자동 갱신 · 만료 후 무효 · 저장할 것 없음
```

역할 방식이 안전한 이유는 세 가지로 정리된다.

1. **만료된다.** 유출되어도 유효 기간이 지나면 쓸모없어진다.
2. **저장할 것이 없다.** 코드나 설정 파일에 아무것도 적지 않으므로 애초에 유출 경로가 사라진다. "키를 잘 보관한다"보다 "키가 없다"가 강하다.
3. **누가 언제 맡았는지 기록된다.** `AssumeRole`은 CloudTrail에 남고, 세션 이름을 지정하므로 추적이 가능하다.

### EC2에서 자격 증명이 오는 경로

EC2에 인스턴스 프로파일(역할)을 붙이면, SDK와 CLI가 알아서 인스턴스 메타데이터 서비스에서 자격 증명을 가져온다. 코드에 키를 넣을 필요가 없다.

```bash
# IMDSv2: 먼저 토큰을 받고, 그 토큰으로 조회한다
TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

**IMDSv2를 강제하는 것은 중요한 보안 설정이다.** IMDSv1은 단순 GET만으로 자격 증명을 읽을 수 있어서, 애플리케이션에 SSRF 취약점이 있으면 공격자가 메타데이터 주소를 호출하게 만들어 자격 증명을 통째로 탈취할 수 있었다. IMDSv2는 PUT으로 토큰을 먼저 받게 해서 단순 SSRF로는 뚫리지 않게 만든다.

### 역할을 직접 맡아보기

```bash
# 역할 맡기 — 임시 자격 증명 3종 세트를 받는다
aws sts assume-role --role-arn arn:aws:iam::111122223333:role/DeploymentRole \
  --role-session-name deploy-hong-20260726

# 지금 내가 누구인지 확인 (권한 문제 디버깅의 첫 명령)
aws sts get-caller-identity
```

`aws sts get-caller-identity`는 권한 트러블슈팅에서 가장 먼저 쳐야 할 명령이다. **"권한이 없다"의 절반은 권한이 없는 게 아니라 내가 예상과 다른 주체로 실행되고 있는 것**이다.

### 사람과 기계를 나눠 생각하기

| 대상 | 권장 방식 | 이유 |
|---|---|---|
| 사람(개발자, 운영자) | IAM Identity Center 등 SSO로 로그인 → 역할 맡기 | 회사 계정 하나로 관리, 퇴사 시 즉시 차단 |
| EC2 / ECS / Lambda | 인스턴스 프로파일 / 태스크 역할 / 실행 역할 | 자격 증명 저장 불필요 |
| EKS 파드 | 서비스 계정에 역할 연결(IRSA) | 노드 전체가 아니라 파드 단위로 최소 권한 |
| CI/CD (GitHub Actions 등) | OIDC 연동으로 역할 맡기 | 저장소 시크릿에 장기 키를 두지 않음 |
| 외부 협력사 | 크로스 계정 역할 + 신뢰 정책 | 우리 계정에 계정을 만들어주지 않아도 됨 |

**결론: 장기 액세스 키를 만드는 것은 "다른 방법이 정말 없을 때"의 마지막 선택지다.**

## 6. S3 버킷 정책 vs IAM 정책

둘 다 S3 접근을 제어하는데 왜 나뉘어 있는가. 질문의 방향이 다르기 때문이다.

| 구분 | IAM 정책 | 버킷 정책 |
|---|---|---|
| 붙는 곳 | User / Group / Role | 버킷 자체 |
| 질문의 방향 | "이 사람은 **무엇에** 접근할 수 있나" | "이 버킷은 **누구를** 허용하나" |
| `Principal` | 없음 | 필수 |
| 크로스 계정 | 상대 계정 정책과 조합 필요 | 상대 계정을 직접 지정 가능 |
| 관리 주체 | 신원 관리자 | 데이터 소유자 |
| 그래서 언제 | 계정 내부 사용자/서비스의 권한을 역할별로 정리할 때 | 버킷 단위로 접근 원천을 통제할 때(크로스 계정, VPC Endpoint 강제, HTTPS 강제) |

**결론: 계정 안의 권한 설계는 IAM 정책으로, 버킷을 둘러싼 경계 조건은 버킷 정책으로.** 둘을 섞어 같은 규칙을 양쪽에 중복 작성하면 나중에 한쪽만 고쳐서 사고가 난다.

버킷 정책이 특히 강한 자리는 **거부 조건**이다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::my-secure-bucket", "arn:aws:s3:::my-secure-bucket/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}
```

누가 어떤 IAM 권한을 갖고 있든, 이 버킷은 HTTP로는 못 건드린다. 명시적 Deny가 모든 Allow를 이기기 때문이다.

여기에 더해 **S3 Block Public Access는 계정과 버킷 양쪽에서 켜두는 것이 기본값**이어야 한다. 공개가 정말 필요하면 CloudFront + OAC로 배포하고 버킷 자체는 잠근 채로 둔다.

## 7. 최소 권한을 실제로 실천하는 방법

"최소 권한 원칙"은 모두가 동의하지만 아무도 지키지 못하는 말이 되기 쉽다. 처음부터 정확한 권한 집합을 아는 사람이 없기 때문이다. 그래서 **한 번에 맞추려 하지 말고 좁혀 나가는 절차로 만든다.**

```
1) 시작    : 역할 단위로 만든다 (사람마다가 아니라 "배포 역할", "읽기 전용 역할")
              AWS 관리형 정책으로 일단 굴러가게 한다
                │
2) 관측    : 며칠~몇 주 실제로 쓴다. CloudTrail과 Access Advisor로
              "실제로 호출된 액션"을 수집한다
                │
3) 좁히기  : IAM Access Analyzer의 정책 생성 기능으로
              실제 사용 이력 기반 정책 초안을 만든다
                │
4) 검증    : 스테이징에서 적용해 깨지는 곳을 찾는다
              aws iam simulate-principal-policy 로 사전 검증
                │
5) 가드레일: 치명적 동작(운영 리소스 삭제, IAM 변경, 로그 비활성화)에는
              SCP/권한 경계로 명시적 Deny를 박는다
                │
6) 주기 점검: 미사용 자격 증명·미사용 권한을 정기적으로 회수한다
```

각 단계에서 쓰는 도구가 실재한다.

```bash
# 이 역할이 특정 액션을 할 수 있는지 실제 요청 없이 시뮬레이션
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::111122223333:role/AppRole \
  --action-names s3:PutObject --resource-arns "arn:aws:s3:::my-app-uploads/tmp/x.txt"

# 누가 언제 무엇을 했는지 (권한 사고 조사의 시작점)
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=DeleteBucket \
  --max-results 20

# 자격 증명 위생 리포트 (미사용 키·MFA 미설정 탐지). 생성이 비동기라 STARTED면 잠시 뒤 다시 조회한다
aws iam generate-credential-report
aws iam get-credential-report --query Content --output text | base64 -d   # 내용은 CSV
```

**IAM Access Analyzer**는 두 가지를 해준다. 하나는 리소스 정책을 분석해 **외부(다른 계정, 퍼블릭)에 열려 있는 리소스를 찾아내는 것**이고, 다른 하나는 CloudTrail 이력을 바탕으로 **실제 사용된 액션만 담은 정책을 자동 생성하는 것**이다. 3단계를 손으로 하지 않아도 되게 해준다.

이 절차와 별개로 기본기 세 가지는 예외 없이 지킨다. **루트 계정은 MFA로 잠그고 루트 액세스 키를 삭제한 뒤 일상 작업에 쓰지 않는다.** **사람 계정에는 MFA를 강제**하고 전체 관리자 권한 성격의 관리형 정책은 실사용 역할에 붙이지 않는다. **CloudTrail은 전 리전에서 켜고 로그 버킷을 변조 불가로 잠근다** — 사고가 났을 때 로그가 없으면 조사 자체가 불가능하다.

## 8. 실무에서는

### 장애 시나리오: "배포 파이프라인이 갑자기 AccessDenied를 뱉는다"

**증상**: 어제까지 잘 되던 배포가 `An error occurred (AccessDenied) when calling the PutObject operation`으로 실패. 코드는 안 바뀌었다.

**진단 순서**

```bash
# 1) 지금 누구로 실행되고 있나 — 여기서 절반이 해결된다
aws sts get-caller-identity

# 2) 그 주체가 이 액션을 할 수 있는지 시뮬레이션
aws iam simulate-principal-policy \
  --policy-source-arn <위에서 나온 ARN> \
  --action-names s3:PutObject --resource-arns "arn:aws:s3:::deploy-artifacts/app/build.zip"

# 3) 버킷 쪽 정책은 무엇을 말하고 있나
aws s3api get-bucket-policy --bucket deploy-artifacts --output text

# 4) 실제 거부 이벤트를 CloudTrail에서 확인 (errorCode를 본다)
#    주의: PutObject 같은 S3 객체 수준 호출은 "데이터 이벤트"라 트레일에서 켜둔 경우에만 기록된다
aws cloudtrail lookup-events --max-results 10 \
  --lookup-attributes AttributeKey=EventName,AttributeValue=PutObject
```

**원인 후보와 판별 신호**

| 관측 | 원인 | 대응 |
|---|---|---|
| `get-caller-identity`가 예상과 다른 역할을 반환 | 파이프라인이 다른 역할을 맡고 있음(설정 변경, 기본 프로파일 변경) | 역할 지정 복구 |
| 시뮬레이션 결과가 `implicitDeny` | 필요한 Allow가 애초에 없음 | 액션/리소스 ARN을 정확히 추가 |
| 시뮬레이션 결과가 `explicitDeny` | 어딘가에 명시적 Deny. SCP나 권한 경계일 가능성이 높다 | 조직 정책 담당자와 확인 |
| 버킷 정책에 `aws:SourceVpce` 조건 | 최근 보안 강화로 VPC Endpoint 경유만 허용됨 | 실행 위치를 VPC 안으로 옮기거나 조건 조정 |
| KMS 관련 오류가 함께 보임 | 버킷이 SSE-KMS인데 KMS 키 정책에 권한 없음 | `kms:GenerateDataKey`, `kms:Decrypt` 권한 추가 |

마지막 항목은 특히 자주 놓친다. **S3 권한을 다 줬는데도 실패한다면 KMS 키 정책을 의심한다.** 암호화된 버킷은 S3 권한과 KMS 권한이 둘 다 있어야 한다.

## 9. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. IAM의 정책 평가는 어떤 순서로 이루어집니까?**

A. 기본은 모든 것이 거부입니다. 요청이 들어오면 먼저 **적용되는 모든 정책에서 명시적 Deny가 있는지 확인하고, 하나라도 있으면 즉시 거부**합니다. 없으면 SCP나 권한 경계 같은 가드레일이 그 동작을 허용 범위에 두는지 보고, 마지막으로 신원 기반 또는 리소스 기반 정책에 Allow가 있는지 확인합니다. 어디에도 Allow가 없으면 암묵적 거부입니다. 그래서 실무에서는 **치명적인 동작에 명시적 Deny를 걸어두는 것이 Allow를 촘촘히 관리하는 것보다 실수에 강합니다.**

- 꼬리 질문: "SCP에 Allow를 넣으면 권한이 생깁니까?" → 생기지 않는다. SCP는 상한선만 정하는 가드레일이라, 실제 권한은 IAM 정책이 부여해야 한다.

**Q. 액세스 키 대신 IAM Role을 쓰라고 하는 이유가 무엇입니까?**

A. 세 가지입니다. 첫째, 역할이 발급하는 STS 임시 자격 증명은 **만료 시각이 있어서** 유출돼도 영구적으로 악용되지 않습니다. 둘째, EC2나 Lambda가 역할을 맡으면 **코드나 설정 어디에도 자격 증명을 저장하지 않으므로** 유출 경로 자체가 사라집니다. 셋째, `AssumeRole`이 CloudTrail에 세션 이름과 함께 기록되어 **누가 언제 어떤 권한을 썼는지 추적**됩니다. 반면 장기 액세스 키는 만료가 없고 유출돼도 아무 신호가 없습니다.

- 꼬리 질문: "GitHub Actions처럼 AWS 밖에서 도는 CI는 어떻게 합니까?" → OIDC 연동으로 역할을 맡게 한다. 저장소 시크릿에 장기 키를 두지 않아도 된다.

**Q. S3 버킷 정책과 IAM 정책은 어떻게 다릅니까?**

A. IAM 정책은 신원에 붙어서 "이 주체가 무엇에 접근할 수 있는가"를 정하고, 버킷 정책은 리소스에 붙어서 "이 버킷이 누구를 허용하는가"를 정합니다. 버킷 정책에는 `Principal`이 필수여서 다른 계정을 직접 지정할 수 있고, 그래서 **크로스 계정 공유나 HTTPS 강제, VPC Endpoint 경유 강제 같은 경계 조건을 걸기에 적합**합니다. 다만 크로스 계정에서는 양쪽 정책이 모두 허용해야 실제 접근이 됩니다.

- 꼬리 질문: "협력사에 파일을 한 번만 주려면요?" → Pre-signed URL이 가장 간단하다. 다만 URL 자체가 자격 증명이므로 만료를 짧게 잡는다.

**Q. 최소 권한 원칙을 실무에서 어떻게 적용합니까?**

A. 처음부터 정확한 권한 집합을 아는 사람은 없다는 전제에서 시작합니다. 역할 단위로 만들고 일단 동작하게 한 뒤, **CloudTrail과 Access Advisor로 실제로 호출된 액션을 수집**하고, IAM Access Analyzer의 정책 생성으로 사용 이력 기반 정책 초안을 만들어 좁힙니다. 적용 전에는 `simulate-principal-policy`로 검증합니다. 그리고 이 과정과 별개로, **운영 리소스 삭제나 CloudTrail 비활성화 같은 치명적 동작에는 SCP로 명시적 Deny를 걸어 상한선을 못 박아둡니다.**

- 꼬리 질문: "권한을 줄이다가 서비스를 깨뜨리면요?" → 스테이징에서 먼저 적용하고, 운영에는 관측 기간을 충분히 둔 뒤 반영한다. Access Analyzer의 미사용 액세스 탐지로 후보를 좁히면 위험이 크게 줄어든다.

## 자주 하는 실수

| 실수 | 왜 틀렸나 | 올바른 이해 |
|---|---|---|
| `Resource`에 `arn:aws:s3:::bucket/*`만 적고 `ListBucket` 허용 | 버킷과 객체는 다른 리소스다 | 버킷 ARN과 `버킷/*`를 둘 다 명시 |
| 액세스 키를 만들어 애플리케이션 설정에 저장 | 만료가 없고 유출 시 무기한 악용 | EC2/ECS/Lambda는 역할을, CI는 OIDC를 쓴다 |
| SCP에 Allow를 넣고 권한이 생겼다고 생각 | 가드레일은 상한만 정한다 | 실제 권한은 IAM 정책이 부여한다 |
| 크로스 계정에서 버킷 정책만 설정 | 양쪽 모두 허용해야 한다 | 상대 계정의 IAM 정책도 확인 |
| 문제가 생기면 일단 `*` 권한으로 열고 나중에 좁힘 | "나중에"는 오지 않는다 | 시뮬레이션으로 필요한 액션을 특정한 뒤 추가 |
| S3 권한만 주고 KMS 암호화 버킷 접근이 안 됨 | 암호화 버킷은 KMS 권한도 필요 | `kms:Decrypt`, `kms:GenerateDataKey` 추가 |
| 루트 계정으로 일상 작업 수행 | 권한 제한이 불가능하고 사고 범위가 무한 | 루트는 MFA로 잠그고 역할로 작업 |

## 한 줄 정리

IAM은 "기본은 거부, 명시적 Deny가 최우선"이라는 단 하나의 평가 규칙 위에 서 있고, 안전한 설계란 **저장할 자격 증명을 없애고(Role+STS), 치명적 동작에는 Deny를 못 박고, 나머지는 관측을 통해 점진적으로 좁혀 가는 것**이다.
