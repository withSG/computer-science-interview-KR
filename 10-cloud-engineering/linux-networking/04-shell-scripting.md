# 셸 스크립팅 (Shell Scripting)

> 손으로 반복하던 운영 작업을 **여러 번 돌려도 안전하고, 실패하면 즉시 멈추며, 왜 실패했는지 남기는** 스크립트로 바꿀 수 있게 된다.

## 학습 목표

- [ ] 반복 운영 작업을 스크립트로 옮길 때의 판단 기준을 설명할 수 있다
- [ ] 변수·조건·반복·함수를 안전한 문법으로 작성할 수 있다
- [ ] `set -euo pipefail`이 각각 무엇을 막는지, 어떤 한계가 있는지 설명할 수 있다
- [ ] 종료 코드와 `trap`으로 실패를 처리하고 뒷정리를 보장할 수 있다
- [ ] 위치 인자와 `getopts`로 인자를 처리할 수 있다
- [ ] cron의 동작 방식과 흔한 함정을 알고 스케줄링을 걸 수 있다
- [ ] 따옴표·경로·멱등성 관점에서 스크립트를 리뷰할 수 있다

## 1. 왜 필요한가

운영 작업의 상당수는 "매번 똑같은 명령을 순서대로 치는 일"이다. 배포 후 헬스체크, 로그 아카이빙, 백업, 인증서 갱신 확인, 디스크 정리 같은 것들. 손으로 하면 세 가지 문제가 생긴다.

- **재현되지 않는다.** 어제 친 명령을 오늘 똑같이 친다는 보장이 없다. 한 단계를 건너뛰거나 순서를 바꿔도 아무도 모른다.
- **지식이 사람에게만 남는다.** 그 사람이 휴가면 아무도 못 한다.
- **새벽 3시에는 사람이 없다.** 정기 작업은 사람의 근무 시간과 무관하게 돌아야 한다.

스크립트는 이 세 가지를 한 번에 해결한다. 절차가 코드로 고정되고, 파일이 곧 문서가 되고, cron이나 systemd timer에 걸면 사람 없이 돈다.

**비유**: 요리 레시피와 같다. 재료와 순서를 적어두면 누가 해도 같은 결과가 나온다.
**비유의 한계**: 레시피는 사람이 읽으면서 "어? 소금이 없네" 하고 멈추지만, **셸 스크립트는 기본적으로 실패해도 다음 줄로 넘어간다.** 백업 실패 후 삭제 명령이 그대로 실행되는 사고가 여기서 나온다. 이 기본값을 바꾸는 것이 뒤에 나올 `set -euo pipefail`이다.

한 가지 선은 그어두자. 셸 스크립트는 100줄 안쪽의 "명령을 순서대로 엮는 일"에 최적이다. 복잡한 자료구조, 정교한 예외 처리, 단위 테스트가 필요해지면 Python 같은 언어로 넘어가는 것이 맞다. 셸로 500줄짜리 로직을 쓰는 것은 잘못된 도구 선택이다.

## 2. 스크립트의 골격

```bash
#!/usr/bin/env bash
#
# rotate-logs.sh - 애플리케이션 로그를 압축 보관하고 오래된 것을 삭제한다
# 사용법: rotate-logs.sh -d /var/log/myapp [-k 14]

set -euo pipefail
IFS=$'\n\t'

readonly SCRIPT_NAME="$(basename "$0")"
readonly LOG_DIR_DEFAULT="/var/log/myapp"

main() {
  local log_dir="$LOG_DIR_DEFAULT"
  local keep_days=7
  ...
}

main "$@"
```

각 줄에 이유가 있다.

- **`#!/usr/bin/env bash`**: `#!/bin/bash`로 직접 박으면 bash 경로가 다른 환경에서 깨진다. `env`가 `PATH`에서 찾아준다.
- **`set -euo pipefail`**: 3절에서 상세히 본다.
- **`IFS=$'\n\t'`**: 기본 IFS에는 공백이 포함돼 있어서, 따옴표를 놓쳤을 때 "My Documents"가 두 개로 쪼개진다. 개행과 탭만 남기면 이 사고가 크게 줄어든다.
- **`readonly`**: 상수는 실수로 재할당되지 않게 잠근다.
- **`main "$@"`**: 로직을 함수에 넣고 마지막에 호출하면, 스크립트가 실행 중에 수정돼도 안전하고 구조도 읽기 쉬워진다.

## 3. set -euo pipefail — 기본값 바꾸기

셸의 기본 동작은 "한 줄이 실패해도 계속 진행"이다. 이 기본값이 위험한 이유를 실제로 보자.

```bash
# 이 스크립트는 백업이 실패해도 삭제를 실행한다
cd /data/important
tar czf /backup/data.tar.gz .     # 디스크가 꽉 차서 실패
rm -rf ./*                        # 그래도 실행됨 → 데이터 소실
```

```
set -e 없음                          set -e 있음
┌────────────┐                     ┌────────────┐
│ cd         │ ✓                   │ cd         │ ✓
├────────────┤                     ├────────────┤
│ tar        │ ✗ 실패              │ tar        │ ✗ 실패
├────────────┤                     └────────────┘
│ rm -rf     │ ✓ 실행됨 (사고)          즉시 종료, exit 1
└────────────┘
```

### 세 옵션이 각각 막는 것

| 옵션 | 막는 것 | 없을 때의 사고 |
|------|--------|--------------|
| `-e` (errexit) | 명령이 0이 아닌 코드로 끝나면 즉시 종료 | 실패를 무시하고 다음 단계 진행 |
| `-u` (nounset) | 정의되지 않은 변수 참조를 에러로 | `rm -rf "$DIR/"`에서 `DIR`이 비면 `rm -rf /` |
| `-o pipefail` | 파이프라인 중 하나라도 실패하면 전체 실패 | 앞 단계가 죽어도 성공으로 판정 |

`-u`의 위력이 특히 크다. 오타 하나로 `$BACKUP_DIR`가 `$BACKUP_DIRR`가 되면 빈 문자열이 되고, `rm -rf "$BACKUP_DIRR"/*`는 루트를 지우는 명령이 된다. `-u`가 켜져 있으면 그 지점에서 멈춘다.

`pipefail`도 마찬가지다.

```bash
# pipefail 없이
curl -f https://api.example.com/data | jq '.items' > out.json
echo $?     # curl이 실패해도 jq가 성공하면 0

# pipefail 있으면 curl의 실패가 전체 실패로 전파된다
```

### -e의 한계 (반드시 알아야 함)

`set -e`는 만능이 아니다. 다음 위치에서는 동작하지 않는다.

```bash
set -e

if grep -q ERROR app.log; then ...; fi   # 조건절 → 종료 안 함 (당연히 그래야 함)
grep -q ERROR app.log || echo "없음"      # ||의 왼쪽 → 종료 안 함
! grep -q ERROR app.log                  # ! 로 반전 → 종료 안 함
producer | consumer                      # 파이프라인 중간 → pipefail 없으면 무시됨
```

여기까지는 대체로 알고 있는 내용이고, 실제로 사고를 만드는 것은 이 규칙이 **함수 안쪽까지 전파된다**는 점이다. 함수를 위와 같은 "실패가 무시되는 문맥"에서 호출하면 그 함수 본문의 모든 명령에서 `set -e`가 꺼진다.

```bash
set -e

check() {
  rm /nonexistent    # 실패
  echo "여기가 실행된다"
}

# 케이스 1 — 그냥 호출하면 rm에서 스크립트가 끝난다
check

# 케이스 2 — 조건절에서 호출하면 본문 전체에서 -e가 무효가 되어
#            rm이 실패해도 다음 줄이 실행되고, echo가 성공했으므로 참으로 판정된다
if check; then
  echo "성공으로 판정"
fi
```

같은 함수인데 호출 위치에 따라 동작이 달라진다. "함수로 감싸고 `if`로 결과를 확인했으니 안전하다"고 믿는 코드가 실제로는 가장 위험한 이유다. 그래서 `set -e`를 켰다고 안심하지 말고, **실패를 반드시 잡아야 하는 지점에는 명시적으로 검사**를 넣는다.

```bash
if ! curl -fsS --max-time 10 "$HEALTH_URL" > /dev/null; then
  echo "[$SCRIPT_NAME] 헬스체크 실패: $HEALTH_URL" >&2
  exit 1
fi
```

에러 메시지는 `>&2`로 stderr에 보내는 것이 관례다. 정상 출력과 섞이지 않아야 파이프로 결과를 넘길 수 있기 때문이다.

## 4. 변수, 조건, 반복, 함수

### 변수

```bash
NAME="deploy"                 # = 앞뒤에 공백을 넣으면 안 된다
echo "$NAME"                  # 항상 큰따옴표로 감싼다
echo "${NAME}_v2"             # 뒤에 글자가 붙으면 중괄호 필수

PORT="${PORT:-8080}"          # 비어 있으면 기본값
: "${DB_HOST:?DB_HOST 환경변수가 필요합니다}"   # 비어 있으면 메시지 출력 후 종료

FILES=$(ls /var/log)          # 명령 치환. 역따옴표 대신 $() 사용 (중첩 가능)
COUNT="${#NAME}"              # 문자열 길이
BASE="${FILE%.tar.gz}"        # 뒤에서부터 패턴 제거
EXT="${FILE##*.}"             # 앞에서부터 최장 일치 제거 → 확장자
```

`: "${DB_HOST:?...}"` 패턴은 필수 환경 변수 검증의 관용구다. 스크립트 맨 위에 몰아두면 "한참 돌다가 중간에 죽는" 상황을 막는다.

### 조건문

```bash
if [[ -f "$CONFIG" ]]; then
  echo "설정 파일 있음"
elif [[ -d "$CONFIG" ]]; then
  echo "디렉토리다"
else
  echo "없음" >&2
  exit 1
fi

if [[ "$COUNT" -gt 100 && "$ENV" == "prod" ]]; then ...
if [[ "$BRANCH" == release/* ]]; then ...      # 패턴 매칭
if [[ "$VERSION" =~ ^v[0-9]+\.[0-9]+$ ]]; then ...   # 정규식
if (( count > 100 )); then ...                 # 산술 비교는 (( ))가 읽기 좋다
```

자주 쓰는 테스트: `-f` 일반 파일, `-d` 디렉토리, `-e` 존재, `-s` 크기가 0보다 큼, `-r/-w/-x` 권한, `-z` 빈 문자열, `-n` 비어 있지 않음.

### `[ ]`와 `[[ ]]`

| 항목 | `[ ]` (POSIX test) | `[[ ]]` (bash 키워드) |
|------|-------------------|---------------------|
| 이식성 | sh 포함 모든 셸 | bash/zsh 등 |
| 따옴표 없는 빈 변수 | 문법 에러 발생 | 안전하게 처리 |
| 논리 결합 | `-a` / `-o` (헷갈림) | `&&` / `\|\|` |
| 패턴 매칭 | 불가 | `==` 우변에 글롭 사용 가능 |
| 정규식 | 불가 | `=~` 지원 |

**그래서 언제 뭘 쓰나**: `#!/bin/sh`로 POSIX 호환이 필요한 경우가 아니면 `[[ ]]`를 쓴다. 실수할 여지가 훨씬 적다.

### 반복문

```bash
for f in /var/log/myapp/*.log; do       # 글롭. 공백 있는 파일명도 안전
  gzip "$f"
done

for i in {1..5}; do echo "시도 $i"; done

while IFS= read -r line; do             # 파일을 한 줄씩 읽는 정석
  echo "처리: $line"
done < hosts.txt

for host in "${HOSTS[@]}"; do           # 배열 순회
  ssh "$host" 'uptime'
done
```

`while IFS= read -r line`의 세 부분에 각각 이유가 있다. `IFS=`는 줄 앞뒤 공백이 잘려나가는 것을 막고, `-r`은 백슬래시를 이스케이프로 해석하지 않게 하며, 큰따옴표는 단어 분리를 막는다. 셋 다 빼면 파일 경로에 공백이나 백슬래시가 있는 순간 깨진다.

**`for f in $(ls)`는 쓰지 않는다.** `ls` 출력을 공백 기준으로 쪼개기 때문에 "my report.log"가 두 개로 분리된다. 글롭(`for f in *.log`)을 쓰면 이 문제가 없다.

### 함수

```bash
log() {
  echo "[$(date '+%F %T')] $*" >&2
}

deploy_one() {
  local host="$1"                       # local을 빼면 전역 변수가 오염된다
  local artifact="$2"

  log "배포 시작: $host"
  scp "$artifact" "$host:/tmp/" || return 1
  ssh "$host" "sudo systemctl restart myapp" || return 1
  log "배포 완료: $host"
}

deploy_one "web-01" "/build/app.jar" || log "web-01 실패"
```

- 함수 안 변수에는 반드시 `local`을 붙인다. 안 붙이면 전역이라 호출자의 변수를 덮어쓴다.
- `return`은 **0~255의 종료 코드만** 반환한다. 값을 돌려주려면 `echo`로 출력하고 호출부에서 `result=$(func)`로 받는다.

## 5. 종료 코드와 에러 처리

```bash
command
echo "$?"        # 직전 명령의 종료 코드
```

| 코드 | 의미 |
|------|------|
| 0 | 성공 |
| 1 | 일반적인 실패 |
| 2 | 셸 내장 명령의 잘못된 사용 (관례) |
| 126 | 파일은 있으나 실행 권한 없음 |
| 127 | 명령을 찾을 수 없음 (오타, PATH 문제) |
| 128+N | 시그널 N으로 종료 |
| 130 | Ctrl+C (128+2, SIGINT) |
| 137 | SIGKILL (128+9). 컨테이너의 OOMKilled |
| 143 | SIGTERM (128+15) |

**137을 알아두면 유용하다.** 쿠버네티스에서 컨테이너 종료 코드가 137이면 SIGKILL로 죽은 것이고, 메모리 한도 초과일 가능성이 높다. 이 판별은 [장애 트러블슈팅](./03-troubleshooting.md)에서 다룬다.

파이프라인의 각 단계 코드는 `PIPESTATUS`에 배열로 남는다.

```bash
set -o pipefail
producer | consumer
echo "${PIPESTATUS[@]}"     # 예: "1 0" → 앞 단계가 실패
```

### trap — 뒷정리 보장

스크립트가 어디서 죽든 임시 파일과 락은 반드시 치워야 한다. `trap`이 그 역할을 한다.

```bash
readonly TMPDIR_="$(mktemp -d)"
readonly LOCKFILE="/var/lock/rotate-logs.lock"

cleanup() {
  local rc=$?
  rm -rf "$TMPDIR_"
  rm -f "$LOCKFILE"
  if (( rc != 0 )); then
    log "실패로 종료 (code=$rc)"
  fi
  exit "$rc"
}
trap cleanup EXIT INT TERM
```

```
정상 흐름                    중간 실패                    Ctrl+C
   │                           │                          │
 작업 1                      작업 1                     작업 1
   │                           │                          │
 작업 2                      작업 2 ✗                   [SIGINT]
   │                           │                          │
 작업 3                     set -e 종료                    │
   │                           │                          │
   └────────► trap EXIT ◄──────┴──────────────────────────┘
                  │
             cleanup 실행 — 어떤 경로로 끝나도 반드시 지난다
```

`EXIT`는 정상 종료·`set -e` 종료 모두에서 발동한다. 여기에 `INT TERM`을 추가하면 Ctrl+C나 종료 요청에도 정리가 보장된다. 임시 파일은 `mktemp`로 만들어야 이름 충돌과 예측 가능한 경로로 인한 문제를 피한다.

## 6. 인자 처리

```bash
$0    # 스크립트 이름
$1 $2 # 위치 인자
$#    # 인자 개수
"$@"  # 모든 인자, 각각을 별개 단어로  ← 거의 항상 이것
"$*"  # 모든 인자를 하나의 문자열로 합침
$$    # 현재 스크립트의 PID
$!    # 마지막 백그라운드 프로세스의 PID
```

`"$@"`와 `"$*"`의 차이는 공백이 있는 인자에서 드러난다.

```bash
# ./run.sh "My File.txt" backup
"$@"  →  "My File.txt"  "backup"    (2개, 원형 유지)
"$*"  →  "My File.txt backup"       (1개로 합쳐짐)
```

다른 명령에 인자를 그대로 넘길 때는 반드시 `"$@"`다.

### 간단한 검증

```bash
if (( $# < 1 )); then
  echo "사용법: $SCRIPT_NAME <환경> [버전]" >&2
  exit 2
fi
env_name="$1"
version="${2:-latest}"      # 두 번째는 선택 인자
```

`set -u`가 켜진 상태에서 없을 수도 있는 인자를 참조하면 스크립트가 죽는다. `${2:-기본값}` 형태로 감싸야 한다.

### getopts — 옵션 방식

```bash
keep_days=7
log_dir=""
verbose=0

while getopts "d:k:vh" opt; do
  case "$opt" in
    d) log_dir="$OPTARG" ;;
    k) keep_days="$OPTARG" ;;
    v) verbose=1 ;;
    h) usage; exit 0 ;;
    *) usage; exit 2 ;;
  esac
done
shift $((OPTIND - 1))       # 처리한 옵션을 걷어내면 $1부터 나머지 인자
```

`"d:k:vh"`에서 콜론이 붙은 문자는 값을 받는 옵션이다. `getopts`는 짧은 옵션(`-d`)만 지원하고 긴 옵션(`--dir`)은 직접 파싱해야 한다. 그 정도로 인터페이스가 복잡해지면 이미 셸의 영역을 넘어선 것이다.

## 7. cron과 스케줄링

### 형식

```
┌───────── 분    (0-59)
│ ┌─────── 시    (0-23)
│ │ ┌───── 일    (1-31)
│ │ │ ┌─── 월    (1-12)
│ │ │ │ ┌─ 요일  (0-7, 0과 7은 일요일)
│ │ │ │ │
* * * * *  실행할 명령

30 3 * * *        매일 03:30
*/10 * * * *      10분마다
0 */6 * * *       6시간마다
0 9 * * 1-5       평일 09:00
0 0 1 * *         매월 1일 자정
@reboot           부팅 시 1회
```

```bash
crontab -e        # 현재 사용자의 crontab 편집
crontab -l        # 목록 확인
sudo crontab -u deploy -l
```

### cron이 사람을 배신하는 지점

**터미널에서는 잘 되던 스크립트가 cron에서만 실패한다**는 것이 이 주제의 전부라고 해도 과언이 아니다. 원인은 거의 항상 아래 넷 중 하나다.

```
   내 터미널                          cron
┌──────────────────┐          ┌──────────────────┐
│ ~/.bashrc 실행    │          │ 프로파일 안 읽음   │
│ PATH 풍부         │          │ PATH 매우 짧음     │
│ 환경 변수 전부     │          │ 거의 없음          │
│ 현재 디렉토리 있음  │          │ 홈 디렉토리에서 시작│
│ 출력이 화면에 보임  │          │ 출력이 사라지거나 메일│
└──────────────────┘          └──────────────────┘
```

1. **PATH가 짧다.** `docker`, `aws`, `java`가 안 잡힌다. 해결: 명령을 절대 경로로 쓰거나 스크립트 상단에 `export PATH=...`를 명시한다.
2. **환경 변수가 없다.** `.bashrc`에서 export하던 값이 하나도 없다. 해결: 스크립트가 직접 설정 파일을 읽게 한다.
3. **작업 디렉토리가 다르다.** 상대 경로가 전부 깨진다. 해결: 스크립트 안에서 `cd`를 명시한다.
4. **출력이 안 보인다.** 실패해도 아무도 모른다. 해결: 항상 로그로 리다이렉트한다.

```
30 3 * * * /usr/local/bin/rotate-logs.sh -d /var/log/myapp >> /var/log/rotate-logs.log 2>&1
```

crontab 파일 안에서는 `%`가 개행으로 해석되므로 `date +\%F`처럼 이스케이프해야 한다는 것도 잘 알려진 함정이다.

### 중복 실행 방지

10분마다 도는 작업이 12분 걸리면 두 개가 겹친다. 겹치면 안 되는 작업에는 락을 건다.

```
*/10 * * * * /usr/bin/flock -n /var/lock/sync.lock /usr/local/bin/sync.sh >> /var/log/sync.log 2>&1
```

`flock -n`은 이미 락이 잡혀 있으면 즉시 포기한다. 별도 코드 없이 중복 실행을 막는 가장 간단한 방법이다.

### cron vs systemd timer

| 항목 | cron | systemd timer |
|------|------|--------------|
| 설정 | crontab 한 줄 | `.service` + `.timer` 두 파일 |
| 로그 | 직접 리다이렉트해야 함 | journal에 자동 수집 |
| 놓친 실행 | 그냥 건너뜀 | `Persistent=true`로 부팅 후 보충 실행 |
| 의존성 | 없음 | 네트워크 준비 후 실행 등 지정 가능 |
| 자원 제한 | 없음 | 유닛에 메모리/CPU 제한 부여 가능 |
| 진입 장벽 | 낮음 | 다소 높음 |

**그래서 언제 뭘 쓰나**: 간단한 정기 작업은 cron으로 충분하다. 로그 추적과 실패 알림, 자원 제한이 중요한 운영 작업은 systemd timer가 낫다. 컨테이너 환경이라면 쿠버네티스 CronJob이 이 역할을 대신한다.

## 8. 안전한 스크립트 체크리스트

배포·삭제·백업처럼 되돌리기 어려운 작업의 스크립트는 아래를 통과해야 한다.

**따옴표**

- 모든 변수 참조를 `"$var"`로 감쌌는가
- `"$@"`를 써야 할 곳에 `$*`를 쓰지 않았는가
- `for f in $(ls)` 대신 글롭이나 `find ... -print0 | xargs -0`을 썼는가

**경로**

- cron에서 돌 것을 감안해 절대 경로를 썼는가
- 상대 경로가 필요하면 스크립트 자신의 위치를 기준으로 잡았는가

```bash
readonly SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/lib/common.sh"
```

**파괴적 명령의 안전장치**

```bash
rm -rf "${TARGET_DIR:?TARGET_DIR가 설정되지 않았습니다}"/*
```

`:?`를 붙이면 변수가 비었을 때 삭제가 실행되지 않는다. `rm -rf`를 쓰는 모든 줄에 이 습관을 붙인다.

**멱등성 (Idempotency)**

같은 스크립트를 두 번, 세 번 돌려도 결과가 같아야 한다. cron은 실패를 재시도하고, 사람도 불안하면 다시 돌린다.

```bash
mkdir -p "$DIR"                 # 이미 있어도 실패하지 않음
ln -sfn "$NEW" /opt/app/current # 기존 링크를 덮어씀
grep -q "^$LINE$" "$FILE" || echo "$LINE" >> "$FILE"   # 이미 있으면 추가 안 함
useradd deploy 2>/dev/null || true                     # 이미 있으면 넘어감
```

반대로 `echo "line" >> config`를 조건 없이 쓰면 실행할 때마다 같은 줄이 쌓인다. 전형적인 비멱등 코드다.

**검증**

```bash
bash -n script.sh        # 문법만 검사 (실행하지 않음)
bash -x script.sh        # 실행되는 명령을 하나씩 출력하며 실행
shellcheck script.sh     # 정적 분석. 따옴표 누락 등을 잡아준다
```

`shellcheck`는 CI에 넣어두면 좋다. 사람이 리뷰에서 놓치는 따옴표 문제를 기계적으로 잡는다.

**위험한 작업에는 dry-run을 넣는다**

```bash
run() {
  if (( DRY_RUN )); then
    echo "[dry-run] $*"
  else
    "$@"
  fi
}
run rm -rf "$OLD_DIR"
```

## 9. 실무에서는

**CI/CD 파이프라인의 실체가 셸 스크립트다.** GitHub Actions의 `run:` 블록, Dockerfile의 `RUN`, 젠킨스 파이프라인의 `sh` 스텝은 전부 셸이다. `set -euo pipefail`을 빠뜨리면 중간 단계가 실패해도 파이프라인이 초록불로 끝나서, 깨진 이미지가 그대로 배포된다. GitHub Actions에서는 `shell: bash`가 기본적으로 실패를 감지하도록 동작하지만, 여러 줄 스크립트에서는 첫 줄에 `set -euo pipefail`을 명시하는 편이 안전하다.

**컨테이너 entrypoint 스크립트.** 컨테이너 시작 시 설정을 렌더링하고 애플리케이션을 띄우는 스크립트를 자주 쓴다. 여기서 중요한 것은 마지막을 `exec "$@"`로 끝내는 것이다. `exec`를 쓰면 셸 프로세스가 애플리케이션으로 교체되어 애플리케이션이 PID 1이 되고, 그래야 도커나 쿠버네티스가 보내는 SIGTERM을 애플리케이션이 직접 받아 그레이스풀 셧다운을 할 수 있다. `exec` 없이 그냥 실행하면 셸이 PID 1로 남아 시그널이 애플리케이션까지 전달되지 않는다.

**언제 Ansible/Terraform으로 넘어가는가.** 서버 한두 대의 반복 작업은 스크립트가 빠르다. 하지만 대상이 수십 대가 되고 "원하는 상태"를 유지해야 하는 순간부터는 구성 관리 도구가 낫다. 이 도구들은 멱등성을 언어 차원에서 보장하고 실행 결과를 모아 보여준다. 셸로 멱등성을 손으로 구현하고 있다면 도구 교체를 검토할 시점이다.

## 10. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. 셸 스크립트 맨 위에 `set -euo pipefail`을 쓰는 이유는?**

A. 셸의 기본 동작이 "명령이 실패해도 다음 줄을 계속 실행"이라서, 백업이 실패했는데 삭제가 실행되는 식의 사고가 납니다. `-e`는 실패 시 즉시 종료하게 하고, `-u`는 정의되지 않은 변수 참조를 에러로 만들어 오타 때문에 `rm -rf "$DIR"`가 `rm -rf /`가 되는 사고를 막습니다. `-o pipefail`은 파이프라인의 종료 코드가 마지막 명령의 것만 반영하는 기본 동작을 바꿔서, `curl | jq`에서 curl이 실패해도 성공으로 판정되는 것을 막습니다.

- 꼬리 질문: "`set -e`면 모든 실패가 잡히나요?" → 아니다. `if` 조건절, `||`의 왼쪽, `!`로 반전한 명령에서는 동작하지 않는다. 특히 함수를 그런 문맥에서 호출하면 함수 본문 전체에서 `-e`가 무효가 되므로, 반드시 잡아야 하는 지점에는 명시적 검사와 `trap`을 함께 쓴다.

**Q. `"$@"`와 `"$*"`의 차이는?**

A. `"$@"`는 각 인자를 원래 경계 그대로 개별 단어로 확장하고, `"$*"`는 전부 하나의 문자열로 합칩니다. 공백이 포함된 인자가 있을 때 차이가 드러나는데, `"My File.txt"`를 넘기면 `"$@"`는 인자 한 개로 유지하지만 `"$*"`는 다른 인자와 합쳐져 경계가 사라집니다. 다른 명령에 인자를 그대로 전달할 때는 항상 `"$@"`를 씁니다.

**Q. 터미널에서는 잘 되는데 cron에서만 실패합니다. 무엇을 확인하나요?**

A. 실행 환경 차이를 봅니다. cron은 로그인 셸이 아니라 `.bashrc`나 `.profile`을 읽지 않기 때문에 PATH가 매우 짧고 환경 변수가 거의 없습니다. 그래서 `docker`나 `aws` 같은 명령이 `command not found`(종료 코드 127)로 실패합니다. 작업 디렉토리도 홈으로 시작하므로 상대 경로가 깨집니다. 대응은 명령을 절대 경로로 쓰거나 스크립트에서 PATH를 명시하고, 필요한 환경 변수를 스크립트가 직접 읽게 하며, 스크립트 안에서 `cd`로 작업 디렉토리를 고정하는 것입니다. 그리고 `>> logfile 2>&1`로 출력을 남겨야 원인을 볼 수 있습니다.

- 꼬리 질문: "작업이 겹치면요?" → `flock -n`으로 락을 걸어 중복 실행을 막는다. 실행 시간이 주기보다 길어질 수 있는 작업에는 필수다.

**Q. 스크립트의 멱등성이 왜 중요한가요?**

A. 정기 작업은 실패 시 재시도되고, 사람도 결과가 불안하면 다시 돌립니다. 그래서 두 번 돌려도 결과가 같아야 안전합니다. `mkdir -p`, `ln -sfn`, 추가 전 존재 확인 같은 방식으로 작성하면 재실행이 안전해지고, 반대로 조건 없는 `>>` 추가나 카운터 증가 같은 코드는 실행 횟수만큼 상태가 달라져서 되돌리기 어려운 문제를 만듭니다.

## 자주 하는 실수

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-----------|
| `set -euo pipefail` 생략 | 실패해도 다음 명령이 실행된다 | 스크립트 첫 줄들에 기본으로 넣는다 |
| 변수를 따옴표 없이 사용 | 공백에서 단어가 쪼개지고 글롭이 확장된다 | 항상 `"$var"` |
| `for f in $(ls)` | 공백 있는 파일명이 분리된다 | 글롭 `for f in *.log` 또는 `find -print0 \| xargs -0` |
| `NAME = "value"` | `=` 앞뒤 공백은 문법 오류 | `NAME="value"` |
| 함수 안 변수에 `local` 미사용 | 전역을 오염시켜 호출자 변수를 덮어쓴다 | `local var="$1"` |
| `return`으로 문자열 반환 시도 | `return`은 0~255 종료 코드만 | `echo`로 출력하고 `$(func)`로 받는다 |
| cron 항목에 상대 경로/환경 의존 | cron은 프로파일을 읽지 않는다 | 절대 경로 + 필요한 환경 명시 |
| cron 출력 리다이렉트 없음 | 실패해도 아무도 모른다 | `>> log 2>&1` 후 로그 감시 |
| 임시 파일 이름을 직접 지음 | 충돌·경쟁 조건·예측 가능성 문제 | `mktemp` + `trap`으로 정리 |
| entrypoint에서 `exec` 미사용 | 셸이 PID 1로 남아 SIGTERM이 앱에 안 간다 | 마지막 줄을 `exec "$@"` |
