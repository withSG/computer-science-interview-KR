# 서버 장애 트러블슈팅 (Troubleshooting)

> "서버가 느려요"라는 한 문장에서 출발해, CPU·메모리·디스크·네트워크 중 어느 자원이 병목인지 5분 안에 지표로 증명하고 1차 대응까지 마칠 수 있게 된다.

## 학습 목표

- [ ] 성능 신고를 받았을 때 위에서 아래로 좁혀가는 고정 절차를 설명할 수 있다
- [ ] Load Average를 코어 수와 추세로 해석하고, 높은 Load의 원인을 CPU와 I/O로 나눌 수 있다
- [ ] `top` / `vmstat` / `iostat` / `free`의 핵심 컬럼을 읽고 병목을 판별할 수 있다
- [ ] 디스크 풀, inode 고갈, 삭제됐지만 열린 파일 문제를 구분해 대응할 수 있다
- [ ] OOM Killer가 왜 동작했는지 근거를 찾고 재발을 막을 수 있다
- [ ] `journalctl`과 텍스트 도구로 로그에서 원인을 좁힐 수 있다

## 선행 지식

- [리눅스 기본기](./01-linux-essentials.md) - 프로세스 상태와 시그널
- [네트워크 진단 명령어](./02-networking-commands.md) - 네트워크가 원인일 때의 검증 도구

## 1. 왜 절차가 필요한가

장애 대응에서 실력 차이는 아는 명령어 개수가 아니라 **순서**에서 갈린다. 같은 상황에서 신입은 코드를 먼저 열고, 경험자는 지표를 먼저 본다. 코드부터 보면 가설이 무한히 많아서 시간이 얼마나 걸릴지 예측할 수 없지만, 지표부터 보면 **매 단계마다 후보의 절반이 사라진다.**

또 하나 중요한 원칙이 있다. **원인 규명보다 영향 축소가 먼저다.** 사용자가 계속 피해를 보는 중이라면, 원인을 몰라도 롤백하거나 인스턴스를 늘려서 피를 멈추는 것이 우선이다. 원인 분석은 그 다음에 해도 늦지 않다.

**비유**: 응급실 트리아지와 같다. 환자가 오면 병명을 먼저 맞히는 게 아니라 활력징후(맥박, 혈압, 체온, 호흡)부터 잰다. 서버의 활력징후가 CPU·메모리·디스크·네트워크다.
**비유의 한계**: 사람의 활력징후는 서로 독립적이지만 서버의 네 자원은 서로를 유발한다. 메모리 부족 → 스왑 → 디스크 I/O 폭증 → CPU iowait 상승처럼 하나의 원인이 네 지표를 전부 흔들어놓는다. 그래서 **가장 먼저 무너진 지표**를 시간축에서 찾는 것이 중요하다.

## 2. 표준 절차

```
┌──────────────────────────────────────────────────────────────────┐
│ 0단계  상황 파악 (1분)                                            │
│  · 언제부터? 전체인가 일부인가? 특정 기능만인가?                    │
│  · 최근 배포/설정 변경이 있었나?  ← 있었다면 1순위 용의자           │
├──────────────────────────────────────────────────────────────────┤
│ 1단계  영향 축소 (즉시)                                           │
│  · 배포 직후면 원인 분석 전에 롤백                                 │
│  · 트래픽 급증이면 스케일 아웃 / 레이트 리밋                        │
├──────────────────────────────────────────────────────────────────┤
│ 2단계  대시보드 (3분)                                             │
│  · p95 지연, 에러율, RPS, 자원 사용률의 "꺾인 시각"을 찾는다        │
│  · 이 시각과 배포/배치 스케줄을 대조                               │
├──────────────────────────────────────────────────────────────────┤
│ 3단계  서버 직접 확인 (5분)  ← 이 문서의 본론                      │
│  uptime → top → free -h → df -h → vmstat 1 → iostat -x 1         │
│  어느 자원이 포화됐는지 하나로 특정한다                            │
├──────────────────────────────────────────────────────────────────┤
│ 4단계  프로세스 특정                                              │
│  ps aux --sort=-%cpu / -%mem, pidstat, iotop                     │
├──────────────────────────────────────────────────────────────────┤
│ 5단계  로그 (5분)                                                 │
│  journalctl -u <svc>, dmesg -T, 애플리케이션 로그                 │
├──────────────────────────────────────────────────────────────────┤
│ 6단계  근본 원인 + 재발 방지                                       │
│  알람 추가, 임계치 조정, 코드 수정, 런북 갱신                       │
└──────────────────────────────────────────────────────────────────┘
```

3단계의 6개 명령은 순서까지 외워두면 좋다. 서버에 접속해 60초 안에 전부 칠 수 있고, 이것만으로 병목 자원이 거의 결정된다.

## 3. Load Average — 첫 번째 신호

```bash
uptime
# 10:30:01 up 12 days,  3:14,  2 users,  load average: 12.30, 8.10, 4.05
#                                                       1분    5분   15분
nproc          # 코어 수. 이걸 모르면 위 숫자는 의미가 없다
```

Load Average는 **실행 중이거나 실행을 기다리는 프로세스 수의 평균**이다. 리눅스에서는 여기에 하나가 더 들어간다.

```
Load Average = R 상태(실행 중 + 실행 대기)  +  D 상태(중단 불가 대기, 주로 디스크 I/O)
                        ↑                              ↑
                   CPU 경합                        I/O 경합
```

**D 상태가 포함된다는 것이 리눅스 Load Average의 핵심**이다. 그래서 Load가 높다고 CPU 병목이라고 단정할 수 없다. CPU는 놀고 있는데 디스크가 막혀서 Load만 치솟는 상황이 흔하다.

판단 기준은 **코어 수**다.

```
코어 8개 기준

Load  5.6 미만 (코어×0.7)  여유
Load  8.0 근처             적정 활용
Load 12.0                  대기열 형성. 지연 체감 시작
Load 30.0                  심각. 즉시 조치

추세 해석 (1분, 5분, 15분)
  12.3 > 8.1 > 4.0   부하 상승 중. 곧 더 나빠진다
  4.0 < 8.1 < 12.3   회복 중. 이미 지나간 사건일 수 있다
  8.0 ≈ 8.1 ≈ 8.0    안정적 고부하. 용량 부족
```

Load만으로는 원인을 알 수 없으므로 곧바로 `top`으로 넘어간다.

## 4. top — CPU가 어디에 쓰이고 있나

```
top - 10:30:01 up 12 days,  load average: 12.30, 8.10, 4.05
Tasks: 210 total,   4 running, 205 sleeping,   0 stopped,   1 zombie
%Cpu(s): 18.2 us,  6.1 sy,  0.0 ni, 44.0 id, 31.2 wa,  0.0 hi,  0.5 si,  0.0 st
MiB Mem :  15884.0 total,   402.1 free,  11230.5 used,   4251.4 buff/cache
MiB Swap:   2048.0 total,    120.0 free,  1928.0 used

  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
 2431 deploy    20   0  8.5g   6.1g  22000 S  92.0  39.4  514:22 java
```

세 번째 줄이 전부다.

| 항목 | 의미 | 높으면 |
|------|------|-------|
| us (user) | 사용자 코드 실행 | 애플리케이션 연산, GC 폭주, 무한 루프 |
| sy (system) | 커널 코드 실행 | 시스템 콜 과다, 컨텍스트 스위칭, 네트워크 인터럽트 |
| ni (nice) | 우선순위 조정된 프로세스 | 배치 작업 |
| id (idle) | 유휴 | 낮을수록 CPU 포화 |
| **wa (iowait)** | I/O 완료를 기다리며 논 시간 | **디스크/네트워크 스토리지 병목** |
| si (softirq) | 소프트웨어 인터럽트 | 네트워크 패킷 처리 폭주 |
| **st (steal)** | 하이퍼바이저가 다른 VM에 넘긴 시간 | **호스트 과밀 또는 버스트 크레딧 소진** |

`st`는 가상화 환경 고유의 지표다. 우리 인스턴스는 실행하고 싶은데 물리 호스트가 CPU를 안 줬다는 뜻이라, **코드를 아무리 고쳐도 해결되지 않는다.** 인스턴스 타입 변경이나 이전이 답이다. 버스터블 계열 인스턴스에서 크레딧이 바닥나면 성능이 제한되면서 이 값이 오르는 경우가 있으므로, 클라우드에서 원인 불명의 지연이 있으면 반드시 확인한다.

`wa`가 높다면 CPU가 아니라 스토리지를 봐야 한다. 그런데 `wa`는 "CPU가 놀면서 I/O를 기다린 비율"이라 CPU가 바쁘면 오히려 낮게 나온다. 그래서 `wa`가 낮다고 I/O 병목이 아니라고 단정하면 안 되고, `iostat`으로 교차 확인한다.

유용한 단축키: `P` CPU 정렬, `M` 메모리 정렬, `1` 코어별 표시, `H` 스레드 표시, `q` 종료.

`1`을 눌러 코어별로 보는 것이 중요하다. 8코어에서 전체 평균이 12%여도 한 코어만 100%면 싱글 스레드 병목이고, 이건 평균만 봐서는 절대 안 보인다.

## 5. 병목 자원 판별 흐름

```
Load Average 높음
  │
  ├─ top의 %wa 가 높다  ────► I/O 계열
  │    │
  │    ├─ iostat 의 await·%util 도 높다   → 디스크 I/O 병목
  │    │    · 슬로우 쿼리 / 로그 과다 쓰기 / 볼륨 IOPS·처리량 상한 도달
  │    │
  │    └─ vmstat 의 si·so 가 계속 0이 아니다 → 메모리 부족이 만든 I/O 폭증
  │         · 누수 / 힙 과다 설정 / 캐시 부족
  │
  └─ top의 %us·%sy 가 높다 ─► CPU 계열
       │
       ├─ %us 우세  → 애플리케이션 코드
       │    · GC 폭주 / 무한 루프 / 비효율 알고리즘
       │
       └─ %sy 우세  → 커널 경로
            · 컨텍스트 스위칭 폭주 / 인터럽트 폭주 / 시스템 콜 과다

Load 는 낮은데 응답만 느리다
  └─ 외부 의존성 지연(DB·외부 API·DNS) 또는 락 대기·커넥션 풀 고갈
     스레드가 대기만 하므로 CPU도 I/O도 쓰지 않아 어떤 시스템 지표에도 안 잡힌다
```

마지막 갈래를 놓치기 쉽다. **모든 자원 지표가 정상인데 느린 경우**가 실무에서 상당히 흔하다. 여기서 서버 지표를 붙들고 있으면 시간만 버린다. 봐야 할 것은 애플리케이션 스레드 덤프, 커넥션 풀 사용률, 분산 트레이싱의 구간별 소요 시간이다.

## 6. vmstat — 시간축으로 보기

```bash
vmstat 1        # 1초 간격
vmstat 1 10     # 10회만
```

```
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 6  3 197400  41200  12000 402000  120  340   890  1420 4200 9800 22  8 39 31  0
```

**첫 줄은 부팅 이후 누적 평균이라 무시하고 둘째 줄부터 본다.** 이 사실을 모르면 정상인 서버를 이상하다고 판단하게 된다.

| 컬럼 | 의미 | 판단 |
|------|------|------|
| r | 실행 대기 프로세스 수 | 코어 수보다 지속적으로 크면 CPU 병목 |
| b | 중단 불가 대기(D 상태) 수 | 0보다 크게 유지되면 I/O 병목 |
| si / so | 초당 swap in / out | **0이 아니면 메모리 부족.** 지속되면 스래싱 |
| bi / bo | 블록 장치 읽기/쓰기 | 급증 시점이 I/O 폭증 시점 |
| cs | 초당 컨텍스트 스위치 | 비정상적으로 크면 스레드 과다, 락 경합 |
| wa | iowait | top의 wa와 동일 |

`si`/`so`가 계속 0이 아니면 그 자체로 결론이다. 스왑은 디스크를 메모리처럼 쓰는 것이라 수십~수백 배 느리고, 스왑이 도는 순간 모든 응답 시간이 무너진다. **메모리 부족은 스왑 사용량이 아니라 `si`/`so`의 지속적 발생으로 판단한다.** 한 번 스왑에 밀려나 그대로 남아 있는 페이지는 성능에 영향을 주지 않기 때문이다.

## 7. free — 메모리를 오해하지 않기

```bash
free -h
```

```
              total        used        free      shared  buff/cache   available
Mem:           15Gi        11Gi       400Mi        50Mi        4.1Gi       3.4Gi
Swap:         2.0Gi       1.9Gi       120Mi
```

```
┌───────────────────────── total 15Gi ───────────────────────┐
│  used 11Gi (애플리케이션)  │ buff/cache 4.1Gi │ free 0.4Gi │
└────────────────────────────┴──────────────────┴────────────┘
                              └─ 필요하면 즉시 회수된다
                    available 3.4Gi = free + 회수 가능한 캐시
```

**`free`가 작다고 메모리 부족이 아니다.** 리눅스는 남는 메모리를 디스크 캐시로 쓰는 것이 정상이고, 애플리케이션이 요구하면 즉시 반환한다. 놀고 있는 메모리는 낭비이므로 캐시로 채워두는 것이 옳은 설계다. 판단은 **`available`** 로 한다.

메모리 부족의 진짜 신호는 세 가지다.

1. `available`이 지속적으로 작다
2. `vmstat`의 `si`/`so`가 계속 0이 아니다
3. `dmesg`에 OOM 로그가 있다

```bash
ps aux --sort=-%mem | head            # 메모리 상위 프로세스
ps -eo pid,rss,comm --sort=-rss | head
smem -rs uss 2>/dev/null | head       # 공유 메모리 중복 제외 (설치돼 있다면)
```

`RSS`는 공유 라이브러리를 여러 프로세스가 중복 계산하므로 합계가 실제보다 크게 나온다. 프로세스별 순수 사용량 비교에는 주의가 필요하다.

## 8. 디스크 — 세 가지 다른 고장

### 8-1. 용량 부족

```bash
df -h                                # 파일시스템별 사용률
du -sh /var/log/* | sort -rh | head  # 큰 디렉토리 찾기
du -xh / --max-depth=1 | sort -rh    # -x: 다른 파일시스템으로 넘어가지 않음
find /var/log -type f -size +500M    # 큰 파일 직접 찾기
```

디스크가 100%가 되면 로그를 못 쓰고, DB 트랜잭션이 실패하고, 임시 파일 생성이 안 되고, 심지어 SSH 로그인도 실패할 수 있다. 단일 원인으로 가장 광범위한 장애를 만든다. 그래서 85% 경고, 90% 알람을 걸어두는 것이 보통이다.

즉시 확보할 곳: 오래된 로그 압축·삭제, `journalctl --vacuum-time=3d`, `docker system prune`, `/tmp` 정리. 다만 **급하다고 로그 파일을 `rm`으로 지우면 안 된다.** 바로 다음 항목의 함정에 빠진다.

### 8-2. 삭제했는데 용량이 안 돌아온다

`df`는 95%인데 `du`로 더해보면 절반밖에 안 나오는 상황. 십중팔구 **프로세스가 열어둔 채 삭제된 파일** 때문이다.

```
파일 삭제의 실제 동작

  rm access.log
      │
      └─► 디렉토리에서 이름만 제거 (unlink)
           inode의 링크 수 1 → 0
           그러나 프로세스가 아직 열고 있으면
           ┌────────────────────────────────────┐
           │ 이름 없음 + 열린 상태 = 공간 유지    │
           │ du로는 안 보이고 df에는 잡힌다       │
           └────────────────────────────────────┘
           프로세스가 close()하거나 종료해야 실제 해제
```

```bash
lsof +L1                     # 링크 수가 1 미만인(=삭제된) 열린 파일 목록
lsof -nP | grep '(deleted)'
```

해결은 **해당 프로세스를 재시작**하는 것이다. 그래서 로그 정리는 `rm`이 아니라 truncate로 해야 한다.

```bash
: > /var/log/myapp/app.log      # 파일은 유지하고 내용만 비운다 (inode 그대로)
```

애초에 이런 일이 없도록 `logrotate`로 회전 정책을 걸고, 회전 후 `copytruncate` 또는 서비스 리로드로 파일 핸들을 갱신하게 한다.

### 8-3. inode 고갈

```bash
df -i
# Filesystem     Inodes  IUsed  IFree IUse% Mounted on
# /dev/nvme0n1p1 3276800 3276790   10  100% /
```

용량은 남았는데 파일 생성이 `No space left on device`로 실패한다면 이것이다. inode는 파일 하나당 하나씩 소비되므로 **작은 파일 수백만 개**가 원인이다. 세션 파일, 캐시 조각, 메일 큐, 잘못 설정된 임시 파일 생성 루프가 단골이다.

```bash
for d in /var/*; do echo "$(find "$d" -xdev -type f 2>/dev/null | wc -l) $d"; done | sort -rn | head
```

파일시스템 생성 시 inode 수가 정해지므로 사후에 늘리기 어렵다. 파일을 지우는 것이 유일한 즉시 해법이다.

### 8-4. I/O 성능

```bash
iostat -x 1                  # 확장 통계
iotop -o                     # 실제로 I/O 하는 프로세스만
pidstat -d 1                 # 프로세스별 I/O
```

주요 컬럼: `r/s`, `w/s`(초당 요청 수), `rkB/s`, `wkB/s`(처리량), `await`(요청당 평균 대기 시간, ms), `%util`(장치가 바빴던 시간 비율).

`await`가 평소 대비 크게 오르면 스토리지가 못 따라가고 있는 것이다. 클라우드에서는 볼륨 유형별로 IOPS와 처리량 상한이 있어서, 상한에 닿으면 스로틀링이 걸리며 `await`가 치솟는다. 이건 서버 사양이 아니라 **볼륨 스펙 문제**라 인스턴스 타입을 올려도 해결되지 않는다.

`%util`은 해석에 주의가 필요하다. 병렬 처리가 가능한 SSD/NVMe에서는 100%여도 여유가 있을 수 있어서, 회전 디스크 시절만큼 신뢰할 지표가 아니다. `await`와 큐 길이를 같이 본다.

## 9. OOM Killer

### 왜 존재하나

리눅스는 기본적으로 메모리를 **오버커밋**한다. 프로세스가 요청한 만큼 실제로 다 쓰지는 않는다는 통계적 가정 위에서, 물리 메모리보다 많이 약속해준다. 덕분에 메모리를 효율적으로 쓸 수 있지만, 모두가 약속받은 만큼 실제로 쓰기 시작하면 물리 메모리가 모자라는 순간이 온다.

이때 시스템 전체가 멈추는 것보다 낫다고 보고, 커널이 프로세스 하나를 골라 SIGKILL로 죽인다. 이것이 OOM Killer다.

```
메모리 압박
    │
    ├─ 캐시 회수 시도
    ├─ 스왑으로 페이지 밀어내기      ← 여기서 이미 응답 시간 붕괴
    └─ 그래도 부족
          │
          └─► OOM Killer 발동
               oom_score가 가장 높은 프로세스 선택
               (대체로 메모리를 가장 많이 쓰는 프로세스)
               SIGKILL — 정리 작업 없이 즉시 종료
```

### 증거 찾기

애플리케이션이 아무 로그도 남기지 않고 사라졌다면 가장 먼저 의심한다. SIGKILL이라 애플리케이션은 아무것도 남길 수 없기 때문이다.

```bash
dmesg -T | grep -i -E 'out of memory|oom.kill'
journalctl -k --since "1 hour ago" | grep -i oom
grep -i 'out of memory' /var/log/messages /var/log/syslog 2>/dev/null
```

```
Out of memory: Killed process 2431 (java) total-vm:9123456kB, anon-rss:6291456kB
```

컨테이너 환경이라면 cgroup 한도에 걸린 것일 수 있다. 쿠버네티스에서는 파드 상태가 `OOMKilled`로, 종료 코드는 `137`(=128+9, SIGKILL)로 나타난다. `kubectl describe pod`의 `Last State`에서 확인한다.

### 대응

- 즉시: 인스턴스/컨테이너 메모리 상향, 레플리카 추가로 분산
- 근본: 누수 지점 확인. JVM이라면 힙 덤프 분석
- **JVM 특유의 함정**: 컨테이너 메모리 한도를 2Gi로 주고 힙(`-Xmx`)도 2Gi로 잡으면 반드시 OOMKilled된다. 힙 외에 메타스페이스, 스레드 스택, 다이렉트 버퍼, JVM 자체 메모리가 추가로 필요하기 때문이다. 힙은 한도보다 확실히 작게 잡거나 컨테이너 인식 옵션으로 비율 지정을 쓴다.
- 절대 죽으면 안 되는 프로세스는 `oom_score_adj`를 낮춰 후보에서 밀어낼 수 있다(범위 -1000~1000). 다만 이건 다른 프로세스가 대신 죽는다는 뜻이므로 신중해야 한다.

## 10. 로그 분석

### journalctl

```bash
journalctl -u nginx -n 200 --no-pager        # 특정 서비스 최근 200줄
journalctl -u nginx -f                       # 실시간
journalctl -u myapp --since "10 min ago"
journalctl --since "2026-07-26 14:00" --until "2026-07-26 15:00"
journalctl -p err -b                         # 이번 부팅의 error 이상만
journalctl -k                                # 커널 메시지 (OOM, 디스크 오류)
journalctl -u myapp -o json-pretty | head    # 구조화된 필드 확인
journalctl --disk-usage                      # 저널이 차지한 용량
journalctl --vacuum-time=7d                  # 7일치만 남기고 정리
```

`-p`의 우선순위: `emerg` `alert` `crit` `err` `warning` `notice` `info` `debug`. 장애 시에는 `-p warning`부터 훑고 `-p err`로 좁힌다.

### 텍스트 도구 조합

```bash
tail -n 200 /var/log/myapp/app.log
tail -f /var/log/nginx/error.log
grep -i -E 'error|exception|timeout' app.log | tail -50
grep -c ' 500 ' access.log                       # 500 응답 개수
grep -A 30 'OutOfMemoryError' app.log | head -40 # 스택트레이스 앞뒤 문맥

# 접속 상위 IP
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head

# 상태 코드 분포
awk '{print $9}' access.log | sort | uniq -c | sort -rn

# 분당 요청 수 (급증 시점 찾기)
awk -F'[:[]' '{print $2":"$3":"$4}' access.log | uniq -c | tail -30
```

로그에서 자주 만나는 문장과 그 의미.

| 로그 메시지 | 진짜 의미 | 확인 |
|------------|----------|------|
| `OutOfMemoryError: Java heap space` | 힙 부족 (OOM Killer와 다름) | 힙 덤프, `-Xmx`, 누수 |
| `Too many open files` | 파일 디스크립터 한계 | `cat /proc/<pid>/limits`, `lsof -p <pid> \| wc -l` |
| `Connection pool exhausted` | 커넥션을 반납 안 하거나 DB가 느림 | 풀 크기, 쿼리 지연, CLOSE_WAIT |
| `SocketTimeoutException` | 상대가 제때 응답 안 함 | 외부 API/DB 지연 |
| `No space left on device` | 용량 또는 inode 고갈 | `df -h`, `df -i` |
| `Cannot allocate memory` | 메모리/프로세스 수 한계 | `free -h`, `ulimit -u` |

`Too many open files`는 파일뿐 아니라 **소켓도 파일 디스크립터를 쓴다**는 점이 핵심이다. 커넥션이 누수되면 결국 여기로 나타난다. systemd 서비스라면 유닛 파일의 `LimitNOFILE`을 올려야 하고, 셸에서 `ulimit -n`만 바꿔봐야 서비스에는 적용되지 않는다.

## 11. 장애 시나리오 모음

### 시나리오 A — CPU 100%, 응답 지연

```bash
uptime                                 # Load 30 (8코어)
top                                    # %us 95, %wa 1 → CPU 병목 확정
ps aux --sort=-%cpu | head -5          # java 프로세스 하나가 780%
top -H -p <PID>                        # 스레드별로 어떤 게 CPU를 먹나
```

원인 후보: 무한 루프, GC 폭주, 정규식 백트래킹, 캐시 미스로 인한 반복 연산, 트래픽 급증.
JVM이면 `jstack <PID>`로 스레드 덤프를 몇 초 간격으로 두세 번 떠서 **같은 스택에 머물러 있는 스레드**를 찾는다. 그 스택이 범인이다.
1차 대응: 배포 직후면 롤백, 아니면 레플리카 추가로 부하 분산.

### 시나리오 B — CPU는 한가한데 느리다

```bash
top          # %us 12, %wa 45   ← iowait 지배
vmstat 1     # b 컬럼 계속 5 이상, si/so 0
iostat -x 1  # await 수백 ms, %util 100
iotop -o     # 특정 프로세스가 쓰기 폭주
```

원인 후보: 로그 레벨을 DEBUG로 켜둔 채 배포, 대용량 배치 실행, DB 체크포인트, 클라우드 볼륨 IOPS 상한 도달.
`si`/`so`가 0인 것이 중요하다. 0이 아니었다면 메모리 부족이 원인인 I/O 폭증이라 대응이 완전히 달라진다.

### 시나리오 C — 프로세스가 흔적 없이 사라짐

```bash
dmesg -T | grep -i 'out of memory'     # OOM 로그 발견
free -h                                 # available 극소, swap 사용 중
```

애플리케이션 로그의 마지막 줄이 아무 예외 없이 뚝 끊겨 있다면 SIGKILL이다. 컨테이너면 종료 코드 137을 확인한다.

### 시나리오 D — 디스크 100%, 지웠는데 그대로

```bash
df -h                    # 98%
du -sh /var/log          # 2GB밖에 안 됨. 계산이 안 맞음
lsof +L1                 # 삭제됐지만 열려 있는 40GB 로그 발견
systemctl restart myapp  # 핸들 해제 → 공간 반환
```

이후 `logrotate` 설정을 점검해 재발을 막는다.

### 시나리오 E — 모든 지표가 정상인데 느리다

자원 지표가 전부 평온하다면 시스템이 아니라 **대기**를 봐야 한다. DB 커넥션 풀 고갈, 외부 API 지연, 분산 락 경합, DNS 조회 지연이 후보다.

```bash
ss -tnp state established | grep <DB_IP> | wc -l   # DB 커넥션 수
curl -o /dev/null -s -w '%{time_starttransfer}\n' http://의존서비스/health
```

이 단계에서는 서버 명령보다 APM/분산 트레이싱이 훨씬 빠르다. [네트워크 진단 명령어](./02-networking-commands.md)의 `curl -w` 시간 분해가 바로 이 상황에서 쓰인다.

## 12. 실무에서는

**지표는 사후가 아니라 사전에 쌓여 있어야 한다.** 장애가 난 뒤에 `top`을 쳐봐야 그 순간의 값만 보인다. "언제부터 나빠졌나"는 시계열 데이터가 있어야 답할 수 있고, 이것이 Prometheus/CloudWatch 같은 모니터링이 필요한 이유다. 서버 명령은 대시보드가 좁혀준 범위를 확정하는 도구지, 대시보드의 대체재가 아니다.

**런북(Runbook)을 남긴다.** 위 시나리오들을 "증상 → 확인 명령 → 판정 → 조치" 형태로 문서화해두면 다음 사람이 새벽 3시에 같은 길을 처음부터 헤매지 않는다. 장애 대응의 진짜 산출물은 복구가 아니라 런북이다.

**조치는 기록하면서 한다.** 무엇을 쳤고 무엇이 나왔는지 남기지 않으면, 상황이 끝난 뒤 원인을 재구성할 수 없고 포스트모템도 추측이 된다.

## 13. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. 서버가 느리다는 신고를 받으면 어떤 순서로 확인하시겠습니까?**

A. 먼저 신고자에게 언제부터인지, 전체인지 일부인지, 최근 배포가 있었는지를 확인합니다. 배포 직후라면 원인 분석보다 롤백을 먼저 해서 영향을 줄입니다. 그다음 모니터링 대시보드에서 지연·에러율·자원 사용률이 꺾인 시각을 찾아 범위를 좁히고, 서버에 접속해 `uptime`, `top`, `free -h`, `df -h`, `vmstat 1`, `iostat -x 1`을 순서대로 쳐서 CPU·메모리·디스크·네트워크 중 어느 자원이 포화됐는지 하나로 특정합니다. 자원이 특정되면 `ps --sort`로 프로세스를 좁히고 로그로 넘어갑니다.

- 꼬리 질문: "네 자원이 다 정상인데 느리면요?" → 대기 문제로 본다. 커넥션 풀 고갈, 외부 의존성 지연, 락 경합은 CPU도 I/O도 안 쓰므로 시스템 지표에 안 잡힌다. 스레드 덤프와 분산 트레이싱으로 간다.

**Q. Load Average가 높으면 CPU가 부족한 건가요?**

A. 아닙니다. 리눅스의 Load Average는 실행 중·실행 대기 프로세스뿐 아니라 디스크 I/O를 기다리는 D 상태 프로세스까지 포함합니다. 그래서 CPU는 절반이 놀고 있는데 스토리지가 막혀서 Load만 치솟는 경우가 흔합니다. 판단하려면 코어 수와 비교한 뒤(`nproc`), `top`의 `%us`와 `%wa`를 봐서 CPU 병목인지 I/O 병목인지 갈라야 합니다. 1분·5분·15분 값의 추세로 상승 국면인지 회복 국면인지도 같이 봅니다.

**Q. `free -h`에서 free가 200MB밖에 없습니다. 메모리 증설이 필요할까요?**

A. 그것만으로는 판단할 수 없습니다. 리눅스는 남는 메모리를 페이지 캐시로 쓰고 애플리케이션이 요구하면 즉시 회수하기 때문에, free가 작은 것은 오히려 정상입니다. 봐야 할 것은 `available` 컬럼이고, 여기에 더해 `vmstat`의 `si`/`so`가 지속적으로 0이 아닌지, `dmesg`에 OOM 기록이 있는지를 확인합니다. 이 세 가지가 겹치면 그때 실제 메모리 부족입니다.

- 꼬리 질문: "스왑 사용량이 1.9Gi인데 괜찮은가요?" → 그 자체로는 판단 근거가 못 된다. 과거에 한 번 밀려나 그대로 남아 있는 페이지는 성능에 영향을 주지 않는다. 지금 스왑이 도는지는 사용량이 아니라 `si`/`so`가 계속 0이 아닌지로 본다.

**Q. 디스크는 95%인데 큰 파일을 찾을 수가 없습니다. 왜일까요?**

A. 프로세스가 열어둔 상태에서 삭제된 파일일 가능성이 큽니다. 리눅스에서 `rm`은 디렉토리에서 이름만 제거하고, 그 파일을 연 프로세스가 있으면 공간은 반환되지 않습니다. 그래서 `du`에는 안 잡히고 `df`에만 잡힙니다. `lsof +L1`로 확인하고 해당 프로세스를 재시작하면 공간이 돌아옵니다. 예방하려면 로그는 `rm` 대신 truncate하거나 logrotate로 관리합니다. 용량이 아니라 inode가 고갈된 경우도 있으므로 `df -i`도 함께 확인합니다.

- 꼬리 질문: "서비스를 재시작할 수 없는 상황이면요?" → `/proc/<PID>/fd/<번호>`가 그 파일을 여전히 가리키고 있으므로, 해당 경로를 truncate해서 공간만 회수할 수 있다. 다만 그 프로세스가 파일 오프셋을 유지한 채 계속 쓰는 형태라면 파일에 빈 구간이 생길 수 있어 어디까지나 임시 조치다.

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-----------|
| Load Average만 보고 CPU 증설 결정 | D 상태(I/O 대기)가 포함된 통합 지표다 | `%us`/`%wa`로 CPU와 I/O를 먼저 가른다 |
| `free`의 free가 적다고 메모리 부족 판단 | buff/cache는 즉시 회수 가능하다 | `available` + `si`/`so` + OOM 로그로 판단 |
| `vmstat 1`의 첫 줄로 판단 | 첫 줄은 부팅 이후 누적 평균이다 | 둘째 줄부터 본다 |
| 디스크 확보하려고 로그를 `rm` | 프로세스가 열고 있으면 공간이 안 돌아온다 | truncate(`: > file`) 또는 logrotate |
| 용량만 보고 `No space left` 판단 | inode 고갈일 수 있다 | `df -h`와 `df -i`를 함께 확인 |
| 프로세스가 사라진 원인을 애플리케이션 로그에서만 찾음 | SIGKILL이면 아무 로그도 못 남긴다 | `dmesg`/`journalctl -k`의 OOM 기록 확인 |
| 컨테이너 메모리 한도와 JVM 힙을 같은 값으로 설정 | 힙 외 영역이 추가로 필요해 반드시 초과한다 | 힙은 한도보다 확실히 작게 |
| 원인 파악 전에는 아무것도 안 건드림 | 그동안 사용자 피해가 계속된다 | 영향 축소(롤백/스케일)가 원인 규명보다 먼저 |
