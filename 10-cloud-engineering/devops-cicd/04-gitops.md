## 1. 왜 필요한가 — Push 방식 배포의 두 가지 구멍

CI 파이프라인 마지막에 배포 단계를 붙이는 가장 흔한 방식은 이렇다.

```
┌──────────┐    ┌───────────────────┐              ┌──────────────┐
│  Git     │───▶│   CI 파이프라인     │──kubectl────▶│  운영 클러스터  │
│ (앱 코드) │    │  빌드 → 테스트 →    │   apply      │              │
└──────────┘    │  배포              │              └──────────────┘
                └───────────────────┘
                        ▲
                 여기에 클러스터 관리자 자격증명(kubeconfig)이 저장돼 있다
```

동작은 한다. 문제는 두 군데다.

### 구멍 1 — 클러스터 자격증명이 외부에 있다

CI 시스템이 클러스터에 `apply`를 하려면 클러스터를 조작할 권한이 필요하다. 그 권한은 시크릿 형태로 CI 쪽에 저장된다. 즉 **운영 클러스터의 열쇠가 클러스터 밖에, 그것도 인터넷에 연결된 SaaS에 놓인다.**

여기서 파생되는 문제들이 있다.

- CI 시스템이 뚫리면 운영 클러스터가 함께 뚫린다. 파이프라인 정의 파일 하나를 바꿀 수 있는 사람은 사실상 운영 배포 권한을 가진 것과 같다
- 환경이 늘어날수록 자격증명이 늘어난다. dev, staging, prod, 리전별 클러스터까지 하면 관리 대상이 곱으로 늘어난다
- 클러스터가 사설망 안에 있으면 외부 CI가 접근할 수 없어, 방화벽에 구멍을 뚫거나 배스천을 세워야 한다. 그 구멍이 또 다른 공격 표면이 된다

### 구멍 2 — 드리프트(Drift)

더 조용하고 더 치명적인 문제다.

```
새벽 3시. 장애가 났다. 담당자가 급하게 손을 쓴다.

  kubectl scale deployment/api --replicas=20
  kubectl set image deployment/api api=api:hotfix-2
  kubectl edit configmap/api-config    # 타임아웃 값을 늘림

서비스는 살아났다. 그리고 아무도 이 변경을 Git에 반영하지 않았다.

  Git의 선언       : replicas 4,  image api:v1.3.0,  timeout 3s
  클러스터의 실제   : replicas 20, image api:hotfix-2, timeout 30s
                     ↑ 두 개가 다르다. 이게 드리프트다.
```

이 상태에서 다음 배포가 나가면 무슨 일이 벌어질까. Git 기준으로 배포되면서 replicas가 4로 돌아가고 타임아웃 설정이 원복되어, 아무도 예상 못 한 장애가 재발한다. 원인 조사는 "우리는 아무것도 안 바꿨는데요"에서 시작해 며칠이 걸린다.

비유하자면 **설계도와 실제 건물이 다른 상태**다. 설계도만 보고 리모델링 계획을 세우면 현장에서 전혀 다른 상황을 만난다.

> 비유의 한계: 건물은 눈으로 보면 차이를 알지만, 클러스터의 드리프트는 **누가 찾아보기 전까지 보이지 않는다.** 그래서 "발견 장치"가 별도로 필요하고, 그게 GitOps 도구의 핵심 기능이다.

두 구멍 모두 원인이 같다. **변경이 클러스터 밖에서 클러스터 안으로 밀어 넣어지고(push), 밀어 넣은 뒤에는 아무도 안 본다.** 방향을 뒤집으면 어떻게 될까.

## 2. GitOps — 방향을 뒤집는다

### 4원칙

GitOps는 다음 네 가지를 만족하는 운영 모델이다.

1. **선언적(Declarative)**: 시스템의 원하는 상태를 명령의 나열이 아니라 선언으로 표현한다. "이렇게 해라"가 아니라 "이런 상태여야 한다"다.
2. **버전 관리되고 불변(Versioned and Immutable)**: 그 선언을 Git에 저장한다. 모든 변경이 커밋으로 남고 되돌릴 수 있다.
3. **자동으로 당겨온다(Pulled Automatically)**: 소프트웨어 에이전트가 Git에서 선언을 가져온다. 사람이나 CI가 밀어 넣지 않는다.
4. **지속적으로 조정된다(Continuously Reconciled)**: 에이전트가 실제 상태를 계속 관찰하고, 선언과 다르면 선언 쪽으로 되돌린다.

4번이 가장 중요하고 가장 오해받는 항목이다. GitOps는 "Git push하면 배포된다"가 아니라 **"Git과 실제가 계속 같도록 유지된다"** 이다. 배포는 그 결과로 일어나는 일일 뿐이다.

### Pull 방식의 그림

```
┌──────────────┐                    ┌────────────────── 운영 클러스터 ──────────────────┐
│  앱 코드 저장소 │                    │                                                  │
└──────┬───────┘                    │  ┌──────────────┐                                │
       │ push                       │  │  GitOps      │                                │
       ▼                            │  │  에이전트     │                                │
┌──────────────┐                    │  │  (ArgoCD)    │                                │
│ CI 파이프라인  │                    │  └──────┬───────┘                                │
│ 빌드 → 테스트  │                    │         │ ① Git을 폴링/웹훅으로 감지               │
│ 이미지 push   │                    │         │ ② 원하는 상태와 실제 상태 비교           │
└──────┬───────┘                    │         │ ③ 다르면 apply                          │
       │ 이미지 태그 갱신 커밋         │         ▼                                        │
       ▼                            │  ┌──────────────────────────────┐                │
┌──────────────┐   ◀────────────────┼──┤  Deployment / Service / ...  │                │
│ 매니페스트 저장소│      pull          │  └──────────────────────────────┘                │
│ (원하는 상태)  │                    │                                                  │
└──────────────┘                    └──────────────────────────────────────────────────┘
        ▲                                              │
        └──────────── 드리프트 발생 시 되돌림 ─────────────┘

핵심: 화살표가 클러스터 안에서 밖으로 나간다. 밖에서 안으로 들어오는 권한이 필요 없다.
```

이 구조가 앞의 두 구멍을 어떻게 막는지 보자.

- **자격증명**: CI는 이제 클러스터 권한이 필요 없다. 이미지 레지스트리에 push하고 매니페스트 저장소에 커밋하는 권한만 있으면 된다. 클러스터 권한은 클러스터 안에 있는 에이전트만 가진다
- **드리프트**: 에이전트가 계속 비교하므로 차이가 즉시 드러난다. 자가 치유를 켜두면 자동으로 되돌아간다
- **덤으로 감사 추적**: "누가 언제 무엇을 왜 바꿨나"가 전부 Git 커밋과 PR로 남는다. `kubectl` 명령 이력을 뒤질 필요가 없다
- **덤으로 롤백**: `git revert` 후 에이전트가 조정하면 이전 상태로 돌아간다

### 저장소를 왜 나누나

앱 코드 저장소와 매니페스트 저장소를 분리하는 것이 일반적이다.

- 매니페스트만 바뀌었을 때 앱 CI가 도는 낭비를 막는다
- 앱 코드 접근 권한과 배포 설정 접근 권한을 분리할 수 있다
- 매니페스트 저장소의 커밋 이력이 곧 배포 이력이 되어 읽기 쉬워진다

CI가 새 이미지를 만든 뒤 매니페스트 저장소의 이미지 태그를 갱신하는 커밋을 만드는 방식이 기본이다. 이 커밋 자체를 자동화하는 별도 컴포넌트를 쓰기도 한다.

## 3. ArgoCD의 동작

### 구성 요소

```
┌───────────────── ArgoCD (클러스터 내부) ─────────────────┐
│                                                          │
│  ┌──────────────┐  Git 저장소를 clone하고 Helm/Kustomize │
│  │ Repo Server  │  를 렌더링해 순수 매니페스트를 만든다     │
│  └──────┬───────┘                                        │
│         │ 렌더링된 매니페스트                              │
│         ▼                                                │
│  ┌──────────────┐  원하는 상태 vs 실제 상태를 비교하고     │
│  │ Application  │  차이가 있으면 apply 한다.              │
│  │ Controller   │  이게 조정 루프(reconciliation loop)다. │
│  └──────┬───────┘                                        │
│         │                                                │
│  ┌──────┴───────┐  웹 UI, CLI, API 제공                  │
│  │  API Server  │  RBAC, SSO 연동                        │
│  └──────────────┘                                        │
└──────────────────────────────────────────────────────────┘
```

### Application — 무엇을 어디에 배포할지 선언한다

ArgoCD는 배포 대상을 `Application`이라는 커스텀 리소스로 표현한다. "이 Git 경로의 매니페스트를 이 클러스터의 이 네임스페이스에 맞춰라"라는 선언이다. 자세한 YAML 예시는 [qna-cicd.md](./qna-cicd.md)에 있으니, 여기서는 각 옵션이 **어떤 운영상 결정을 담고 있는지**를 본다.

동기화 정책은 `syncPolicy.automated` 아래에 모여 있고, `prune`과 `selfHeal`은 그 하위 옵션이다. 즉 `automated`를 켜지 않으면 나머지 둘은 켜도 동작하지 않는다.

| 설정 | 켰을 때 | 꺼야 하는 경우 |
|------|--------|--------------|
| `automated` | Git이 바뀌면 사람 승인 없이 동기화 | 운영 환경에서 릴리스 시점을 통제해야 할 때 |
| `automated.prune` | Git에서 사라진 리소스를 클러스터에서도 삭제 | 클러스터에 매니페스트 밖 리소스가 섞여 있을 때 (위험) |
| `automated.selfHeal` | 클러스터가 수동 변경되면 Git 상태로 되돌림 | 긴급 수동 개입이 필요한 순간 (뒤에서 다룬다) |

**언제 뭘 쓰나**: 개발 환경은 셋 다 켜서 완전 자동으로 두고, 운영은 `automated`를 끄거나 매니페스트 저장소에 PR 승인을 강제해 사람이 릴리스 시점을 정하는 구성이 흔하다.

### 조정 루프와 두 가지 상태

ArgoCD는 각 Application에 대해 두 종류의 상태를 따로 보여준다. 헷갈리기 쉬운 지점이다.

```
Sync Status (동기화 상태)          "Git과 클러스터가 같은가?"
   Synced      : 같다
   OutOfSync   : 다르다 (Git이 바뀌었거나, 클러스터가 손으로 바뀌었거나)

Health Status (헬스 상태)          "배포된 것이 정상 동작하는가?"
   Healthy     : Pod가 Ready, Deployment가 목표 개수 충족
   Progressing : 아직 롤아웃 중
   Degraded    : 실패 (이미지 pull 실패, 크래시 루프 등)
```

**Synced인데 Degraded**인 상황이 실제로 자주 나온다. Git에 적힌 대로 정확히 apply 됐지만, 그 매니페스트가 가리키는 이미지 태그가 레지스트리에 없어서 Pod가 못 뜨는 경우다. 이 구분을 알면 진단이 빨라진다. Sync 문제면 Git이나 권한을 보고, Health 문제면 Pod와 이벤트를 본다.

조정 루프는 기본적으로 주기적 폴링으로 돌고, Git 저장소에 웹훅을 걸면 커밋 즉시 감지한다. 운영에서는 웹훅을 붙여 반영 지연을 없애는 것이 보통이다.

### 배포 순서가 필요할 때

DB 마이그레이션이 앱보다 먼저 끝나야 하는 것처럼 순서가 중요한 경우가 있다. ArgoCD는 두 장치를 제공한다.

- **Sync Wave**: 리소스에 `argocd.argoproj.io/sync-wave` 어노테이션으로 숫자를 붙이면 작은 순서부터 적용된다. Namespace → CRD → 애플리케이션 순으로 나눌 때 쓴다
- **Resource Hook**: `PreSync`, `Sync`, `PostSync`, `SyncFail` 단계에 Job을 끼워 넣는다. 마이그레이션 Job은 보통 `PreSync`다

### 시크릿은 어떻게 하나

GitOps의 원칙상 모든 것이 Git에 있어야 하는데, 시크릿을 평문으로 Git에 넣을 수는 없다. Kubernetes Secret은 base64 인코딩일 뿐 암호화가 아니라는 점도 기억해야 한다. 두 가지 접근이 있다.

- **암호화해서 Git에 넣는다**: 클러스터 안의 컨트롤러만 복호화할 수 있는 형태로 암호화한 리소스를 커밋한다. Git에 모든 것이 있다는 원칙을 유지한다
- **참조만 Git에 넣는다**: 실제 값은 외부 시크릿 저장소(Vault, 클라우드 시크릿 관리 서비스)에 두고, Git에는 "어느 키를 가져오라"는 참조만 커밋한다. 오퍼레이터가 그 참조를 보고 Secret을 만든다

후자가 운영에서 더 흔하다. 키 회전과 접근 감사를 시크릿 저장소가 담당하게 되기 때문이다.

### 장애 시나리오 — selfHeal이 긴급 조치를 되돌린다

```
증상   : 장애 대응으로 kubectl scale로 replicas를 20으로 올렸는데
         몇 분 뒤 다시 4로 돌아가 서비스가 또 죽는다.
진단   : 1) ArgoCD UI에서 해당 Application의 이벤트를 확인
              argocd app history <app-name>
         2) syncPolicy에 selfHeal이 켜져 있는지 본다
         3) 클러스터 이벤트에서 누가 스케일을 되돌렸는지 확인
              kubectl describe deployment/api | tail -30
원인   : GitOps 에이전트가 설계대로 동작한 것이다. 손으로 바꾼 것은
         드리프트로 인식되어 Git 상태로 되돌려진다. 버그가 아니다.
대응   : 즉시 - 두 가지 선택지가 있다.
         (a) 매니페스트 저장소에 replicas 변경을 커밋한다. 정석이지만 몇 분 걸린다.
         (b) 정말 급하면 해당 Application의 자동 동기화를 일시 중지한 뒤 손으로 조치하고,
             상황이 끝난 직후 반드시 Git에 반영하고 다시 켠다.
         근본 - 부하 변동은 손으로 스케일하지 말고 오토스케일러에 맡긴다.
                오토스케일러가 관리하는 필드는 매니페스트에서 제외하거나
                차이 무시(ignoreDifferences) 설정으로 충돌을 막는다.
```

이 시나리오의 교훈: **GitOps를 도입하면 "긴급할 때 손으로 고친다"는 운영 습관 자체를 바꿔야 한다.** 도구만 넣고 습관을 안 바꾸면 도구와 사람이 싸운다.

## 4. IaC와 Terraform

### 클러스터 밖에도 인프라가 있다

ArgoCD는 Kubernetes 리소스를 관리한다. 그런데 클러스터 자체는 누가 만들까. VPC, 서브넷, 로드 밸런서, 관리형 DB, IAM 역할, DNS는? 이건 클라우드 API를 호출해야 하는 영역이고, 여기가 IaC(Infrastructure as Code)의 자리다.

콘솔에서 클릭으로 만드는 방식의 문제는 앞서 본 드리프트와 정확히 같다. 누가 언제 무엇을 왜 만들었는지 남지 않고, 재현할 수 없고, 스테이징과 운영이 미묘하게 달라진다.

### Terraform의 선언적 모델

Terraform은 원하는 인프라를 HCL로 선언하면 현재 상태와 비교해 차이만큼만 API를 호출한다.

```bash
terraform init      # 프로바이더 플러그인 설치, 백엔드 설정
terraform plan      # 무엇이 생성/변경/삭제될지 미리 보여준다 (실행하지 않음)
terraform apply     # plan 결과를 실제로 적용
terraform destroy   # 관리 중인 리소스를 제거
```

`plan`이 있다는 것이 결정적이다. **적용 전에 변경 내용을 리뷰할 수 있다.** 실무에서는 PR에 `plan` 결과를 자동으로 댓글로 붙이고, 리뷰어가 그 출력을 보고 승인한 뒤 머지 시점에 `apply`가 도는 구성을 쓴다. 특히 `plan`에 "삭제 후 재생성(replace)"이 뜨는 리소스가 있는지 확인하는 게 중요하다. DB 인스턴스에 이게 뜨면 데이터가 날아간다.

### state 파일 — 왜 필요하고 왜 위험한가

Terraform은 자기가 만든 리소스의 목록과 속성을 **state 파일**에 기록한다. 이게 없으면 안 될까?

```
사용자가 선언한 것          Terraform이 아는 것          클라우드의 실제
┌────────────────┐      ┌────────────────┐      ┌────────────────┐
│  main.tf        │      │  state 파일     │      │  실제 리소스     │
│  "EC2 1대 필요"  │◀────▶│ "i-0abc123 이   │◀────▶│  i-0abc123      │
│                 │      │  내가 만든 그것" │      │                 │
└────────────────┘      └────────────────┘      └────────────────┘
        ①                       ②                       ③

①과 ③만 있으면: 클라우드에 EC2가 5대 있을 때 어느 것이 내가 관리하는 1대인지 모른다.
②가 그 연결을 기억한다. 코드의 논리적 이름과 클라우드의 실제 ID를 잇는 장부다.
```

state 파일이 하는 일이 하나 더 있다. 매번 모든 리소스를 클라우드에 조회하면 느리기 때문에, 이전에 본 속성을 캐시해두고 변경 판단을 빠르게 한다.

문제는 이 파일의 성격이다.

- **잃어버리면 곤란하다.** Terraform이 자기가 만든 리소스를 잊어버려서, 다음 `apply`에서 같은 것을 또 만들려 한다
- **동시에 쓰면 깨진다.** 두 사람이 동시에 `apply`하면 state가 서로를 덮어써 실제와 어긋난다
- **민감 정보가 들어간다.** DB 비밀번호처럼 리소스 속성으로 들어간 값이 state에 평문으로 기록될 수 있다. 그래서 state 파일을 Git에 커밋하면 안 된다

그래서 실무에서는 **원격 백엔드**를 쓴다. 클라우드 오브젝트 스토리지에 state를 두고, 암호화와 버전 관리를 켜고, **잠금(locking)** 을 걸어 동시 `apply`를 막는다. AWS라면 S3 버킷에 state를 두고 잠금 장치를 함께 구성하는 방식이 전통적이다.

### 드리프트 감지

Terraform에도 드리프트 문제가 있다. 누가 콘솔에서 보안 그룹 규칙을 하나 추가하면 코드와 실제가 달라진다.

```bash
terraform plan -refresh-only   # 실제 상태를 조회해 state와의 차이만 보여준다
```

ArgoCD와 다른 점은 **Terraform은 상시 조정하지 않는다**는 것이다. 사람이나 파이프라인이 `plan`을 돌려야 차이를 안다. 그래서 실무에서는 정기 스케줄로 `plan`을 돌려 차이가 나면 알림을 보내는 파이프라인을 따로 만든다.

이미 콘솔에서 만들어진 리소스를 Terraform 관리 아래로 가져올 때는 `terraform import`로 state에 등록한 뒤, 코드가 그 리소스와 일치하도록 작성한다. 코드를 먼저 쓰고 `plan`이 "변경 없음"이 될 때까지 맞추는 것이 순서다.

## 5. Terraform과 ArgoCD의 역할 구분

둘 다 "선언한 대로 만든다"라서 헷갈리기 쉽다. 그러나 다루는 대상과 조정 방식이 다르다.

| 기준 | Terraform | ArgoCD |
|------|----------|--------|
| 관리 대상 | 클라우드 리소스 (VPC, 클러스터 자체, RDS, IAM, DNS) | 클러스터 안의 Kubernetes 리소스 |
| 실행 주체 | 사람 또는 CI가 `apply`를 실행 | 클러스터 안 컨트롤러가 상시 실행 |
| 조정 시점 | 실행할 때만 (이벤트성) | 계속 (루프) |
| 상태 저장 | 별도 state 파일 | 별도 상태 저장 없음. 클러스터의 실제 상태가 곧 진실 |
| 드리프트 감지 | `plan`을 돌려야 안다 | 상시 감지하고 표시한다 |
| 드리프트 복구 | 사람이 `apply` | `selfHeal`로 자동 |
| 롤백 | 코드 되돌리고 다시 `apply` | `git revert` 후 자동 동기화 |
| 잘하는 것 | 생애주기가 긴 기반 인프라 | 자주 바뀌는 애플리케이션 배포 |

**언제 뭘 쓰나**: 경계는 대체로 "클러스터가 생기기 전인가 후인가"다. 클러스터와 그것이 얹힐 네트워크, 클러스터가 붙을 DB와 IAM은 Terraform. 클러스터 안에서 도는 애플리케이션과 그 설정은 ArgoCD. 둘 다 가능한 회색 지대(인그레스 컨트롤러, 모니터링 스택 같은 클러스터 애드온)는 팀 규칙으로 한쪽에 몰아준다. **같은 리소스를 두 도구가 함께 관리하는 상황만은 반드시 피한다.** 서로가 서로를 드리프트로 인식해 무한히 되돌리는 싸움이 난다.

### 장애 시나리오 — apply가 잠금에서 멈춘다

```
증상   : terraform apply 실행 시 "Error acquiring the state lock" 으로 멈춘다.
진단   : 1) 에러 메시지에 나온 Lock ID, 잠근 사람, 잠근 시각을 읽는다
         2) 그 시각에 CI 파이프라인이 돌고 있었는지 확인한다
         3) 팀 채널에 "지금 apply 중인 분 계신가요"를 먼저 묻는다
원인   : 세 가지 중 하나다.
         - 다른 사람 또는 파이프라인이 실제로 apply 중이다 → 기다린다
         - 앞선 apply가 중간에 강제 종료되어 잠금이 남았다
         - 네트워크 단절로 잠금 해제 요청이 실패했다
대응   : 실행 중인 작업이 없다는 것을 확인한 뒤에만 강제 해제한다.
              terraform force-unlock <LOCK_ID>
         진행 중인 apply가 있는데 강제 해제하면 state가 깨져 복구가 훨씬 어려워진다.
         근본 - apply는 사람 로컬이 아니라 파이프라인 한 곳에서만 실행하도록 통제한다.
                환경별로 state를 분리해 잠금 경합 자체를 줄인다.
```

## 6. 실무에서는

GitOps와 IaC를 도입할 때 실제로 시간이 드는 것은 도구 설치가 아니라 **저장소와 환경을 어떻게 나눌지 결정하는 일**이다.

- **환경 분리**: 디렉터리로 나눌지, 브랜치로 나눌지. 브랜치로 나누면 환경 간 변경 전파가 머지가 되어 매력적이지만, 환경별 차이가 영구 diff로 남아 관리가 어려워진다. 디렉터리 분리에 오버레이(Kustomize)나 값 파일(Helm)로 차이를 표현하는 방식이 더 널리 쓰인다
- **템플릿 도구**: Helm은 패키징과 배포에, Kustomize는 기본 매니페스트에 환경별 패치를 얹는 데 강하다. 섞어 쓰기도 한다
- **Application 관리**: Application이 수십 개가 되면 그것들을 관리할 상위 Application을 두는 "App of Apps" 패턴이나, 하나의 정의에서 여러 Application을 생성하는 방식을 쓴다
- **Terraform 상태 분리**: 하나의 거대한 state는 `plan`이 느려지고 잠금 경합이 심해지며 실수의 폭발 반경이 커진다. 환경별, 계층별(네트워크/데이터/애플리케이션)로 나눈다

## 7. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. GitOps가 기존 CI/CD 배포와 무엇이 다른가요?**

A. 배포 트리거의 방향이 다릅니다. 기존 방식은 CI 파이프라인이 클러스터에 밀어 넣는 Push 방식이라, CI 쪽에 클러스터 자격증명이 저장되어야 합니다. GitOps는 클러스터 안의 에이전트가 Git을 당겨오는 Pull 방식이라 외부에 클러스터 권한을 둘 필요가 없습니다. 더 중요한 차이는 지속적 조정입니다. Push 방식은 배포 순간 이후로는 아무도 실제 상태를 보지 않아 드리프트가 쌓이는데, GitOps 에이전트는 선언과 실제를 계속 비교해 차이를 드러내고 자동으로 되돌립니다.

- 꼬리 질문: "Git이 다운되면 배포가 멈추지 않나요?" → 새 배포는 멈추지만 이미 돌고 있는 서비스에는 영향이 없다. Git 가용성이 배포 파이프라인의 의존성이 되는 것은 맞고, 그래서 매니페스트 저장소의 가용성을 별도로 챙긴다.

**Q. ArgoCD의 selfHeal은 항상 켜두는 게 좋은가요?**

A. 환경에 따라 다릅니다. 개발이나 스테이징은 켜두는 게 좋습니다. 실험적 수동 변경이 자동으로 정리되어 환경이 항상 Git과 일치합니다. 운영은 주의가 필요합니다. 장애 대응 중 손으로 조치한 것이 몇 분 뒤 되돌려져 장애가 재발할 수 있습니다. 그래서 운영에서는 켜두되 긴급 시 동기화를 일시 중지하는 절차를 팀이 알고 있어야 하고, 오토스케일러처럼 다른 컨트롤러가 관리하는 필드는 차이 무시 설정으로 충돌을 미리 막아둡니다.

- 꼬리 질문: "긴급 조치를 하고 나면 무엇을 해야 하나요?" → 상황이 끝나는 즉시 Git에 반영하고 동기화를 다시 켠다. 이 후속 조치를 빠뜨리면 다음 배포에서 조치가 사라진다.

**Q. Terraform의 state 파일은 왜 필요한가요? 없으면 안 되나요?**

A. 코드에 적힌 논리적 이름과 클라우드의 실제 리소스 ID를 연결하는 장부입니다. 이게 없으면 클라우드에 있는 여러 리소스 중 어느 것이 이 코드가 만든 것인지 알 수 없어서, 다음 실행 때 같은 것을 또 만들거나 남의 리소스를 건드릴 수 있습니다. 다만 위험도 함께 옵니다. 리소스 속성이 그대로 기록되므로 민감 정보가 평문으로 들어갈 수 있고, 동시에 두 사람이 적용하면 깨집니다. 그래서 Git에 커밋하지 않고, 암호화와 버전 관리를 켠 원격 백엔드에 두고, 잠금을 걸어 동시 실행을 막습니다.

- 꼬리 질문: "state를 잃어버리면 어떻게 하나요?" → 원격 백엔드의 버전 관리로 복구를 먼저 시도하고, 안 되면 `terraform import`로 실제 리소스를 하나씩 다시 등록한다. 그래서 백엔드 버저닝이 사실상 필수다.

**Q. Terraform과 ArgoCD를 함께 쓸 때 역할을 어떻게 나누시겠습니까?**

A. 클러스터가 생기기 전의 것은 Terraform, 클러스터 안의 것은 ArgoCD로 나눕니다. VPC, EKS 클러스터 자체, RDS, IAM 역할, DNS는 Terraform이 관리하고, 그 클러스터 위에서 도는 애플리케이션 매니페스트는 ArgoCD가 관리합니다. 조정 방식이 다른 것도 이 경계와 맞습니다. 기반 인프라는 변경이 드물고 신중해야 하니 `plan` 리뷰 후 적용하는 이벤트성 모델이 맞고, 애플리케이션은 자주 바뀌니 상시 조정 루프가 맞습니다. 중요한 건 같은 리소스를 둘이 함께 관리하지 않는 것입니다. 그러면 서로를 드리프트로 인식해 계속 되돌리는 충돌이 납니다.

- 꼬리 질문: "인그레스 컨트롤러나 모니터링 스택은 어느 쪽인가요?" → 회색 지대다. 정답이 있다기보다 팀 규칙으로 한쪽에 몰아주는 것이 중요하다. 클러스터 생성 직후 반드시 있어야 하는 것은 Terraform으로, 나머지는 ArgoCD로 가르는 기준이 흔하다.

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-----------|
| "GitOps = Git push하면 자동 배포" | 자동 배포는 결과일 뿐, 본질은 지속적 조정이다 | Git과 실제가 계속 같도록 유지되는 것이 핵심 |
| CI 파이프라인이 `kubectl apply`를 직접 실행 | 클러스터 자격증명이 외부에 노출된다 | CI는 커밋까지, 적용은 클러스터 안 에이전트가 |
| 긴급 상황에 `kubectl edit`로 조치하고 끝 | selfHeal이 되돌려 장애가 재발한다 | 동기화 일시 중지 → 조치 → 즉시 Git 반영 → 재개 |
| Kubernetes Secret을 그대로 Git에 커밋 | base64는 인코딩이지 암호화가 아니다 | 암호화 후 커밋하거나 외부 시크릿 저장소를 참조 |
| Terraform state를 Git에 커밋 | 민감 정보 평문 노출, 동시 수정 충돌 | 암호화·버저닝·잠금이 되는 원격 백엔드 사용 |
| `plan` 없이 바로 `apply` | 삭제 후 재생성으로 데이터가 날아갈 수 있다 | PR에 `plan` 출력을 붙이고 replace 여부를 확인 |
| 하나의 거대한 state로 전체 인프라 관리 | `plan`이 느려지고 잠금 경합과 실수 반경이 커진다 | 환경별·계층별로 분리 |
| 같은 리소스를 Terraform과 ArgoCD가 함께 관리 | 서로를 드리프트로 보고 무한히 되돌린다 | 소유권을 한쪽에 명확히 지정 |

## 한 줄 정리

GitOps는 배포 방향을 Push에서 Pull로 뒤집어 **클러스터 권한을 밖으로 내보내지 않고 드리프트를 상시 감지**하는 모델이고, Terraform은 클러스터 밖 인프라를 state 파일이라는 장부로 추적하는 이벤트성 IaC이며, 둘의 경계는 "클러스터가 생기기 전인가 후인가"로 나눈다.
