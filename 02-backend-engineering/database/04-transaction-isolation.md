# 트랜잭션과 격리 수준 (Transaction & Isolation Level)

> 동시에 실행되는 트랜잭션이 서로를 어디까지 볼 수 있는지, MySQL이 락 없이 그걸 해내는 원리는 무엇인지, 그리고 동시 수정 충돌을 낙관적/비관적 락 중 무엇으로 막을지 판단할 수 있게 된다.

## 학습 목표

- [ ] ACID 네 가지 속성을 각각 무엇이 보장해 주는지 설명할 수 있다
- [ ] Dirty Read, Non-Repeatable Read, Phantom Read를 구분하고 어느 격리 수준에서 막히는지 안다
- [ ] MySQL InnoDB가 REPEATABLE READ에서 MVCC와 갭 락으로 무엇을 하는지 설명할 수 있다
- [ ] 낙관적 락과 비관적 락을 상황에 맞게 선택할 수 있다

## 선행 지식

- SQL의 `BEGIN` / `COMMIT` / `ROLLBACK`
- [영속성 컨텍스트](./02-persistence-context.md) - 트랜잭션이 영속성 컨텍스트의 경계라는 점

## 1. 왜 필요한가

계좌 이체는 두 개의 UPDATE로 이루어진다.

```sql
UPDATE account SET balance = balance - 10000 WHERE id = 1;   -- 출금
UPDATE account SET balance = balance + 10000 WHERE id = 2;   -- 입금
```

첫 번째와 두 번째 사이에 서버가 죽으면 돈이 공중에서 사라진다. 이 두 문장을 **하나의 덩어리로 묶어, 전부 반영되거나 전부 없던 일이 되게** 하는 장치가 트랜잭션이다.

혼자 쓰는 DB라면 여기서 끝이다. 문제는 **수백 개의 트랜잭션이 동시에 같은 행을 건드릴 때** 생긴다. 완전히 순서대로 하나씩 실행하면 정확하지만 처리량이 바닥난다. 그렇다고 마음대로 섞으면 결과가 틀린다. 이 사이 어디에 설 것인지를 정하는 다이얼이 **격리 수준**이다.

> **비유** — 공유 문서를 여러 명이 동시에 편집하는 상황이다. "남이 저장하기 전 초안까지 다 보이는 모드", "저장된 것만 보이는 모드", "내가 열었을 때의 버전을 끝까지 보는 모드"를 고르는 것과 같다.
>
> **비유의 한계** — 문서 편집기는 화면 표시만 달라지지만, DB의 격리 수준은 **락 획득 범위와 성능**까지 바꾼다. 높은 격리 수준은 단순히 "덜 보이는" 게 아니라 다른 트랜잭션을 대기시킨다.

## 2. ACID

| 속성 | 무엇을 보장하나 | 어떻게 구현되나 |
|------|----------------|----------------|
| Atomicity(원자성) | 전부 반영되거나 전부 취소된다 | 언두 로그(Undo Log)에 변경 전 값을 남겨 두고 롤백 시 되돌린다 |
| Consistency(일관성) | 트랜잭션 전후로 DB 제약이 깨지지 않는다 | PK/FK/UNIQUE/CHECK 제약, 트리거 |
| Isolation(격리성) | 동시 트랜잭션이 서로 간섭하지 않는다 | 락, MVCC, 격리 수준 |
| Durability(지속성) | 커밋된 결과는 장애가 나도 살아남는다 | WAL(Write-Ahead Logging). InnoDB의 리두 로그(Redo Log) |

**Durability의 구현 방식을 알아 두면 좋다.** 커밋할 때마다 데이터 파일을 디스크에 쓰는 건 너무 느리다. 그래서 InnoDB는 변경 내용을 **먼저 순차 기록되는 리두 로그에 쓰고** 커밋을 완료한다. 실제 데이터 페이지는 나중에 천천히 디스크로 내려간다. 장애가 나면 재기동 시 리두 로그를 재생해 복구한다. 랜덤 쓰기를 순차 쓰기로 바꾸는 것이 핵심 아이디어다.

**네 가지 중 실무에서 가장 자주 다루는 건 Isolation이다.** 나머지 셋은 DB가 알아서 해 주지만, 격리 수준은 개발자가 고르고 그 결과를 감당해야 하기 때문이다.

## 3. 세 가지 이상 현상

### Dirty Read — 커밋되지 않은 값을 읽는다

```
시간 →

트랜잭션 A ──[balance 1000 → 2000 UPDATE]────────[ROLLBACK]──
                        │
트랜잭션 B ─────────────[SELECT → 2000 읽음]──────────────────
                                  ↑
                        존재한 적 없는 값을 읽었다
```

A가 롤백하면 2000이라는 값은 DB 어디에도 없었던 값이 된다. B가 그 값으로 계산했다면 결과 전체가 오염된다.

### Non-Repeatable Read — 같은 행을 두 번 읽었는데 값이 다르다

```
트랜잭션 A ──[SELECT id=1 → 1000]────────────────[SELECT id=1 → 2000]──
                                       │
트랜잭션 B ────────────────[UPDATE 2000 + COMMIT]──────────────────────
```

A의 관점에서는 "내가 아무것도 안 했는데 값이 변했다". 조회 결과를 근거로 판단하고 그 다음 문장에서 다시 조회하는 로직이라면 앞뒤가 어긋난다.

### Phantom Read — 같은 조건으로 조회했는데 행 개수가 다르다

```
트랜잭션 A ──[WHERE age > 20 → 3건]──────────────[WHERE age > 20 → 4건]──
                                       │
트랜잭션 B ────────────────[age=25 INSERT + COMMIT]────────────────────
```

Non-Repeatable Read는 **값**이 바뀌는 것, Phantom Read는 **행 수**가 바뀌는 것이다. 원인도 다르다. 전자는 UPDATE/DELETE, 후자는 INSERT다.

## 4. 격리 수준 4단계

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read | 기본값인 DB |
|----------|:---:|:---:|:---:|---|
| READ UNCOMMITTED | 발생 | 발생 | 발생 | (거의 안 씀) |
| READ COMMITTED | 방지 | 발생 | 발생 | Oracle, PostgreSQL, SQL Server |
| REPEATABLE READ | 방지 | 방지 | 발생(표준 기준) | MySQL InnoDB |
| SERIALIZABLE | 방지 | 방지 | 방지 | (성능상 특수 상황만) |

표에서 "발생"은 **SQL 표준이 허용한다**는 뜻이지 반드시 일어난다는 뜻이 아니다. 실제 동작은 DB 구현에 따라 다르다. 대표적인 게 MySQL InnoDB로, REPEATABLE READ에서 Phantom Read도 대부분 막는다(5절).

**READ UNCOMMITTED**는 얻는 것에 비해 잃는 게 커서 실무에서 쓰지 않는다. PostgreSQL은 아예 이 수준을 지정해도 내부적으로 READ COMMITTED로 동작시킨다.

**READ COMMITTED**는 문장(statement)마다 최신 커밋 상태를 본다. 짧은 트랜잭션이 대부분인 OLTP에서 무난해서 여러 DB의 기본값이다. 대신 같은 트랜잭션에서 같은 행을 두 번 읽으면 값이 달라질 수 있다.

**REPEATABLE READ**는 트랜잭션이 처음 읽은 시점의 상태를 끝까지 유지한다. 조회-판단-조회 흐름의 일관성이 필요할 때 유리하다.

**SERIALIZABLE**은 트랜잭션들이 하나씩 순서대로 실행된 것과 같은 결과를 보장한다. MySQL에서는 일반 SELECT까지 공유 락을 걸어 이를 구현하므로, 읽기끼리도 쓰기를 막는 상태가 되어 처리량이 크게 떨어진다.

```java
// Spring에서 메서드 단위로 지정 (기본값은 DB 설정을 따르는 DEFAULT)
@Transactional(isolation = Isolation.READ_COMMITTED)
public void process() { ... }
```

격리 수준을 올리기 전에 먼저 물어야 할 질문이 있다. **"이 문제가 정말 격리 수준으로 풀어야 할 문제인가?"** 대부분의 동시성 사고(재고 차감, 좌석 예약, 포인트 사용)는 격리 수준을 올려서가 아니라 **락이나 원자적 UPDATE로** 푸는 것이 맞다(6절).

## 5. MySQL InnoDB의 REPEATABLE READ

### 5.1 MVCC — 락 없이 일관된 읽기

InnoDB는 행을 수정할 때 **덮어쓰지 않는다.** 변경 전 버전을 언두 로그에 남기고, 각 행에는 "이 버전을 만든 트랜잭션 ID"가 함께 기록된다.

```
                    현재 테이블                      언두 로그 (과거 버전 체인)
                ┌──────────────────┐            ┌──────────────────┐
  balance       │ balance = 2000   │ ─────────▶ │ balance = 1000   │
                │ trx_id  = 120    │            │ trx_id  = 90     │
                └──────────────────┘            └──────────────────┘
                       ↑                               ↑
   trx 130 이 읽으면 ──┘                               │
   (120은 이미 커밋됨 → 최신 버전 사용)                 │
                                                       │
   trx 100 이 읽으면 ─────────────────────────────────┘
   (120은 내 시작 이후 → 과거 버전을 따라간다)
```

트랜잭션은 시작할 때 **읽기 뷰(Read View)** 를 만든다. "그 시점에 어떤 트랜잭션들이 아직 진행 중이었나"를 담은 스냅샷이다. 행을 읽을 때 그 행의 버전이 내 읽기 뷰 기준으로 보이면 안 되는 것이면, 언두 로그를 따라 과거 버전으로 거슬러 올라간다.

두 격리 수준의 차이는 **읽기 뷰를 언제 만드는가** 하나로 정리된다.

| | READ COMMITTED | REPEATABLE READ |
|---|---|---|
| 읽기 뷰 생성 시점 | SELECT 문장마다 새로 | 트랜잭션의 첫 조회 시 한 번 |
| 같은 행 반복 조회 | 다른 값이 나올 수 있다 | 항상 같은 값 |
| 갭 락 | 사용하지 않음 | 사용함 |

이 방식의 가장 큰 이득은 **읽기가 쓰기를 막지 않고, 쓰기가 읽기를 막지 않는다**는 것이다. 조회에 락을 걸지 않으므로 동시성이 크게 올라간다.

참고로 InnoDB에서 읽기 뷰는 `START TRANSACTION` 문장이 아니라 **트랜잭션 내 첫 조회 시점**에 만들어진다. "트랜잭션 시작 시점 스냅샷"이라는 설명은 대체로 맞지만, 정확히는 첫 읽기 시점이다.

### 5.2 갭 락 — 없는 행을 잠근다

MVCC는 **일반 SELECT**를 보호한다. 그런데 `SELECT ... FOR UPDATE`처럼 락을 거는 읽기(Locking Read)는 스냅샷이 아니라 현재 데이터를 봐야 한다. 여기서 Phantom Read를 막는 두 번째 장치가 필요하다.

```
id 기준으로 정렬된 인덱스

        ░░░░░░░░  ← 갭 락 (−∞ ~ 1)
   [ id = 1 ]     ← 레코드 락
        ░░░░░░░░  ← 갭 락 (1 ~ 3)
   [ id = 3 ]     ← 레코드 락
        ░░░░░░░░  ← 갭 락 (3 ~ 5)
   [ id = 5 ]     ← 레코드 락
        ░░░░░░░░  ← 갭 락 (5 ~ +∞)

레코드 락 : 존재하는 행의 수정/삭제를 막는다
갭   락 : 행과 행 "사이의 빈 공간"에 INSERT하는 것을 막는다
넥스트키 락 = 레코드 락 + 그 앞쪽 갭 락
```

```sql
-- 트랜잭션 A
START TRANSACTION;
SELECT * FROM users WHERE age > 20 FOR UPDATE;   -- 넥스트키 락 획득

-- 트랜잭션 B (같은 시각)
INSERT INTO users VALUES (4, 27);   -- 갭 락에 막혀 대기
```

행이 아직 존재하지 않는 구간까지 잠그기 때문에, 조건에 맞는 새 행이 끼어드는 걸 원천 차단한다. 이게 InnoDB가 REPEATABLE READ에서 Phantom Read를 막는 방식이다.

**대가도 있다.** 갭 락은 존재하지 않는 행을 잠그므로, 서로 다른 값을 INSERT하려던 트랜잭션들이 같은 갭에서 충돌해 대기하거나 데드락에 빠질 수 있다. 인덱스가 없는 컬럼으로 범위 조건을 걸면 락 범위가 테이블 전체로 번지기도 한다. 락을 거는 쿼리는 **인덱스가 잘 잡혀 있는 조건으로** 좁혀야 한다는 실무 규칙이 여기서 나온다.

### 5.3 예외: MVCC로도 막히지 않는 경우

```sql
-- 초기: id=1(age=15), id=3(age=25)
-- 트랜잭션 A
START TRANSACTION;
SELECT * FROM users WHERE age > 20;   -- 1건 (id=3)

    -- 트랜잭션 B
    INSERT INTO users VALUES (5, 35);
    COMMIT;

-- 트랜잭션 A
SELECT * FROM users WHERE age > 20;   -- 여전히 1건 (스냅샷 기준, 정상)

UPDATE users SET age = 99 WHERE age > 20;   -- 현재 데이터 기준으로 실행됨
                                            -- → id=5 도 함께 수정된다

SELECT * FROM users WHERE age > 20;   -- 2건! 유령이 나타났다
```

UPDATE는 스냅샷이 아니라 **현재 데이터에 적용된다.** 그 결과 id=5는 "내 트랜잭션이 직접 수정한 행"이 되고, 자기가 수정한 행은 항상 자기에게 보여야 하므로 이후 조회에 등장한다. 면접에서 이 예외까지 언급하면 원리를 이해했다는 신호가 된다.

## 6. 동시 수정 충돌: 낙관적 락 vs 비관적 락

### 6.1 격리 수준으로는 안 풀리는 문제

```
재고 10개, 두 사용자가 동시에 1개씩 주문

트랜잭션 A: SELECT stock → 10
트랜잭션 B: SELECT stock → 10
트랜잭션 A: UPDATE stock = 9   (10 - 1)
트랜잭션 B: UPDATE stock = 9   (10 - 1)   ← A의 차감이 덮어써졌다

2개 팔렸는데 재고는 1개만 줄었다
```

**갱신 손실(Lost Update)** 이다. 두 트랜잭션 모두 커밋에 성공했고 격리 수준도 지켜졌는데 결과가 틀렸다. 애플리케이션이 "읽은 값으로 계산해서 다시 쓰는" 구조이기 때문에, 격리 수준만으로는 막을 수 없다.

### 6.2 낙관적 락 — 충돌은 드물다고 가정한다

락을 걸지 않고, **커밋할 때 그 사이 아무도 안 건드렸는지 검사**한다. JPA는 `@Version` 필드로 지원한다.

```java
@Entity
public class Product {
    @Id @GeneratedValue
    private Long id;

    private int stock;

    @Version
    private Long version;   // JPA가 자동으로 관리한다
}
```

```sql
-- JPA가 만드는 UPDATE
UPDATE product SET stock = 9, version = 6
WHERE id = 1 AND version = 5;
--                        ^^^^^^^^^^^
-- 다른 트랜잭션이 먼저 커밋했다면 version 이 이미 6이라 0건 갱신
-- → JPA가 이를 감지해 예외를 던진다
```

갱신된 행이 0건이면 JPA는 `OptimisticLockException`을 던지고, Spring Data JPA 환경에서는 `ObjectOptimisticLockingFailureException`으로 변환되어 올라온다. 애플리케이션은 이 예외를 잡아 **재시도**하거나 사용자에게 "다른 사용자가 먼저 수정했습니다"를 알린다.

DB 락을 잡지 않으므로 성능 부담이 없다. 대신 **충돌 시 실패하므로 재시도 로직이 반드시 필요**하다.

### 6.3 비관적 락 — 충돌이 잦다고 가정한다

읽는 순간 DB 락을 걸어 다른 트랜잭션을 대기시킨다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Product p where p.id = :id")
Optional<Product> findByIdForUpdate(@Param("id") Long id);
```

```sql
-- 실행되는 SQL
SELECT * FROM product WHERE id = 1 FOR UPDATE;
-- 이 트랜잭션이 커밋/롤백할 때까지, 같은 행에 락을 걸려는 트랜잭션(FOR UPDATE)과
-- UPDATE/DELETE 를 시도하는 트랜잭션이 대기한다.
-- 락을 걸지 않는 일반 SELECT 는 MVCC 덕분에 대기 없이 자기 버전을 읽는다.
```

충돌이 나도 실패하지 않고 순서대로 처리된다. 대신 락 대기가 생기므로 처리량이 떨어지고, 락을 잡는 순서가 트랜잭션마다 다르면 **데드락**이 발생할 수 있다.

### 6.4 선택 기준

| | 낙관적 락 | 비관적 락 |
|---|---|---|
| 방식 | `@Version`으로 커밋 시점 검증 | `SELECT ... FOR UPDATE`로 즉시 락 |
| DB 락 | 걸지 않음 | 걸림 |
| 충돌 시 | 예외 발생 → 재시도 필요 | 대기했다가 순서대로 처리 |
| 처리량 | 충돌이 드물면 높음 | 락 대기로 낮아짐 |
| 위험 | 재시도 폭주 | 데드락, 락 대기 타임아웃 |
| 그래서 언제 | 게시글 수정, 프로필 변경 등 같은 행 충돌이 드문 경우 | 한정 수량 재고 차감, 좌석 예약 등 충돌이 잦고 실패하면 안 되는 경우 |

**세 번째 선택지도 기억해 두자.** 값을 읽지 않고 DB에서 원자적으로 처리할 수 있으면 락 자체가 필요 없다.

```sql
UPDATE product SET stock = stock - 1
WHERE id = 1 AND stock >= 1;
-- 갱신 행 수가 0이면 재고 부족. 읽기-계산-쓰기 구간이 없으므로 갱신 손실도 없다
```

단순 카운터 증감이나 재고 차감은 이 방식이 가장 빠르고 안전한 경우가 많다. 다만 JPA의 변경 감지를 거치지 않는 벌크 연산이므로 1차 캐시와의 불일치에 주의한다([영속성 컨텍스트](./02-persistence-context.md) 9절).

---

## 7. 실무에서는

**트랜잭션은 짧게.** 트랜잭션이 열려 있는 동안 DB 커넥션과 락을 붙잡는다. 트랜잭션 안에서 외부 API를 호출하거나 파일을 업로드하면, 상대 서버가 느려질 때 커넥션 풀이 먼저 마른다. 외부 호출은 트랜잭션 밖으로 빼는 게 원칙이다.

**현재 격리 수준은 이렇게 확인한다.**

```sql
-- MySQL 8.0
SELECT @@transaction_isolation;

-- 진행 중인 트랜잭션과 락 대기 확인 (MySQL 8.0)
SELECT * FROM performance_schema.data_locks;
SELECT * FROM information_schema.innodb_trx;
```

**데드락은 없앨 수 없고 줄이는 것이다.** 여러 행을 잠글 때 **항상 같은 순서(예: PK 오름차순)로** 접근하도록 코드를 맞추면 순환 대기가 사라진다. InnoDB는 데드락을 감지하면 한쪽을 롤백시키므로, 애플리케이션은 해당 예외를 잡아 재시도할 수 있어야 한다.

## 8. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. 트랜잭션 격리 수준 네 가지와 각각 허용되는 이상 현상을 설명해 주세요.**

A. READ UNCOMMITTED는 커밋 전 데이터까지 읽어 Dirty Read가 발생합니다. READ COMMITTED는 커밋된 것만 읽어 Dirty Read를 막지만, 문장마다 최신 상태를 보므로 Non-Repeatable Read와 Phantom Read가 남습니다. REPEATABLE READ는 트랜잭션 내내 같은 스냅샷을 보므로 Non-Repeatable Read까지 막고, 표준상 Phantom Read가 남습니다. SERIALIZABLE은 전부 막지만 동시성이 크게 떨어집니다. MySQL InnoDB 기본값은 REPEATABLE READ, Oracle과 PostgreSQL은 READ COMMITTED입니다.
- 꼬리 질문: "Non-Repeatable Read와 Phantom Read 차이는?" → 전자는 같은 행의 값이 바뀌는 것(UPDATE/DELETE), 후자는 조건에 맞는 행 개수가 바뀌는 것(INSERT)이다.

**Q. MySQL은 REPEATABLE READ인데 왜 Phantom Read가 거의 안 생기나요?**

A. 두 가지 장치가 있습니다. 일반 SELECT는 MVCC로 처리되어 트랜잭션의 읽기 뷰 기준 과거 버전을 언두 로그에서 읽으므로, 이후 커밋된 INSERT가 보이지 않습니다. `SELECT ... FOR UPDATE` 같은 락 읽기는 스냅샷을 쓰지 않으므로 넥스트키 락, 즉 레코드 락과 갭 락을 함께 걸어 조건 범위에 새 행이 INSERT되는 것을 차단합니다.
- 꼬리 질문: "완전히 막히나요?" → 아니다. 스냅샷 조회 후 같은 조건으로 UPDATE를 실행하면 UPDATE는 현재 데이터에 적용되므로, 그때 수정된 행이 이후 조회에 나타난다.

**Q. MVCC의 장점이 무엇인가요?**

A. 읽기가 락을 잡지 않는다는 점입니다. 수정 시 이전 버전을 언두 로그에 남겨 두고 각 트랜잭션이 자기 읽기 뷰에 맞는 버전을 읽기 때문에, 읽기와 쓰기가 서로를 막지 않습니다. 격리성을 유지하면서 동시성을 확보하는 방식입니다.
- 꼬리 질문: "단점은?" → 오래 열린 트랜잭션이 있으면 언두 로그를 정리하지 못해 버전 체인이 길어지고, 조회할 때 체인을 거슬러 올라가는 비용과 저장 공간이 늘어난다.

**Q. 재고 차감 같은 동시성 문제를 어떻게 해결하시겠어요?**

A. 먼저 읽기-계산-쓰기 구간을 없앨 수 있는지 봅니다. `stock = stock - 1 WHERE stock >= 1` 같은 원자적 UPDATE로 처리되면 락이 필요 없습니다. 그럴 수 없는 로직이라면 충돌 빈도로 판단합니다. 충돌이 드물면 `@Version` 기반 낙관적 락에 재시도를 붙이고, 한정 수량 판매처럼 충돌이 잦고 실패하면 곤란한 경우에는 `SELECT ... FOR UPDATE` 비관적 락을 씁니다.
- 꼬리 질문: "비관적 락의 위험은?" → 락 대기로 처리량이 떨어지고, 잠그는 순서가 엇갈리면 데드락이 난다. 락 획득 순서를 통일하고 타임아웃을 설정해야 한다.

## 자주 하는 실수

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-----------|
| 격리 수준을 올리면 갱신 손실도 막힌다고 생각한다 | 읽기-계산-쓰기는 애플리케이션 로직이라 격리 수준의 관할이 아니다 | 원자적 UPDATE나 낙관적/비관적 락으로 푼다 |
| REPEATABLE READ가 모든 DB에서 Phantom Read를 허용한다고 외운다 | InnoDB는 MVCC와 갭 락으로 대부분 막는다 | "표준상 허용, 구현에 따라 다르다"로 이해한다 |
| MVCC를 "커밋된 것만 읽는 기능"으로 이해한다 | 버전을 여러 개 유지해 각 트랜잭션이 자기 시점 버전을 읽는 구조다 | 언두 로그와 읽기 뷰까지 함께 설명한다 |
| 낙관적 락에 재시도 없이 `@Version`만 붙인다 | 충돌 시 예외가 그대로 사용자에게 전달된다 | 재시도 또는 명확한 실패 안내를 함께 설계한다 |
| 트랜잭션 안에서 외부 API를 호출한다 | 응답이 늦으면 커넥션과 락을 그만큼 오래 붙잡는다 | 외부 호출은 트랜잭션 밖으로 분리한다 |

---

## 한 줄 정리

격리 수준은 동시 트랜잭션이 서로를 어디까지 볼지 정하는 다이얼이고, MySQL InnoDB는 MVCC로 락 없는 일관된 읽기를, 갭 락으로 팬텀 방지를 구현한다. 다만 갱신 손실은 격리 수준이 아니라 락 전략으로 풀어야 한다.
