# JWT 토큰 (JSON Web Token)

> JWT는 "서버가 기억하지 않는 대신, 표 자체에 정보를 적고 위조 방지 도장을 찍는" 방식이다.
> 이 문서를 읽고 나면 토큰 세 조각을 직접 해독하고, 서명이 무엇을 보장하고 무엇을 보장하지 않는지,
> 왜 발급한 토큰을 취소하기가 그토록 어려운지 설명할 수 있다.

## 학습 목표

- [ ] 실제 JWT 문자열을 세 조각으로 나눠 각각이 무엇인지 해독할 수 있다
- [ ] 서명이 보장하는 것(위조 방지)과 보장하지 않는 것(기밀성)을 구분할 수 있다
- [ ] HS256과 RS256을 언제 각각 쓰는지 근거를 대며 고를 수 있다
- [ ] Access Token과 Refresh Token을 분리하는 이유를 설명할 수 있다
- [ ] JWT를 즉시 무효화하기 어려운 근본 원인과 우회책 세 가지를 비교할 수 있다
- [ ] 토큰 저장 위치별 XSS/CSRF 취약점을 판단할 수 있다

## 선행 지식

## 1. 왜 필요한가 — 저장소 조회를 없애고 싶다

세션 방식의 구조적 부담은 하나로 요약된다. **요청마다 저장소를 조회해야 한다.**

```
[세션]  요청 → WAS → Redis 조회 → 사용자 확인 → 처리
                      ↑ 매 요청마다 네트워크 왕복
                        Redis가 죽으면 전원 로그아웃
                        서비스가 10개면 10개 모두 이 Redis를 바라봐야 함
```

마이크로서비스에서 이 부담이 특히 커진다. 주문·결제·알림 서비스가 각각 "이 요청 보낸 사람이 누구지?"를
확인하려면 전부 같은 저장소를 찔러야 한다. 서비스 간 결합이 생기고 저장소는 병목이 된다.

**발상의 전환**: 서버가 기억하는 대신 **정보를 표 자체에 적어두면** 저장소 조회가 필요 없다.
문제는 위조다. 표에 "나는 관리자다"라고 적혀 있으면 누구나 그렇게 적어서 낼 수 있다. 그래서 발급자가
**위조 방지 도장(서명)**을 찍는다. 도장을 검증할 수 있는 쪽만 진짜와 가짜를 구별한다.

이것이 JWT다. **정보를 담고, 서명으로 위조를 막고, 서버는 아무것도 기억하지 않는다.**

> **비유**: 종이 신분증과 같다. 이름과 생년월일이 그 위에 적혀 있으니 발급 기관에 전화해서 확인할 필요가
> 없다. 대신 위조 방지 홀로그램이 붙어 있어 가짜를 걸러낸다.
>
> **비유의 한계**: 신분증은 분실 신고를 하면 즉시 정지되지만, JWT는 한 번 발급되면 만료 전까지 발급자도
> 되돌릴 수 없다. 이 차이가 JWT의 가장 큰 약점이며 5장의 주제다.

## 2. 구조 — 실제 토큰을 뜯어보자

JWT는 `.`으로 구분된 세 조각이다. 아래는 jwt.io에서 예제로 쓰이는 실제 토큰이다.

```
Header    │ eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
          │ .
Payload   │ eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ
          │ .
Signature │ SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

앞 두 조각은 **Base64URL 인코딩**일 뿐이라 지금 바로 해독할 수 있다. 표준 Base64와 달리 `+`/`/` 대신
`-`/`_`를 쓰고 끝의 `=` 패딩을 떼는데, URL이나 헤더에 그대로 실려도 이스케이프가 필요 없게 만든 변형이다.
그래서 `base64 -d`에 날것으로 넘기면 길이가 맞지 않아 실패한다. 떼어 낸 만큼 채워 주면 된다.

```bash
echo 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9' | base64 -d
# {"alg":"HS256","typ":"JWT"}

# 길이가 4의 배수가 되도록 '='를 채운다. '-'나 '_'가 섞여 있다면 tr '_-' '/+'로 함께 되돌린다
echo 'eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ==' | base64 -d
# {"sub":"1234567890","name":"John Doe","iat":1516239022}
```

세 번째 조각은 바이너리 해시라 텍스트로 해독되지 않는다. 대신 **직접 계산해 맞춰볼 수 있다.**
이 토큰의 서명 키는 문자열 `your-256-bit-secret`이다.

```bash
H='eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9'
P='eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ'

printf '%s' "$H.$P" \
  | openssl dgst -sha256 -hmac 'your-256-bit-secret' -binary \
  | openssl base64 -A | tr '+/' '-_' | tr -d '='
# SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c   ← 토큰의 세 번째 조각과 동일
```

여기서 두 가지가 드러난다. **서명은 헤더와 페이로드 문자열 전체에 대한 HMAC**이므로 페이로드를 한 글자만
바꿔도 값이 달라진다. 그리고 **키를 모르면 서명을 다시 만들 수 없으므로** 위조가 안 된다.

### 페이로드에 들어가는 것 — 등록된 클레임

페이로드의 각 항목을 **클레임(Claim)**이라 부른다. 표준으로 정해진 이름들이 있다.

| 클레임 | 이름 | 의미 | 실무 용도 |
|--------|------|------|----------|
| `iss` | Issuer | 발급자 | 여러 발급자를 신뢰할 때 검증 |
| `sub` | Subject | 토큰의 주체 | 보통 사용자 고유 ID |
| `aud` | Audience | 대상 수신자 | 이 토큰이 내 서비스용인지 확인 |
| `exp` | Expiration Time | 만료 시각(Unix time) | **필수에 가깝다.** 없으면 영구 토큰 |
| `nbf` | Not Before | 이 시각 전에는 무효 | 예약 발급 |
| `iat` | Issued At | 발급 시각 | 토큰 나이 계산, 일괄 무효화 기준점 |
| `jti` | JWT ID | 토큰 고유 식별자 | **블랙리스트의 키로 쓴다** |

여기에 서비스가 필요한 값(`role`, `tenantId` 등)을 자유롭게 추가할 수 있다. 다만 페이로드가 커지면
**모든 요청의 헤더 크기가 커진다.** 세션 ID는 수십 바이트인데 JWT는 수백 바이트~1KB가 되기도 한다.

### 안티패턴: 페이로드에 아무거나 담기

```json
{ "sub": "7", "email": "kim@example.com", "phone": "010-1234-5678",
  "internalMemo": "VIP, 클레임 이력 3건", "password": "hashed_value" }
```

**왜 문제인가**

Base64는 암호화가 아니라 **인코딩일 뿐이다.** 토큰을 가진 사람은 누구든 위 명령 한 줄로 전부 읽는다.
개발자 도구를 열 줄 아는 사용자, 브라우저 확장 프로그램, 중간에 로그를 남기는 프록시 전부가 이 값을 본다.
"서명이 있으니 안전하다"는 오해가 이 실수를 만든다. 서명은 **읽기를 막는 게 아니라 고치기를 막는다.**

**개선**

```json
{ "iss": "https://auth.myservice.com", "sub": "7", "aud": "myservice-api",
  "role": "USER", "iat": 1516239022, "exp": 1516240822, "jti": "b1f0c9e4-…" }
```

식별자와 권한 판단에 꼭 필요한 최소한만 담는다. 이메일이나 이름이 필요하면 `sub`로 DB를 조회한다.
"조회를 없애려고 JWT를 썼는데?"라고 생각할 수 있지만, **인증 검증에는 조회가 없다**는 것이 핵심이다.
프로필 데이터를 읽는 것은 어차피 비즈니스 로직이다.

## 3. 서명 — 무엇을 보장하고 무엇을 보장하지 않나

**보장하는 것**은 둘이다. 페이로드가 발급 이후 변경되지 않았다는 **무결성**, 이 토큰을 만든 것이 키를
가진 발급자라는 **진정성**.

**보장하지 않는 것**은 셋이다. 내용은 누구나 읽으므로 **기밀성**이 없고, 토큰을 그대로 복사해 쓰면 정상
요청과 구분되지 않으므로 **재사용 방지**가 없으며, 서명이 유효하고 만료 전이면 서버가 거부할 근거가
없으므로 **취소 가능성**이 없다.

내용까지 숨기려면 JWS(서명)가 아니라 **JWE(JSON Web Encryption)**를 써야 한다. 다만 실무에서 JWE는
드물다. 애초에 민감정보를 안 담는 편이 간단하기 때문이다.

### HS256 vs RS256

```
[HS256 — 대칭키]                       [RS256 — 비대칭키]

  발급 서버                              인증 서버
  secret ──서명──► JWT                   개인키 ──서명──► JWT
                    │                                      │
  검증 서버         ▼                    검증 서버 A/B/C     ▼
  secret ──검증──► OK                    공개키 ──검증──► OK

  → 검증하려면 서명할 수 있는             → 검증만 가능. 공개키가 유출돼도
    키를 그대로 줘야 한다                   토큰을 만들 수 없다
```

| 구분 | HS256 (HMAC-SHA256) | RS256 (RSA-SHA256) |
|------|---------------------|---------------------|
| 키 구조 | 하나의 비밀 키 | 개인키(서명) + 공개키(검증) |
| 검증자에게 주는 것 | 비밀 키 그대로 | 공개키만 |
| 검증자가 토큰을 위조할 수 있나 | **가능** | 불가능 |
| 서명/검증 속도 | 빠름 | 느림 |
| 언제 쓰나 | 발급자와 검증자가 **같은 주체**일 때(모놀리식) | 발급자와 검증자가 **다를 때**(MSA, 서드파티) |

한 줄 결론: **토큰을 만드는 쪽과 검사하는 쪽이 같은 애플리케이션이면 HS256, 검사만 하는 주체가 따로
있으면 RS256.** 마이크로서비스 10개에 HS256 비밀 키를 뿌리는 순간, 그중 하나만 뚫려도 관리자 토큰이
찍혀 나온다.

### 안티패턴: 검증을 안 하고 디코딩만 한다

```js
// 안티패턴
const payload = jwt.decode(token);   // 서명을 확인하지 않는다
return payload.sub;
```

**왜 문제인가**

`decode`는 Base64를 풀기만 한다. 공격자가 헤더와 페이로드를 원하는 대로 쓰고 서명 자리에 아무 문자열이나
붙여도 통과한다. `{"sub":"1","role":"ADMIN"}`을 직접 만들어 넣으면 그대로 관리자가 된다. `decode`는
만료된 토큰의 내용을 로그에 남기는 것처럼 **검증이 필요 없는 상황에서만** 쓰는 함수다.

**개선**

```js
const payload = jwt.verify(token, process.env.JWT_SECRET, {
  algorithms: ['HS256'],                    // 알고리즘을 서버가 고정한다
  issuer: 'https://auth.myservice.com',
  audience: 'myservice-api',
});
return payload.sub;
```

`algorithms` 옵션이 특히 중요하다. 이 값을 주지 않으면 검증 알고리즘을 고르는 결정권이 **토큰 헤더의
`alg`** 쪽으로 넘어갈 수 있다. 이를 노린 공격이 둘 있다.

- **`alg: none` 공격** — 헤더를 `{"alg":"none"}`으로 바꾸고 서명 자리를 비우면, 검증을 건너뛰는
  구현에서 무조건 통과한다.
- **알고리즘 혼동(Algorithm Confusion)** — RS256을 쓰는 서버에 `alg`를 `HS256`으로 바꾼 토큰을 보낸다.
  서버가 "HMAC 검증에 쓸 키"로 **공개키를 그대로 사용**하면, 공개키는 누구나 아는 값이므로 공격자가
  유효한 서명을 만들 수 있다.

둘 다 "알고리즘을 토큰이 정하게 둔" 것이 원인이다. 요즘 라이브러리들은 키 타입으로 후보를 좁히거나
`none`을 아예 거부하는 식으로 방어선을 두고 있지만, 그 방어에 기대는 것과 직접 못 박는 것은 다르다.
**검증 알고리즘은 항상 서버 코드가 고정한다.**

## 4. Access Token과 Refresh Token

토큰 하나만 쓰면 만료 시간을 정할 수 없는 딜레마에 빠진다. 길게(30일) 잡으면 탈취당했을 때 30일간
무방비고, 짧게(15분) 잡으면 사용자가 15분마다 재로그인해야 한다. 해결책은 **역할을 쪼개는 것**이다.

| 구분 | Access Token | Refresh Token |
|------|-------------|---------------|
| 용도 | 모든 API 호출의 인증 | Access Token 재발급 **전용** |
| 유효기간 | 짧게 (분 단위) | 길게 (일~주 단위) |
| 전송 빈도 | 요청마다 (노출 많음) | 갱신할 때만 (노출 적음) |
| 서버 저장 | 안 함 | **저장하는 편이 좋다** (무효화 위해) |
| 권장 보관 위치 | 메모리(JS 변수) | HttpOnly + Secure + SameSite 쿠키 |

핵심 원리 한 줄: **자주 노출되는 것은 짧게, 오래 사는 것은 노출을 줄인다.**

```
  Client                              Auth Server            Resource API
    │ POST /login                          │                      │
    ├─────────────────────────────────────►│                      │
    │ AT(15분) + RT(14일, HttpOnly 쿠키)    │                      │
    │◄─────────────────────────────────────┤                      │
    │ GET /orders   Authorization: Bearer AT                      │
    ├────────────────────────────────────────────────────────────►│
    │                     … 15분 경과 …                            │
    │ GET /orders   → 401 Unauthorized (exp 초과)                  │
    │◄────────────────────────────────────────────────────────────┤
    │ POST /token/refresh  (RT 쿠키 자동 전송)                     │
    ├─────────────────────────────────────►│  저장된 RT와 대조     │
    │ 새 AT + 새 RT (Rotation)              │                      │
    │◄─────────────────────────────────────┤                      │
```

### Refresh Token Rotation

단순 Refresh Token에는 구멍이 있다. **탈취를 탐지할 방법이 없다.** 공격자가 Refresh Token을 훔쳐
계속 Access Token을 받아가도 서버 입장에서는 정상 사용자와 구분되지 않는다.

Rotation은 재발급할 때마다 Refresh Token도 새것으로 바꾸고 **이전 것을 즉시 무효 처리**한다.
여기에 재사용 감지(Reuse Detection)를 붙인다.

```
정상:  RT1 ──재발급──► RT2 ──재발급──► RT3      (RT1, RT2는 폐기됨)

탈취:  공격자가 RT2를 훔쳐 먼저 사용 → RT3 발급, RT2 폐기
       정상 사용자가 나중에 RT2로 재발급 시도
       → "이미 폐기된 토큰이 다시 왔다" = 탈취 발생 신호
       → 해당 사용자의 토큰 계보 전체를 무효화하고 재로그인 요구
```

이 설계의 묘미는 **누가 진짜인지 몰라도 된다**는 점이다. 폐기된 토큰이 다시 등장했다는 사실 자체가
어느 한쪽이 복제본이라는 증거이므로, 양쪽 다 끊고 다시 로그인시키면 비밀번호를 모르는 공격자는 밀려난다.

## 5. 왜 JWT는 취소하기 어려운가

JWT의 장점과 단점은 **같은 성질에서 나온다.** 서버가 아무것도 기억하지 않는다는 것.

```
[세션]  로그아웃 → 저장소에서 세션 삭제 → 즉시 차단
                   ↑ 서버가 "권한의 원본"을 쥐고 있음

[JWT]   로그아웃 → 클라이언트가 토큰 삭제
                   ↑ 서버는 아무것도 안 함
                     이미 복사해 둔 토큰이 있다면 만료 전까지 계속 유효
```

강제 로그아웃, 계정 정지, 권한 강등이 **다음 만료 시각까지 반영되지 않는다.** "토큰을 무효화한다"는 말
자체가 JWT의 설계 전제와 충돌한다. 우회책은 셋이다.

| 방법 | 원리 | 대가 |
|------|------|------|
| **만료를 짧게** | 5~15분 뒤 자연 소멸 | 무효화까지 최대 그 시간만큼 지연, 갱신 요청 증가 |
| **블랙리스트** | 무효화된 `jti`를 Redis에 저장하고 검증 시 조회 | **저장소 조회가 부활한다** — Stateless를 일부 포기 |
| **토큰 버전** | 사용자별 `tokenVersion`을 DB에 두고 값이 다르면 거부 | 사용자 단위 일괄 무효화만 가능, 조회는 여전히 필요 |

```js
// 로그아웃: 남은 유효기간만큼만 블랙리스트에 올린다
const { jti, exp } = jwt.verify(token, secret, { algorithms: ['HS256'] });
const ttl = exp - Math.floor(Date.now() / 1000);
// TTL 지정 문법은 클라이언트마다 다르다 (아래는 ioredis 기준)
if (ttl > 0) await redis.set(`bl:${jti}`, '1', 'EX', ttl);

// 검증: 서명 확인 후 블랙리스트 조회
const payload = jwt.verify(token, secret, { algorithms: ['HS256'] });
if (await redis.exists(`bl:${payload.jti}`)) throw new Error('revoked token');
```

TTL을 토큰의 남은 수명과 맞추는 것이 핵심이다. 어차피 만료된 토큰은 서명 검증 단계에서 걸리므로
블랙리스트에 영원히 남겨둘 이유가 없다. 이렇게 하면 블랙리스트 크기가 자동으로 관리된다.

**"그럼 세션이랑 뭐가 다른가?"** — 차이는 조회 실패 시의 기본값이다. 세션은 저장소에 **있어야** 통과지만
블랙리스트는 저장소에 **없어야** 통과다. 즉 Redis가 잠시 죽어도 JWT는 (무효화가 반영되지 않을 뿐)
서비스가 계속 돌아간다. 또 블랙리스트에는 로그아웃·정지된 소수만 들어가므로 데이터 양이 훨씬 적다.

현실적인 조합은 이렇다. **Access Token은 짧게 + 무상태로 검증, Refresh Token은 서버에 저장 + Rotation.**
강제 로그아웃은 Refresh Token을 지우는 것으로 처리하고, Access Token은 몇 분 안에 자연 만료되게 둔다.
즉시성이 반드시 필요한 관리자 기능에만 블랙리스트를 추가한다.

## 6. 어디에 저장할 것인가

| 저장 위치 | XSS | CSRF | 비고 |
|-----------|-----|------|------|
| `localStorage` | **매우 취약** | 안전 | 스크립트 한 줄로 탈취. 새로고침해도 남아 피해가 길다 |
| `sessionStorage` | **매우 취약** | 안전 | 탭 단위로 사라질 뿐 XSS에는 동일하게 뚫린다 |
| 일반 쿠키 | 취약 | **매우 취약** | `document.cookie`로 읽히고 자동 전송까지 된다. 최악 |
| HttpOnly 쿠키 | 안전 | 취약 | JS 접근 불가. 단 브라우저가 자동 전송 |
| HttpOnly + Secure + SameSite | 안전 | 안전 | **권장 조합** |
| JS 메모리 변수 | 상대적으로 안전 | 안전 | 새로고침 시 사라짐 → Refresh Token으로 복구 |

`localStorage`가 특히 위험한 이유는 XSS의 **파급력** 때문이다. 사이트 어디든 스크립트 주입이 하나만
성립하면 `localStorage.getItem('token')` 한 줄로 끝난다. 반면 CSRF는 `SameSite` 속성 한 줄로 대부분
막힌다. **막기 쉬운 위험을 감수하고 막기 어려운 위험을 없애는 쪽**이 합리적이다.

### 안티패턴: 토큰 둘 다 localStorage에

```js
// 안티패턴
localStorage.setItem('accessToken', at);
localStorage.setItem('refreshToken', rt);
```

**왜 문제인가**

XSS 한 번으로 두 토큰이 모두 털린다. Access Token만 털렸다면 몇 분 뒤 만료되지만, Refresh Token까지
털리면 공격자는 **몇 주 동안 토큰을 계속 갱신**할 수 있다. 사용자가 비밀번호를 바꿔도 서버에서 Refresh
Token을 폐기하지 않는 한 세션이 유지된다. 짧은 만료로 얻은 이점이 통째로 무너지는 지점이다.

**개선**

```js
// 서버: Refresh Token은 응답 본문이 아니라 쿠키로 내려준다
res.cookie('rt', refreshToken, {
  httpOnly: true, secure: true, sameSite: 'strict',
  path: '/auth/refresh',                       // 갱신 요청에만 전송되도록 경로를 좁힌다
  maxAge: 14 * 24 * 60 * 60 * 1000,
});
res.json({ accessToken });                     // AT만 본문으로

// 클라이언트: AT는 메모리에만
let accessToken = null;
async function refresh() {
  const res = await fetch('/auth/refresh', { method: 'POST', credentials: 'include' });
  accessToken = (await res.json()).accessToken;
}
```

Access Token은 `Authorization` 헤더로 보내 브라우저가 자동 전송하지 않으므로 CSRF와 무관하고, Refresh Token은 쿠키 속성으로 CSRF를 막는다.

## 7. 실무에서는

**JWT가 맞는 상황** — 여러 서비스·도메인이 같은 인증을 공유해야 하거나(MSA, 서버 간 API), 모바일 앱이
주 클라이언트라 쿠키를 쓰기 번거롭거나, 인증 서버와 검증 서버가 조직적으로 분리돼 RS256으로 공개키만
배포하고 싶을 때다.

**JWT가 과하거나 부적절한 상황** — 브라우저 한 종류만 상대하는 단일 서비스라면 세션이 더 단순하고 안전하다.
강제 로그아웃이 **초 단위로** 반영돼야 하는 금융·어드민도 세션 쪽이 맞다. 페이로드에 담을 게 많아 헤더가
비대해지는 경우도 재검토 대상이다.

**"JWT는 세션보다 확장성이 좋다"는 말의 조건** — 블랙리스트나 서버 저장 Refresh Token을 도입하는 순간
저장소 조회가 돌아온다. 그래도 조회 대상 데이터가 훨씬 적다는 이점은 남는다. 무상태성은 0과 1이 아니라
정도의 문제다.

**검증은 서명만으로 끝내지 않는다.** `exp` 만료 여부, `iss`가 신뢰하는 발급자인지, `aud`가 **내 서비스**를
대상으로 하는지, 그리고 알고리즘 화이트리스트를 함께 본다. 특히 `aud`를 빠뜨리면 다른 서비스용으로 발급된
토큰이 그대로 통과한다.

## 8. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. JWT의 서명은 무엇을 보장하나요?**

A. 무결성과 진정성을 보장합니다. 페이로드가 발급 이후 변조되지 않았고, 키를 가진 발급자가 만든 토큰이라는
것을 확인해 줍니다. 반대로 기밀성은 보장하지 않습니다. 헤더와 페이로드는 Base64URL 인코딩일 뿐이라 토큰을
가진 사람은 누구나 내용을 읽을 수 있습니다. 그래서 비밀번호나 개인정보를 페이로드에 담으면 안 됩니다.

- 꼬리 질문: "내용을 숨기려면?" → 서명 방식(JWS) 대신 암호화 방식(JWE)을 쓰거나, 애초에 식별자만 담고
  나머지는 서버에서 조회한다. 후자가 일반적이다.

**Q. HS256과 RS256 중 무엇을 쓰시겠어요?**

A. 발급자와 검증자가 같은 주체인지로 판단합니다. 한 애플리케이션이 발급도 검증도 하면 HS256이 간단하고
빠릅니다. 마이크로서비스 여러 개가 검증만 하거나 외부 파트너가 검증해야 하면 RS256을 씁니다. HS256은
검증하려면 서명할 수 있는 키를 그대로 줘야 해서, 검증자 중 하나가 뚫리면 그쪽에서 관리자 토큰을 만들어낼
수 있기 때문입니다.

- 꼬리 질문: "알고리즘 혼동 공격을 아세요?" → RS256 서버에 `alg`를 HS256으로 바꾼 토큰을 보내 공개키를
  HMAC 키로 쓰게 만드는 공격. 서버가 검증 알고리즘을 코드에 고정하면 막힌다.

**Q. JWT는 로그아웃을 어떻게 처리하나요?**

A. 근본적으로 서버가 상태를 갖지 않기 때문에 발급된 토큰을 회수할 수 없습니다. 그래서 세 가지를 조합합니다.
첫째, Access Token의 만료를 몇 분 단위로 짧게 잡아 노출 시간을 줄입니다. 둘째, Refresh Token은 서버에
저장해 두고 로그아웃 시 삭제해 더 이상 갱신되지 않게 합니다. 셋째, 즉시 차단이 꼭 필요하면 `jti`를 키로
Redis 블랙리스트를 두되 TTL을 토큰 남은 수명에 맞춥니다.

- 꼬리 질문: "블랙리스트를 쓰면 세션과 같은 것 아닌가요?" → 저장소 실패 시 동작이 반대다. 세션은 조회
  실패가 곧 인증 실패지만 블랙리스트는 조회 실패해도 서비스가 계속된다. 데이터 양도 훨씬 적다.

**Q. Access Token과 Refresh Token을 왜 나누나요?**

A. 유효기간 딜레마 때문입니다. 하나만 쓰면 길게 잡을 때 탈취 피해가 커지고, 짧게 잡으면 사용자가 계속
재로그인해야 합니다. 그래서 자주 전송돼 노출 위험이 큰 Access Token은 짧게, 갱신할 때만 쓰여 노출이 적은
Refresh Token은 길게 가져갑니다. 여기에 Rotation을 붙이면 폐기된 Refresh Token이 다시 등장했을 때
탈취를 탐지해 계보 전체를 끊을 수 있습니다.

- 꼬리 질문: "Rotation에서 정상 사용자와 공격자를 어떻게 구분하나요?" → 구분하지 않는다. 재사용이
  감지되면 양쪽 다 무효화하고 재로그인시킨다. 공격자는 비밀번호를 모르므로 밀려난다.

## 자주 하는 실수

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-----------|
| 페이로드가 암호화된다고 생각 | Base64URL 인코딩일 뿐, 누구나 해독 | 민감정보는 담지 않는다. 필요하면 JWE |
| `jwt.decode()`로 인증 처리 | 서명을 확인하지 않아 위조 토큰이 통과 | 항상 `verify` + 알고리즘 화이트리스트 |
| 토큰 헤더의 `alg`를 신뢰 | `none` 공격, 알고리즘 혼동 공격 | 검증 알고리즘은 서버 코드가 고정 |
| `exp` 없이 발급 | 영구 토큰이 된다 | 만료는 사실상 필수, Access는 분 단위 |
| `aud` 검증 생략 | 다른 서비스용으로 발급된 토큰이 통과 | 내 서비스 대상인지 반드시 확인 |
| Refresh Token을 localStorage에 | XSS 한 번으로 장기 세션 탈취 | HttpOnly + Secure + SameSite 쿠키 |
| JWT라서 무조건 확장성이 좋다 | 블랙리스트 도입 시 조회가 부활 | 무상태성은 정도의 문제, 조합을 설계한다 |
| "서버에서 토큰을 즉시 삭제한다"는 답변 | 서버에는 삭제할 대상이 없다 | 짧은 만료 + RT 폐기 + 필요 시 블랙리스트 |

## 한 줄 정리

JWT는 정보를 표에 적고 서명으로 위조만 막는 방식이라 저장소 조회 없이 검증되지만, 바로 그 이유로
**읽히는 것도 막지 못하고 취소하는 것도 어렵다** — 이 두 대가를 설계로 어떻게 상쇄하느냐가 전부다.
