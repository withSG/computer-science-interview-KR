# 이벤트 루프 (Event Loop)

> 실행 스레드가 하나뿐인 JavaScript가 어떻게 수십 개의 네트워크 요청과 애니메이션을 동시에 다루는가. 이 문서를 읽으면 콜 스택·호스트 API·태스크 큐의 협업 구조를 그림으로 그리고, 화면이 멈추는 현상의 원인을 지목할 수 있다.

## 학습 목표

- [ ] "JavaScript는 싱글 스레드"라는 문장의 정확한 범위를 설명할 수 있다
- [ ] 콜 스택, 호스트 API, 태스크 큐, 이벤트 루프의 역할을 구분할 수 있다
- [ ] 브라우저의 한 사이클(태스크 → 마이크로태스크 → 렌더링)을 순서대로 말할 수 있다
- [ ] Node.js 이벤트 루프의 페이즈 구조와 브라우저와의 차이를 설명할 수 있다
- [ ] 블로킹이 만드는 증상을 알고 청킹·워커로 해결할 수 있다

## 1. 왜 필요한가

브라우저에서 서버 응답을 기다리는 코드를 "동기적으로" 짠다고 상상해보자.

```js
// 동기 요청 (실제로 이렇게 쓰면 안 된다)
const xhr = new XMLHttpRequest();
xhr.open('GET', '/api/items', false); // 세 번째 인자 false = 동기
xhr.send();                            // 여기서 응답이 올 때까지 멈춘다
console.log(xhr.responseText);
```

응답이 300ms 걸리면 그 300ms 동안 **콜 스택이 비지 않는다**. 콜 스택이 비지 않으면 브라우저는 클릭 이벤트도 처리 못 하고, 애니메이션도 못 그리고, 스크롤도 안 된다. 사용자 눈에는 페이지가 죽은 것으로 보인다. 그래서 이 방식은 현재 메인 스레드에서 사용이 권장되지 않는다.

해결의 방향은 둘 중 하나였다.

1. **스레드를 늘린다** — 요청마다 스레드를 하나씩 붙인다. Java 서블릿 모델이 이 방식이다. 대신 스레드 생성 비용, 컨텍스트 스위칭, 공유 자원 동기화(락, 경쟁 상태) 문제가 따라온다.
2. **기다리지 않는다** — "끝나면 이 함수를 불러줘"라고 등록하고 곧장 다음 줄로 넘어간다.

JavaScript는 UI를 다루는 언어였기 때문에 2번을 택했다. DOM을 여러 스레드가 동시에 건드리면 일관성을 지키기가 매우 어렵기 때문이다. **이벤트 루프는 2번 전략을 구현한 장치**다.

> **비유**: 1인 카페. 바리스타(콜 스택)는 한 번에 한 잔만 만든다. 하지만 오븐(호스트 API)에 스콘을 넣어두면 바리스타는 다른 주문을 받고, 오븐이 "땡" 하면(콜백이 큐에 들어가면) 손이 비는 즉시 스콘을 꺼낸다.
>
> **비유의 한계**: 실제 오븐은 저절로 돌아가지만, 브라우저의 "오븐"은 **별도 스레드**다. 즉 병렬 처리는 존재한다. 다만 그 결과를 다루는 JavaScript 코드만 한 줄에 하나씩 실행될 뿐이다.

## 2. "싱글 스레드"의 정확한 의미

가장 흔한 오해가 "JavaScript는 모든 게 하나의 스레드에서 돈다"는 것이다. 정확히는 **JavaScript 코드를 실행하는 스레드가 하나**다. 브라우저 자체는 다중 스레드로 동작한다.

```
┌──────────────────────── 브라우저 프로세스 ─────────────────────────┐
│                                                                    │
│  ┌── 메인(렌더러) 스레드 ────────────┐   ┌── 네트워크 스레드 ───┐  │
│  │  JS 실행 · 스타일 · 레이아웃      │   │  HTTP 요청/응답      │  │
│  │  ┌──────────┐   ┌──────────┐     │   └─────────────────────┘  │
│  │  │Call Stack│   │  Heap    │     │   ┌── 타이머 스레드 ─────┐  │
│  │  └──────────┘   └──────────┘     │   │  setTimeout 계시     │  │
│  └───────────────────────────────────┘   └─────────────────────┘  │
│                                          ┌── 컴포지터 스레드 ───┐  │
│  ┌── Web Worker 스레드(선택) ────────┐   │  합성 · 스크롤       │  │
│  │  DOM 접근 불가, 순수 계산 전용    │   └─────────────────────┘  │
│  └───────────────────────────────────┘                            │
└────────────────────────────────────────────────────────────────────┘
```

`setTimeout`, `fetch`, `addEventListener`는 JavaScript 언어 명세에 없는 **호스트 환경(브라우저/Node.js)의 API**다. 이들은 작업을 다른 스레드에 맡기고 즉시 반환한다. 그래서 "JS는 싱글 스레드인데 어떻게 동시에 여러 요청을 보내냐"는 질문의 답은 **"요청을 보내는 건 JS가 아니라 브라우저"** 다.

## 3. 구성 요소와 전체 흐름

```
        ┌──────────────────────────────────────────────┐
        │            JavaScript 엔진                    │
        │   ┌────────────┐        ┌────────────┐        │
        │   │ Call Stack │        │   Heap     │        │
        │   │  (실행 중) │        │  (객체 저장)│        │
        │   └─────┬──────┘        └────────────┘        │
        └─────────┼────────────────────────────────────┘
                  │ ① 비동기 API 호출
                  ▼
        ┌──────────────────────────────────────────────┐
        │   호스트 환경 (Web API / libuv)               │
        │   타이머 · 네트워크 · 파일 I/O · DOM 이벤트    │
        └─────────┬────────────────────────────────────┘
                  │ ② 완료되면 콜백을 큐에 넣는다
                  ▼
        ┌──────────────────────────────────────────────┐
        │  Microtask Queue  (우선)                      │
        │    Promise 반응, queueMicrotask, MutationObserver│
        ├──────────────────────────────────────────────┤
        │  Task Queue (매크로태스크)                    │
        │    setTimeout, 이벤트 콜백, I/O 완료           │
        └─────────┬────────────────────────────────────┘
                  │ ③ 콜 스택이 비면 꺼내 올린다
                  ▲
             Event Loop  ← 이 순환을 무한 반복
```

각 구성 요소가 하는 일은 정확히 이만큼이다.

| 구성 요소 | 역할 | 오해하기 쉬운 점 |
|----------|------|-----------------|
| 콜 스택 | 실행 컨텍스트를 쌓고 코드를 실행 | 하나뿐이며, 비어야 다음 콜백이 올라온다 |
| 호스트 API | 타이머·네트워크·I/O를 **다른 스레드에서** 처리 | JS 엔진의 일부가 아니다 |
| 태스크 큐 | 완료된 콜백이 대기하는 FIFO | 큐는 여러 개일 수 있다(사용자 입력, 타이머 등) |
| 마이크로태스크 큐 | Promise 반응 전용 큐 | 태스크 큐보다 **항상 먼저** 비워진다 |
| 이벤트 루프 | 스택이 비면 큐에서 하나 꺼내 올리는 반복문 | 스케줄러일 뿐, 코드를 직접 실행하진 않는다 |

### setTimeout 한 줄을 추적하면

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
console.log('C');
// A → C → B
```

```
① console.log('A') 실행                    Stack: [Global, log]  → 'A' 출력
② setTimeout 호출                          Stack: [Global, setTimeout]
   └ 브라우저 타이머 스레드에 콜백 등록 후 즉시 반환
③ console.log('C') 실행                    Stack: [Global, log]  → 'C' 출력
④ 전역 코드 종료                            Stack: [ ]           ← 여기서 비로소
⑤ 0ms가 이미 지났으므로 콜백이 태스크 큐에 있음
⑥ 이벤트 루프가 콜백을 스택에 올림          Stack: [callback]     → 'B' 출력
```

`setTimeout(fn, 0)`의 0은 **"0ms 뒤에 실행"이 아니라 "0ms 뒤에 큐에 넣을 자격을 준다"** 는 뜻이다. 실제 실행은 콜 스택이 비고 마이크로태스크가 전부 처리된 뒤다. 게다가 HTML 명세는 타이머 중첩 깊이가 5를 넘으면 최소 지연을 4ms로 올리도록 정하고 있고, 브라우저는 백그라운드 탭의 타이머를 그보다 훨씬 크게 늦춘다. **`setTimeout`의 지연은 최솟값 보장이지 정확한 시각 보장이 아니다.**

## 4. 브라우저 이벤트 루프의 한 사이클

브라우저에서는 렌더링이 이 순환에 끼어든다. 순서를 정확히 알아야 "왜 DOM을 바꿨는데 화면에 늦게 반영되지"를 설명할 수 있다.

```
┌──────────────────── 한 번의 반복(tick) ────────────────────┐
│                                                            │
│  1. 태스크 큐에서 태스크 하나를 꺼내 끝까지 실행            │
│         (중간에 끊기지 않는다 = run-to-completion)          │
│                          │                                 │
│  2. 마이크로태스크 큐를 전부 비운다                         │
│         (처리 중 새로 추가된 것도 이번에 다 처리)           │
│                          │                                 │
│  3. 렌더링 기회 (필요할 때만, 대략 화면 주사율에 맞춰)      │
│       ├ requestAnimationFrame 콜백 실행                    │
│       ├ 스타일 계산 → 레이아웃 → 페인트 → 합성             │
│       └ 이 단계는 매 tick마다 일어나지 않는다               │
│                                                            │
└────────────────────────────────────────────────────────────┘
                     ↺ 반복
```

여기서 **1번이 끝날 때까지 3번은 절대 일어나지 않는다**. 이것이 블로킹의 정체다. 60Hz 화면이라면 프레임 간격이 약 16.7ms인데, 태스크 하나가 100ms를 잡아먹으면 그 사이 6프레임이 통째로 사라진다.

성능 도구들은 50ms를 넘는 태스크를 **롱 태스크(Long Task)** 로 분류한다. 사용자 입력에 대한 반응이 이 태스크 뒤로 밀리기 때문이다.

## 5. Node.js의 이벤트 루프

Node.js도 이벤트 루프를 쓰지만 구현이 다르다. 브라우저의 "태스크 큐 하나"가 아니라, **libuv가 관리하는 여러 페이즈(phase)** 를 정해진 순서로 순회한다.

```
   ┌───────────────────────────┐
┌─►│   timers                  │  setTimeout / setInterval 콜백
│  ├───────────────────────────┤
│  │   pending callbacks       │  일부 시스템 오퍼레이션 콜백
│  ├───────────────────────────┤
│  │   idle, prepare           │  내부용
│  ├───────────────────────────┤
│  │   poll                    │  I/O 이벤트 수집, 여기서 대기
│  ├───────────────────────────┤
│  │   check                   │  setImmediate 콜백
│  ├───────────────────────────┤
│  │   close callbacks         │  socket.on('close') 등
└──┴───────────────────────────┘

각 콜백 사이마다:  process.nextTick 큐 → Promise 마이크로태스크 큐 순으로 비운다
```

기억할 점 세 가지다.

- **`process.nextTick`이 Promise보다 먼저다.** Node에만 있는 별도 큐이며 우선순위가 가장 높다. 재귀 호출하면 이벤트 루프가 다음 페이즈로 넘어가지 못한다.
- **Node.js 11부터** 타이머·즉시 콜백을 **하나 실행할 때마다** 마이크로태스크를 비운다. 그 이전에는 같은 페이즈의 콜백을 몰아서 처리한 뒤 비웠기 때문에 출력 순서가 브라우저와 달랐다. 지금은 브라우저와 거의 같게 동작한다.
- **네트워크 I/O는 스레드 풀을 쓰지 않는다.** epoll/kqueue 같은 OS의 비동기 알림을 그대로 쓴다. 반면 파일 시스템, DNS 조회, 일부 암호화 연산은 libuv 스레드 풀(기본 4개)에 위임한다. 그래서 무거운 파일 작업을 동시에 많이 던지면 스레드 풀이 병목이 된다.

### 브라우저 vs Node.js

| 구분 | 브라우저 | Node.js | 그래서 무엇이 달라지나 |
|------|---------|---------|---------------------|
| 큐 구조 | 태스크 큐(여러 종류) + 마이크로태스크 큐 | 6개 페이즈 + nextTick + 마이크로태스크 | Node는 `setTimeout`과 `setImmediate` 순서가 상황에 따라 달라질 수 있다 |
| 렌더링 단계 | 사이클에 포함(rAF, 레이아웃, 페인트) | 없음 | Node에는 `requestAnimationFrame`이 없다 |
| 최우선 큐 | 마이크로태스크 큐 | `process.nextTick` 큐 | Node에서는 nextTick 남용이 루프를 굶긴다 |
| I/O 처리 | 브라우저 내부 스레드 | libuv (네트워크는 OS 이벤트, 파일은 스레드 풀) | 파일 I/O 동시성은 스레드 풀 크기에 영향받는다 |
| 블로킹 영향 | UI 정지, 입력 무반응 | 모든 요청 지연, 헬스체크 실패 | 양쪽 다 "하나가 막히면 전부 막힌다" |

**결론**: 구조는 다르지만 규칙은 같다. 콜 스택이 비어야 다음 일이 진행되고, 마이크로태스크는 태스크보다 먼저 처리된다.

## 6. 블로킹이 만드는 실제 증상

동기 코드가 콜 스택을 오래 잡으면 사용자는 이렇게 느낀다.

- 버튼을 눌러도 눌린 표시조차 나지 않는다 (`:active` 스타일도 렌더링 단계에서 그려지므로)
- 스크롤이 끊기거나 아예 안 움직인다
- CSS 애니메이션이 뚝뚝 끊긴다 (합성만으로 처리되는 `transform`/`opacity` 애니메이션은 예외적으로 버틸 수 있다)
- 입력창에 타이핑한 글자가 한참 뒤에 몰려서 나타난다
- 심하면 브라우저가 "페이지가 응답하지 않습니다" 대화상자를 띄운다

### 안티패턴 1 — 큰 배열을 한 번에 처리

```js
// 안티패턴
function renderAll(items) {           // items가 20만 건이라면
  for (const item of items) {
    heavyTransform(item);
  }
  paint();
}
button.addEventListener('click', () => renderAll(bigList));
```

**왜 문제인가**: 이 함수 전체가 **하나의 태스크**다. 태스크는 중간에 끊기지 않으므로(run-to-completion) 끝날 때까지 렌더링도, 다른 클릭 처리도 일어나지 않는다. 사용자는 클릭 후 몇 초간 굳은 화면을 본다.

```js
// 개선 1 — 작업을 쪼개 태스크 사이에 렌더링 기회를 준다
function renderInChunks(items, chunkSize = 500) {
  let index = 0;
  function step() {
    const end = Math.min(index + chunkSize, items.length);
    for (; index < end; index++) heavyTransform(items[index]);
    if (index < items.length) {
      setTimeout(step, 0);   // 다음 태스크로 넘긴다 → 그 사이 렌더링 가능
    } else {
      paint();
    }
  }
  step();
}
```

```js
// 개선 2 — 계산 자체를 워커 스레드로 옮긴다
// main.js
const worker = new Worker('./transform-worker.js');
worker.postMessage(bigList);
worker.onmessage = (e) => paint(e.data);

// transform-worker.js
self.onmessage = (e) => {
  const result = e.data.map(heavyTransform);  // 메인 스레드와 무관하게 실행
  self.postMessage(result);
};
```

청킹은 구현이 간단하지만 총 소요 시간은 오히려 늘어난다. 순수 계산이 크다면 **Web Worker로 옮기는 것이 근본적인 해법**이다. 다만 워커는 DOM에 접근할 수 없고, 주고받는 데이터는 복사(또는 전송)되므로 설계를 나눠야 한다.

### 안티패턴 2 — 바쁜 대기(busy waiting)

```js
// 안티패턴
function sleep(ms) {
  const end = Date.now() + ms;
  while (Date.now() < end) {}   // CPU를 태우며 스택을 점유
}
sleep(1000);
```

**왜 문제인가**: 이 루프가 도는 1초 동안 콜 스택이 비지 않는다. 타이머가 만료돼도, 응답이 도착해도 큐에서 꺼내올 수 없다. 대기하려고 쓴 코드가 오히려 모든 것을 멈춘다.

```js
// 개선 — 스택을 비우고 기다린다
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function run() {
  await sleep(1000);   // 대기 중 콜 스택이 비어 다른 작업이 진행된다
  console.log('1초 뒤');
}
run();
```

### 진단 방법

Chrome DevTools의 **Performance 패널**에서 기록하면 메인 스레드 트랙에 회색 막대(태스크)가 그려지고, 50ms를 넘는 것은 빨간 삼각형으로 표시된다. 그 막대를 클릭하면 어떤 함수가 시간을 잡아먹었는지 콜 트리로 볼 수 있다. "느린 것 같다"는 감이 아니라 **어떤 태스크가 몇 ms를 점유했는지** 숫자로 확인하고 최적화 대상을 정한다.

## 7. 실무에서는

**렌더링 최적화**: 스크롤·리사이즈 이벤트는 초당 수십 번 발생한다. 핸들러에서 레이아웃을 읽고 쓰면 프레임마다 강제 동기 레이아웃이 일어난다. 쓰로틀로 호출 빈도를 줄이고, 실제 DOM 변경은 `requestAnimationFrame` 안에서 하는 것이 정석이다.

**서버**: Node.js 서버에서 JSON 파싱, 이미지 처리, 암호화 같은 CPU 작업을 요청 핸들러에서 그대로 돌리면 그 시간만큼 **모든 요청**이 지연된다. 워커 스레드로 분리하거나 별도 서비스로 빼는 것이 일반적인 대응이다. 스레드 풀로 요청을 격리하는 Spring MVC 모델과 대비되는 지점이며, 면접에서 자주 비교를 요구한다.

**측정 지표**: 사용자 입력에 대한 반응 지연은 이벤트 루프가 얼마나 잘 비어 있는지에 좌우된다. 롱 태스크를 줄이는 작업이 곧 체감 성능 개선이다.

## 8. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. 싱글 스레드인 JavaScript가 어떻게 비동기를 처리하나요?**

A. JavaScript 엔진의 실행 스레드와 콜 스택은 하나지만, 타이머·네트워크·파일 I/O 같은 작업은 언어가 아니라 브라우저나 Node.js 같은 호스트 환경이 별도 스레드에서 처리합니다. 완료되면 콜백을 큐에 넣고, 이벤트 루프가 콜 스택이 빈 것을 확인한 뒤 그 콜백을 스택에 올립니다. 즉 대기는 호스트가 하고 JS는 결과 처리만 합니다.

- 꼬리 질문: "그럼 진짜 병렬 처리는 불가능한가요?" → Web Worker나 Node의 worker_threads로 별도 스레드에서 JS를 돌릴 수 있다. 다만 메모리를 공유하지 않고 메시지로 통신하며, 워커는 DOM에 접근할 수 없다.

**Q. `setTimeout(fn, 0)`은 왜 즉시 실행되지 않나요?**

A. 0ms는 "지금 실행"이 아니라 "0ms 뒤에 태스크 큐에 넣을 수 있다"는 의미입니다. 실제 실행은 현재 동기 코드가 모두 끝나 콜 스택이 비고, 마이크로태스크 큐까지 비워진 다음입니다. 게다가 명세상 타이머가 다섯 단계 넘게 중첩되면 최소 지연이 4ms로 올라가고 백그라운드 탭에서는 더 늦춰지므로, 지연 시간은 최솟값 보장일 뿐 정확한 시각 보장이 아닙니다.

- 꼬리 질문: "그럼 `setTimeout(fn, 0)`은 언제 쓰나요?" → 무거운 작업을 여러 태스크로 쪼개 사이사이에 렌더링과 입력 처리 기회를 주고 싶을 때.

**Q. 브라우저와 Node.js의 이벤트 루프는 어떻게 다른가요?**

A. 브라우저는 태스크 하나를 실행한 뒤 마이크로태스크를 비우고, 필요하면 렌더링 단계를 수행하는 순환입니다. Node.js는 timers, poll, check 등 여러 페이즈를 순회하는 libuv 구조이고 렌더링 단계가 없으며, Promise보다 우선순위가 높은 `process.nextTick` 큐가 따로 있습니다. 다만 Node 11부터는 콜백 하나마다 마이크로태스크를 비워 브라우저와 출력 순서가 거의 같아졌습니다.

- 꼬리 질문: "Node에서 `setTimeout(fn, 0)`과 `setImmediate` 중 뭐가 먼저인가요?" → 메인 모듈에서는 프로세스 성능에 따라 순서가 달라질 수 있고, I/O 콜백 안에서는 poll 다음이 check 페이즈이므로 `setImmediate`가 먼저다.

**Q. 화면이 멈추는 현상을 이벤트 루프로 설명해보세요.**

A. 렌더링은 태스크가 끝난 뒤에만 일어납니다. 동기 코드가 콜 스택을 오래 점유하면 그 태스크가 끝나지 않아 스타일 계산·레이아웃·페인트가 미뤄지고, 클릭이나 입력 콜백도 큐에서 대기만 합니다. 50ms를 넘는 롱 태스크가 반복되면 사용자는 화면이 멈춘 것으로 느낍니다. 해결책은 작업을 여러 태스크로 쪼개거나 Web Worker로 옮기는 것입니다.

## 한 줄 정리

이벤트 루프는 "콜 스택이 비면 큐에서 콜백을 하나 꺼내 올린다"는 단순한 규칙을 무한 반복하는 스케줄러이며, 실제 대기와 I/O는 호스트 환경의 다른 스레드가 담당하기 때문에 단일 실행 스레드로도 비동기가 가능하다.
