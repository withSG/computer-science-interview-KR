# 실행 컨텍스트 (Execution Context)

> JavaScript 엔진이 "이 변수는 어디 있고, this는 무엇이며, 다음에 어디로 돌아가야 하는가"를 관리하는 방식. 이 문서를 읽으면 호이스팅·스코프·클로저가 왜 그렇게 동작하는지 하나의 원리로 설명할 수 있다.

## 학습 목표

- [ ] 실행 컨텍스트의 세 구성 요소(렉시컬 환경, 변수 환경, this 바인딩)를 설명할 수 있다
- [ ] 생성 단계와 실행 단계를 나눠서 코드 실행 순서를 추적할 수 있다
- [ ] 콜 스택에 컨텍스트가 쌓이고 걷히는 과정을 그림으로 그릴 수 있다
- [ ] 스코프 체인이 "호출 위치"가 아니라 "정의 위치"로 결정되는 이유를 설명할 수 있다

## 선행 지식

- 없음 — 이 문서부터 시작해도 된다. 다만 함수 선언과 호출을 코드로 써본 경험은 있어야 한다.

---

## 1. 왜 필요한가

아래 한 줄짜리 코드를 엔진 입장에서 읽어보자.

```js
console.log(userName);
```

엔진은 이 줄을 실행하려고 최소한 세 가지를 알아야 한다.

1. `userName`이라는 이름이 **어느 저장소에** 있는가? 지금 함수 안인가, 바깥인가, 전역인가?
2. 여기서 찾지 못하면 **어디로 올라가서** 더 찾아야 하는가?
3. 만약 `this.userName`이었다면 **`this`는 지금 무엇을 가리키는가**?

이 세 질문에 답하려면 "지금 실행 중인 코드가 놓인 환경 정보"를 어딘가에 모아둬야 한다. 그 묶음이 **실행 컨텍스트(Execution Context)** 다. 즉 실행 컨텍스트는 새로운 기능이 아니라, 엔진이 코드를 실행하기 위해 **반드시 들고 있어야 하는 메타데이터의 집합**이다.

> **비유**: 연극 무대의 세팅표. 배우(코드)가 등장하기 전에 조명·소품·배경(변수, this, 상위 스코프)을 먼저 세팅해두고, 장면이 끝나면 세팅을 걷어낸다.
>
> **비유의 한계**: 무대 세팅은 하나뿐이지만 실행 컨텍스트는 **여러 개가 스택처럼 겹쳐 쌓인다**. 안쪽 장면이 끝나야 바깥 장면이 이어진다는 점까지 포함해야 정확하다.

이 개념 하나를 잡으면 호이스팅, TDZ, 스코프 체인, 클로저가 전부 "실행 컨텍스트의 부작용"으로 설명된다. 그래서 이 문서가 이 폴더의 출발점이다.

---

## 2. 실행 컨텍스트의 종류

| 종류 | 언제 생성되나 | 개수 |
|------|--------------|------|
| 전역 실행 컨텍스트 | 스크립트가 처음 평가될 때 | 실행 환경(realm)당 1개 |
| 함수 실행 컨텍스트 | **함수가 호출될 때마다** | 호출 횟수만큼 |
| 모듈 실행 컨텍스트 | ES Module이 평가될 때 | 모듈당 1개 |
| eval 실행 컨텍스트 | `eval()` 호출 시 | 호출 횟수만큼 |

여기서 가장 중요한 건 **"함수 정의 시점이 아니라 호출 시점"** 이라는 점이다. 함수를 100번 호출하면 실행 컨텍스트도 100번 만들어지고 100번 사라진다. 재귀 함수가 메모리를 많이 먹는 이유가 여기 있다.

실무에서 다루는 건 사실상 전역과 함수 두 종류다. `eval`은 쓰지 않는 것이 원칙이므로 이후 설명에서는 제외한다.

## 3. 실행 컨텍스트의 구성 요소

```
┌───────────────────────────────────────────────────┐
│              Execution Context                    │
│                                                   │
│  ┌─────────────────────────────────────────────┐  │
│  │  LexicalEnvironment (렉시컬 환경)            │  │
│  │  ┌───────────────────────────────────────┐  │  │
│  │  │ Environment Record (환경 레코드)       │  │  │
│  │  │   식별자 ─ 값 매핑 (let/const, 매개변수)│  │  │
│  │  └───────────────────────────────────────┘  │  │
│  │  ┌───────────────────────────────────────┐  │  │
│  │  │ Outer Reference (외부 렉시컬 환경 참조) │  │  │
│  │  │   → 상위 스코프를 가리키는 화살표       │  │  │
│  │  └───────────────────────────────────────┘  │  │
│  └─────────────────────────────────────────────┘  │
│                                                   │
│  ┌─────────────────────────────────────────────┐  │
│  │  VariableEnvironment (변수 환경)             │  │
│  │    var 선언, 함수 선언문 보관                │  │
│  └─────────────────────────────────────────────┘  │
│                                                   │
│  ┌─────────────────────────────────────────────┐  │
│  │  this 바인딩                                 │  │
│  └─────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────┘
```

### 3-1. 렉시컬 환경 = 환경 레코드 + 외부 참조

**환경 레코드(Environment Record)** 는 "이 스코프에 어떤 이름이 있고 그 값은 무엇인가"를 적어둔 장부다. 변수명이 키, 값이 값인 표라고 생각하면 된다.

**외부 렉시컬 환경 참조(Outer Reference)** 는 "여기서 못 찾으면 저기로 가서 찾아라"를 가리키는 포인터다. 이 포인터를 계속 따라가면 만들어지는 연결 리스트가 바로 **스코프 체인(Scope Chain)** 이다. 스코프 체인은 별도 자료구조가 아니라 렉시컬 환경들이 외부 참조로 이어진 결과일 뿐이다.

```js
const global = 'G';

function outer() {
  const o = 'O';
  function inner() {
    const i = 'I';
    console.log(i, o, global); // I O G
  }
  inner();
}
outer();
```

```
inner의 환경 레코드   { i: 'I' }
        │ outer 참조
        ▼
outer의 환경 레코드   { o: 'O', inner: fn }
        │ outer 참조
        ▼
전역 환경 레코드      { global: 'G', outer: fn }
        │ outer 참조
        ▼
       null   ← 여기까지 없으면 ReferenceError
```

탐색은 **항상 안에서 밖으로 한 방향**이다. 바깥에서 안쪽 변수는 볼 수 없다. 그래서 `inner` 밖에서 `i`를 참조하면 `ReferenceError`가 난다.

### 3-2. 변수 환경은 왜 따로 있나

"렉시컬 환경 하나면 될 텐데 왜 변수 환경이 또 있지?"가 핵심 질문이다. 답은 **`var`와 `let`의 스코프 단위가 다르기 때문**이다.

블록 `{ }`에 진입하면 엔진은 **새 렉시컬 환경을 만들어 갈아 끼운다**. 하지만 변수 환경은 함수 진입 시 만든 것을 그대로 유지한다.

```js
function f() {
  var v = 1;
  let l = 1;
  {
    var v = 2;  // 변수 환경(함수 단위)에 그대로 덮어씀
    let l = 2;  // 블록용 새 렉시컬 환경에 별도 등록
    console.log(v, l); // 2 2
  }
  console.log(v, l);   // 2 1  ← v만 블록을 뚫고 나왔다
}
f();
```

```
함수 진입 시            블록 진입 시
LexicalEnv ──┐          LexicalEnv ──→ [블록 레코드 { l: 2 }] ──outer──┐
             ├→ [함수 레코드]                                          │
VariableEnv ─┘          VariableEnv ──→ [함수 레코드 { v: 2, l: 1 }] ◄─┘
```

`var`가 블록을 무시하는 현상은 문법적 예외가 아니라 **저장 위치가 다르기 때문**이다. 이 구조를 이해하면 `var`를 쓰지 말아야 할 이유가 규칙 암기가 아니라 원리로 남는다.

함수에 처음 진입하는 시점에는 렉시컬 환경과 변수 환경이 **같은 환경 레코드를 가리킨다**. 블록이 등장할 때 비로소 렉시컬 환경만 갈라진다.

### 3-3. this 바인딩

`this`도 실행 컨텍스트가 들고 있는 정보다. 일반 함수는 **호출 방식**에 따라 컨텍스트 생성 시점에 `this`가 정해진다. 화살표 함수는 자신의 `this`를 갖지 않고, 외부 참조를 따라 올라가 바깥 환경의 `this`를 찾는다. 즉 화살표 함수의 `this`는 스코프 체인 탐색과 같은 방식으로 해결된다.

```js
const obj = {
  label: 'obj',
  normal() {
    const inner = () => this.label;  // 화살표는 normal의 this를 그대로 쓴다
    return [this.label, inner()];
  },
};

console.log(obj.normal());        // ['obj', 'obj']

const detached = obj.normal;
// detached();  ← 호출 방식이 바뀌면 this도 바뀐다 (strict 모드에서 undefined → TypeError)
```

객체 리터럴 자체는 스코프를 만들지 않는다. 그래서 `obj`의 프로퍼티로 직접 화살표 함수를 넣으면 `this`는 `obj`가 아니라 **객체 리터럴을 감싼 바깥 환경의 `this`** 가 된다. 메서드 자리에 화살표 함수를 쓰면 안 되는 이유다.

`this`의 4가지 바인딩 규칙과 우선순위는 별도 주제라 여기서는 "실행 컨텍스트가 보관하는 정보 중 하나"라는 사실까지만 짚는다. 자세한 내용은 [qna-javascript.md](./qna-javascript.md)의 this 문항을 보자.

## 4. 생성 단계와 실행 단계

실행 컨텍스트는 만들어지자마자 코드를 실행하지 않는다. **두 단계**를 거친다.

| 단계 | 하는 일 | 결과 |
|------|--------|------|
| 생성 단계(Creation Phase) | 스코프 안의 선언을 훑어 환경 레코드에 이름 등록, 외부 참조 연결, this 결정 | 아직 값 할당은 없음 |
| 실행 단계(Execution Phase) | 코드를 한 줄씩 실행하며 값 할당·연산·함수 호출 | 실제 값이 채워짐 |

이 분리가 **호이스팅의 정체**다. 코드가 위로 이동하는 게 아니라, 실행 전에 이름이 먼저 등록될 뿐이다.

```js
function demo() {
  console.log(a); // undefined  ← 이름은 있고 값은 아직
  console.log(fn); // [Function: fn]
  // console.log(b); // ReferenceError (TDZ)

  var a = 1;
  let b = 2;
  function fn() {}

  console.log(a, b); // 1 2
}
demo();
```

생성 단계가 끝난 직후 `demo`의 환경은 이렇게 생겼다.

```
생성 단계 종료 시점
┌──────────────────────────────────────────┐
│ VariableEnvironment                      │
│   a  : undefined      ← var는 초기화까지  │
│   fn : <function>     ← 함수 선언문은 통째로│
├──────────────────────────────────────────┤
│ LexicalEnvironment                       │
│   b  : <uninitialized> ← 접근하면 TDZ 에러 │
└──────────────────────────────────────────┘

실행 단계 진행
  a = 1  → a: 1
  b = 2  → b: 2 (여기서 초기화, TDZ 종료)
```

`var`는 등록과 동시에 `undefined`로 초기화되고, `let`/`const`는 등록만 되고 초기화되지 않는다. 이 **초기화 시점의 차이**가 TDZ의 전부다. 자세한 내용은 [02-hoisting-tdz.md](./02-hoisting-tdz.md)에서 다룬다.

## 5. 콜 스택 — 컨텍스트가 쌓이고 걷히는 과정

실행 컨텍스트는 **콜 스택(Call Stack)** 이라는 LIFO 구조에 쌓인다. 가장 위에 있는 컨텍스트가 "현재 실행 중인 컨텍스트"다.

```js
function third()  { console.log('3'); }
function second() { third(); }
function first()  { second(); }
first();
```

```
 시간 →
 ①            ②            ③            ④            ⑤            ⑥
                                        ┌────────┐
                            ┌────────┐  │ third  │
              ┌────────┐    │ second │  │ second │   ┌────────┐
┌────────┐    │ first  │    │ first  │  │ first  │   │ first  │   ┌────────┐
│ Global │    │ Global │    │ Global │  │ Global │   │ Global │   │ Global │
└────────┘    └────────┘    └────────┘  └────────┘   └────────┘   └────────┘
 스크립트      first 호출    second 호출  third 호출   third 반환   second 반환
 평가
```

스택이 걷히는 순서가 곧 함수가 반환되는 순서다. 개발자 도구의 **Call Stack 패널**이 보여주는 목록, 그리고 에러의 스택 트레이스가 정확히 이 스택의 스냅샷이다.

```js
function boom() { throw new Error('터짐'); }
function wrap() { boom(); }
wrap();
// Error: 터짐
//     at boom (...)   ← 스택 맨 위
//     at wrap (...)
//     at ... (전역)    ← 스택 맨 아래
```

### 스택 오버플로

콜 스택 크기에는 한계가 있다. 종료 조건 없는 재귀는 컨텍스트를 무한히 쌓아 스택을 넘긴다.

```js
function infinite() { return infinite(); }
infinite(); // RangeError: Maximum call stack size exceeded
```

`return infinite();`처럼 꼬리 호출 형태로 써도 소용없다. **V8은 꼬리 호출 최적화(TCO)를 구현하지 않았기 때문**에 스택 프레임이 그대로 쌓인다. 깊은 재귀가 필요하면 반복문이나 명시적 스택으로 바꿔야 한다.

## 6. 스코프 체인은 언제 결정되는가

가장 헷갈리는 지점이다. 실행 컨텍스트는 **호출할 때** 만들어지지만, 그 컨텍스트의 **외부 참조는 함수가 정의된 위치**로 결정된다. 함수 객체는 생성될 때 자신이 정의된 렉시컬 환경을 `[[Environment]]` 내부 슬롯에 저장해두고, 나중에 호출되면 그 값을 외부 참조로 꽂는다.

```js
const x = 'global';

function printX() {
  console.log(x);     // printX가 '정의된' 곳 기준으로 찾는다
}

function caller() {
  const x = 'caller';
  printX();           // 'global'  ← 'caller'가 아니다
}

caller();
```

이것이 **렉시컬 스코프(정적 스코프)** 다. 호출 위치가 아니라 소스 코드에 적힌 위치로 상위 스코프가 결정되므로, 코드를 보는 것만으로 변수 탐색 경로를 예측할 수 있다.

그리고 함수가 `[[Environment]]`를 붙들고 있다는 사실 때문에, 외부 함수가 끝나 콜 스택에서 사라져도 그 환경 레코드는 메모리에 남을 수 있다. 이게 [클로저](./03-closure.md)다.

## 7. 실무에서는

**디버깅**: Chrome DevTools의 Sources 패널에서 브레이크포인트를 걸면 오른쪽에 `Call Stack`과 `Scope`가 뜬다. `Scope`의 `Local` / `Closure` / `Global` 항목이 곧 렉시컬 환경의 체인이다. "변수가 왜 undefined지?"를 추측 대신 눈으로 확인할 수 있다.

**성능**: 함수 호출은 공짜가 아니다. 컨텍스트 생성·소멸 비용이 있다. 다만 최신 엔진은 인라이닝으로 대부분 상쇄하므로, **호출 횟수를 줄이려고 함수를 합치는 최적화는 대개 잘못된 우선순위**다. 병목은 보통 DOM 조작이나 네트워크에 있다.

**프레임워크**: React 함수 컴포넌트도 결국 매 렌더마다 호출되는 평범한 함수다. 렌더 한 번 = 실행 컨텍스트 한 번. 그 안에서 만들어진 이벤트 핸들러는 그 렌더의 렉시컬 환경을 붙들고 있고, 이 사실이 stale closure 버그의 근본 원인이다.

**서버**: Node.js도 같은 콜 스택 하나로 동작한다. 요청 처리 중 무거운 동기 연산을 돌리면 그 스택이 비지 않아 **다른 모든 요청이 멈춘다**. 스레드 풀로 요청마다 스택을 분리하는 Spring MVC와 대조되는 지점이다.

## 8. 안티패턴과 개선

### 안티패턴 1 — 선언 위치를 흩뿌린 var

```js
// 안티패턴
function calc(items) {
  for (var i = 0; i < items.length; i++) {
    var total = (total || 0) + items[i];
  }
  return total;
}
```

**왜 문제인가**: `total`과 `i`는 생성 단계에서 이미 함수 최상단에 `undefined`로 등록된다. 코드를 읽는 사람은 `total`이 루프 안에서만 사는 변수라고 착각하지만 실제로는 함수 전체에서 살아 있다. `total || 0` 같은 방어 코드도 이 착각을 감추려는 흔적이다.

```js
// 개선
function calc(items) {
  let total = 0;
  for (let i = 0; i < items.length; i++) {
    total += items[i];
  }
  return total;
}
```

`let`은 블록 렉시컬 환경에 등록되므로 **선언 위치와 유효 범위가 일치**한다. 코드가 곧 스코프 설명서가 된다.

### 안티패턴 2 — 선언 없는 할당으로 전역 오염

```js
// 안티패턴 (non-strict 모드)
function setup() {
  config = { retry: 3 };   // 선언 키워드 없음
}
setup();
console.log(config);       // 전역에서 접근된다
```

**왜 문제인가**: 어느 스코프에서도 `config`를 찾지 못하면 엔진은 전역 객체에 프로퍼티를 만들어버린다. 함수 지역 변수를 의도했는데 전역이 오염되고, 이름이 겹치면 다른 모듈의 값을 조용히 덮어쓴다. 게다가 전역 객체가 살아 있는 한 GC 대상이 되지 않아 메모리 누수로 이어진다.

```js
// 개선
'use strict';              // 모듈은 자동 strict
function setup() {
  const config = { retry: 3 };
  return config;
}
```

strict 모드에서는 같은 코드가 `ReferenceError`로 즉시 실패한다. ES Module은 기본이 strict이므로, 모듈 시스템을 쓰는 것만으로도 이 함정을 피할 수 있다.

## 9. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. 실행 컨텍스트란 무엇이고 어떤 요소로 구성되나요?**

A. 코드를 실행하는 데 필요한 환경 정보의 묶음입니다. 식별자 장부인 환경 레코드와 상위 스코프를 가리키는 외부 참조로 이뤄진 렉시컬 환경, `var`와 함수 선언문을 담는 변수 환경, 그리고 this 바인딩으로 구성됩니다. 전역 컨텍스트는 스크립트 평가 시, 함수 컨텍스트는 함수 호출 시마다 생성되어 콜 스택에 LIFO로 쌓입니다.

- 꼬리 질문: "렉시컬 환경과 변수 환경을 왜 나눴나요?" → `var`는 함수 스코프, `let`/`const`는 블록 스코프이기 때문. 블록 진입 시 렉시컬 환경만 새로 갈아 끼우고 변수 환경은 유지하므로 `var`가 블록을 뚫고 나온다고 설명한다.

**Q. 호이스팅은 왜 발생하나요?**

A. 실행 컨텍스트가 생성 단계와 실행 단계로 나뉘기 때문입니다. 생성 단계에서 스코프 내 선언을 먼저 환경 레코드에 등록하므로, 실행 단계에서 선언문보다 위에 있는 코드도 그 이름을 찾을 수 있습니다. 코드가 물리적으로 위로 이동하는 것이 아닙니다.

- 꼬리 질문: "그럼 `let`은 왜 에러가 나나요?" → 등록은 되지만 초기화가 선언문 도달 시점으로 미뤄지기 때문. 그 사이 구간이 TDZ.

**Q. 스코프 체인은 호출 시점에 결정되나요, 정의 시점에 결정되나요?**

A. 정의 시점입니다. 함수 객체는 생성될 때 자신이 정의된 렉시컬 환경을 `[[Environment]]`에 저장하고, 호출되어 컨텍스트가 만들어질 때 그 값을 외부 참조로 사용합니다. 그래서 전역에 정의된 함수를 다른 함수 안에서 호출해도 상위 스코프는 여전히 전역입니다.

- 꼬리 질문: "`this`도 그런가요?" → 아니다. 일반 함수의 `this`는 호출 방식에 따라 동적으로 결정된다. 화살표 함수만 예외적으로 스코프 체인을 따라 렉시컬하게 결정된다.

**Q. 콜 스택이 넘치면 어떤 에러가 나고, 왜 나나요?**

A. `RangeError: Maximum call stack size exceeded`가 발생합니다. 함수 호출마다 실행 컨텍스트가 스택에 쌓이는데 종료 조건 없는 재귀는 이를 무한히 쌓기 때문입니다. V8은 꼬리 호출 최적화를 구현하지 않아 꼬리 재귀로 바꿔도 해결되지 않으므로, 반복문이나 명시적 스택 구조로 변환해야 합니다.

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-----------|
| "실행 컨텍스트는 함수 정의할 때 생긴다" | 정의는 함수 객체를 만들 뿐 | **호출할 때마다** 새로 생성된다 |
| "호이스팅은 코드가 위로 올라가는 것" | 소스는 그대로다 | 생성 단계에서 **선언이 먼저 등록**될 뿐 |

| "블록도 실행 컨텍스트를 만든다" | 컨텍스트는 함수/전역/모듈 단위 | 블록은 **렉시컬 환경만** 새로 만든다 |

## 한 줄 정리

실행 컨텍스트는 "식별자 장부(환경 레코드) + 상위 스코프 화살표(외부 참조) + this"를 담아 콜 스택에 쌓이는 실행 환경이며, 생성 단계에서 이름을 먼저 등록하고 실행 단계에서 값을 채우는 두 박자 동작이 호이스팅·TDZ·클로저의 공통 뿌리다.
