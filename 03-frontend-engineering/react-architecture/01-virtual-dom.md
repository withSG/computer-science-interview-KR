# 가상 DOM (Virtual DOM)

> Virtual DOM이 실제로 해결한 문제가 "속도"가 아니라 "명령형 DOM 조작"이었다는 것을 설명할 수 있게 된다.

## 학습 목표

- [ ] 직접 DOM 조작 방식이 왜 규모가 커질수록 무너지는지 설명할 수 있다
- [ ] Virtual DOM이 하는 일과 하지 않는 일을 구분할 수 있다
- [ ] "Virtual DOM은 빠르다"가 왜 부정확한 문장인지 반박할 수 있다
- [ ] Svelte, Solid처럼 Virtual DOM 없이 같은 문제를 푸는 방식과 비교할 수 있다

## 선행 지식

- DOM이 무엇인지, `document.querySelector` 수준의 조작 경험
- [브라우저 동작 원리](../browser-fundamentals/README.md) - 렌더링 파이프라인을 알면 이해가 쉽다

## 1. 왜 필요한가

### 명령형 DOM 조작의 진짜 문제

할 일 목록에서 "완료된 항목 개수"를 표시하는 기능을 순수 DOM API로 만들어 보자.

```js
// 상태는 여기에, 화면은 저기에
let todos = [];

function addTodo(text) {
  todos.push({ id: Date.now(), text, done: false });

  // 화면 갱신 1: 목록에 <li> 추가
  const li = document.createElement('li');
  li.textContent = text;
  document.querySelector('#list').appendChild(li);

  // 화면 갱신 2: 개수 표시 갱신
  document.querySelector('#count').textContent =
    `${todos.filter(t => t.done).length} / ${todos.length}`;

  // 화면 갱신 3: 목록이 비어있을 때 안내 문구 숨기기
  document.querySelector('#empty').style.display = 'none';
}
```

기능을 하나 추가할 때마다 "그 변경이 화면의 어느 부분에 영향을 주는지"를 개발자가 전부 기억하고 코드로 적어야 한다. 여기에 `toggleTodo`, `removeTodo`, `filterTodos`가 붙으면 각 함수마다 세 곳의 갱신 코드를 다시 써야 한다. 함수 5개 × 갱신 지점 4개 = 20개의 조합을 사람이 관리하는 셈이다.

이 방식이 무너지는 지점은 성능이 아니다. **하나를 빠뜨렸을 때 상태와 화면이 어긋난다**는 것이다. `todos` 배열에는 항목이 3개인데 화면에는 2개만 보이는 상황, 개수는 갱신됐는데 안내 문구가 그대로 남아 있는 상황. 이 버그는 재현이 어렵고 원인 추적이 힘들다.

### 그래서 나온 발상

"갱신 코드를 일일이 쓰지 말고, **현재 상태로 화면 전체를 다시 그리면** 어떨까?"

```js
function render() {
  document.querySelector('#app').innerHTML = buildHtml(todos);
}
```

상태가 바뀌면 `render()` 한 번만 호출하면 되니 어긋날 일이 없다. 하지만 이 방식에는 치명적인 문제가 있다.

- 입력 중이던 `<input>`의 포커스와 커서 위치가 날아간다
- 스크롤 위치가 초기화된다
- 재생 중이던 `<video>`가 처음부터 다시 시작된다
- 실제로 바뀐 건 글자 하나인데 DOM 노드 수백 개를 파괴하고 다시 만든다

Virtual DOM은 이 두 방식의 절충안이다. **개발자는 "전체를 다시 그린다"고 쓰되, 실제 DOM에는 바뀐 부분만 반영한다.**

## 2. Virtual DOM이란 무엇인가

### 정의

Virtual DOM은 **UI의 모양을 기술한 순수 JavaScript 객체 트리**다. 실제 DOM 노드가 아니라, "이런 모양이어야 한다"는 설계도에 가깝다.

JSX는 문법 설탕일 뿐이고, 컴파일되면 객체를 만드는 함수 호출이 된다.

```jsx
// 우리가 쓰는 코드
const element = <li className="item">우유 사기</li>;

// 변환 결과 (개념적으로)
const element = createElement('li', { className: 'item' }, '우유 사기');

// 그 함수가 반환하는 값 (단순화)
{
  type: 'li',
  key: null,
  props: {
    className: 'item',
    children: '우유 사기'
  }
}
```

핵심은 `element`가 **아무것도 하지 않는 값**이라는 점이다. 화면에 아무 영향이 없고, DOM API를 부르지도 않는다. 그냥 객체다. 그래서 만들고 버리는 비용이 실제 DOM 노드보다 훨씬 싸다.

실제 DOM 노드 하나는 스타일 계산, 레이아웃 정보, 이벤트 타깃 등 브라우저가 관리하는 방대한 속성을 함께 들고 있다. 반면 위 객체는 필드 세 개짜리 평범한 JS 객체다. 이 비대칭이 Virtual DOM 전략이 성립하는 근거다.

### 트리는 중첩된 객체다

자식이 있으면 `props.children`에 또 다른 엘리먼트 객체가 들어간다. 그래서 "트리"다.

```jsx
const tree = (
  <ul className="todo-list">
    <li>우유 사기</li>
    <li>설거지</li>
  </ul>
);
```

```
{
  type: 'ul',
  props: {
    className: 'todo-list',
    children: [
      { type: 'li', props: { children: '우유 사기' } },
      { type: 'li', props: { children: '설거지' } }
    ]
  }
}
```

`type`이 문자열이면 호스트 엘리먼트(브라우저의 `<ul>`, `<li>`)이고, 함수나 클래스면 우리가 만든 컴포넌트다. 컴포넌트 타입인 엘리먼트를 만나면 React가 그것을 실행해(함수 컴포넌트면 함수를 호출하고, 클래스 컴포넌트면 인스턴스를 만들어 `render`를 호출한다) 다시 엘리먼트 트리를 얻고, 문자열 타입만 남을 때까지 이 과정을 반복한다.

여기서 자주 헷갈리는 세 단어를 구분해 두자.

| 용어 | 정체 | 예 |
|------|------|-----|
| 컴포넌트 (Component) | 엘리먼트를 반환하는 함수 그 자체 | `function TodoItem() { ... }` |
| 엘리먼트 (Element) | "이걸 이렇게 그려라"를 기술한 불변 객체 | `<TodoItem text="우유" />`의 결과 |
| 인스턴스 | 화면에 실제로 존재하는 그것 (React 내부의 fiber, 실제 DOM 노드) | 마운트된 뒤에 생긴다 |

엘리먼트는 **한 번 만들어지면 바뀌지 않는다.** 화면을 갱신한다는 것은 기존 엘리먼트를 수정하는 게 아니라, 새 엘리먼트 트리를 만들어 이전 것과 비교하는 것이다.

### 비유: 리모델링 설계도

벽을 부수기 전에 도면 두 장(현재 도면, 새 도면)을 겹쳐 놓고 "여기 벽만 옮기면 되네"를 먼저 계산하는 것과 같다. 도면 위에서 지우고 그리는 건 싸지만, 실제 벽을 부수는 건 비싸다.

**비유의 한계**: 설계도 비교는 사람이 한 번만 하지만, React는 상태가 바뀔 때마다 매번 도면을 새로 그리고 다시 비교한다. 그 반복 비용이 공짜가 아니라는 점이 뒤에 나올 "빠르다는 오해"의 핵심이다.

## 3. 상태 변경부터 화면 반영까지

```
 setState 호출
      │
      ▼
┌───────────────────────────────────────────────┐
│ 1. 렌더 (Render)                              │
│    컴포넌트 함수를 다시 호출해                 │
│    새 Virtual DOM 트리를 만든다                │
│    → 실제 DOM은 아직 그대로                    │
└───────────────────────────────────────────────┘
      │
      ▼
┌───────────────────────────────────────────────┐
│ 2. 비교 (Diffing) + 재조정 (Reconciliation)   │
│    이전 트리 ↔ 새 트리를 맞대어 보고           │
│    "무엇을 바꿔야 하는지" 목록을 만든다        │
│    → 실제 DOM은 아직 그대로                    │
└───────────────────────────────────────────────┘
      │
      ▼
┌───────────────────────────────────────────────┐
│ 3. 커밋 (Commit)                              │
│    계산된 변경 목록만 실제 DOM에 일괄 적용     │
│    → 여기서 처음으로 실제 DOM이 바뀐다         │
└───────────────────────────────────────────────┘
      │
      ▼
 브라우저가 레이아웃·페인트 수행
```

여기서 반드시 구분해야 할 두 단어가 있다.

| 용어 | 의미 | 비용 |
|------|------|------|
| 리렌더링 (re-render) | 컴포넌트 함수가 다시 호출되어 새 Virtual DOM 객체를 만드는 것 | 상대적으로 저렴 |
| DOM 업데이트 | 실제 DOM 노드의 속성·구조가 바뀌는 것 | 비쌈 (레이아웃·페인트 유발) |

**리렌더링이 일어났다고 DOM이 바뀌는 게 아니다.** 비교 결과 차이가 없으면 3단계에서 아무 일도 하지 않는다. 이 구분을 못 하면 "리렌더링 = 성능 문제"라는 잘못된 공식에 갇힌다.

### 배치 업데이트

한 이벤트 핸들러 안에서 상태를 여러 번 바꿔도 렌더는 한 번만 일어난다.

```jsx
function handleClick() {
  setCount(c => c + 1);   // 여기서 렌더링 X
  setName('React');       // 여기서 렌더링 X
  setOpen(true);          // 여기서 렌더링 X
  // 핸들러가 끝난 뒤 → 렌더 1회, DOM 커밋 1회
}
```

직접 DOM을 조작했다면 세 번의 DOM 쓰기가 발생하고, 그 사이사이에 브라우저가 레이아웃을 다시 계산했을 수도 있다. Virtual DOM 계층이 중간에 있으면 이런 묶음 처리가 자연스럽게 가능해진다.

React 17까지는 이 묶음 처리가 React 이벤트 핸들러 안에서만 적용됐다. `setTimeout` 콜백이나 `fetch` 응답 처리 안에서 상태를 세 번 바꾸면 렌더도 세 번 일어났다. React 18에서 `createRoot`로 마운트하면 이런 위치에서도 자동으로 묶인다(자동 배칭).

## 4. "Virtual DOM은 빠르다"는 오해

### 왜 부정확한가

숫자 하나만 바꾸는 상황을 보자.

```js
// 직접 조작: DOM 쓰기 1회. 끝.
document.getElementById('count').textContent = '42';
```

```jsx
// React: 컴포넌트 함수 호출 → 새 VDOM 트리 생성 → 이전 트리와 비교
//        → 변경 목록 계산 → DOM 쓰기 1회
setCount(42);
```

최종적으로 발생하는 DOM 쓰기는 똑같이 1회다. 그런데 React는 그 앞에 **트리 생성과 비교라는 추가 작업**을 얹었다. 순수한 실행 시간만 보면 직접 조작이 빠르다. 당연하다. 일을 덜 하니까.

Virtual DOM은 DOM 조작을 **빠르게** 만드는 기술이 아니라, **필요 이상의 DOM 조작을 막아 주는** 기술이다. 상한선을 낮춰 주는 것이지 하한선을 낮추는 게 아니다.

```
직접 조작 (수동 최적화)
  ├─ 최선의 경우: React보다 빠름 (사람이 정확히 최소 변경만 함)
  └─ 최악의 경우: 매우 느림 (실수로 전체를 다시 그림, 어긋난 상태)

Virtual DOM
  ├─ 최선의 경우: 직접 조작보다 약간 느림 (diffing 오버헤드)
  └─ 최악의 경우: 여전히 괜찮음 (diffing이 최소 변경을 보장)
        ↑
   "성능의 바닥을 보장한다"가 Virtual DOM의 실제 효용
```

### 정확한 표현

- 틀린 표현: "Virtual DOM은 DOM보다 빠르다"
- 맞는 표현: "Virtual DOM은 **손으로 최적화하지 않아도** 납득할 만한 성능이 나오게 해준다"

면접에서는 이렇게 답하면 된다. "Virtual DOM의 이점은 절대 속도가 아니라, 선언적으로 코드를 쓰면서도 DOM 조작 횟수가 폭발하지 않도록 보장해 주는 것입니다."

### Virtual DOM이 하지 않는 일

"React를 쓰니 성능은 알아서 되겠지"라는 기대가 어디서 깨지는지 명확히 해 두자.

**불필요한 리렌더링을 막아 주지 않는다.** 부모 컴포넌트가 리렌더링되면 자식은 props가 그대로여도 함께 다시 실행된다. Virtual DOM은 그 결과를 비교해서 DOM 변경을 막아 줄 뿐, 비교 작업 자체가 일어나는 것은 막지 못한다. 자식 트리가 크면 비교 비용이 그대로 든다.

**렌더 함수 안의 느린 코드를 빠르게 해 주지 않는다.** 컴포넌트 안에서 1만 건을 정렬하고 있다면 그건 Virtual DOM과 무관한 순수한 JS 실행 시간이다.

**브라우저의 레이아웃·페인트 비용을 없애 주지 않는다.** DOM을 최소한으로만 바꿔도, 그 변경이 레이아웃을 유발하는 속성(`width`, `top` 등)이면 브라우저는 다시 계산해야 한다. 노드가 수천 개면 그 재계산이 병목이다.

**노드 개수를 줄여 주지 않는다.** 1만 행짜리 테이블을 그리라고 하면 그대로 1만 개의 DOM 노드를 만든다. 이 문제의 답은 Virtual DOM이 아니라 가상 스크롤이다.

```
Virtual DOM이 담당하는 구간
             │
  상태 변경 ─┼─► [렌더] ─► [비교] ─► [커밋] ─► 레이아웃 ─► 페인트
             │      ↑         ↑        ↑          ↑          ↑
             │   내 코드   VDOM 담당  VDOM 담당  브라우저   브라우저
             │   (느리면
             │    그대로 느림)
```

## 5. 진짜 가치는 선언적 UI

### 명령형 vs 선언적

| 구분 | 명령형 (Imperative) | 선언적 (Declarative) |
|------|-------------------|---------------------|
| 개발자가 쓰는 것 | 화면을 **어떻게** 바꿀지 절차 | 화면이 **무엇**이어야 하는지 결과 |
| 상태-화면 동기화 | 개발자 책임 | 프레임워크 책임 |
| 상태 종류가 늘어날 때 | 조합이 곱셈으로 증가 | 조건 분기 한 줄 추가 |
| 예시 | `el.style.display = 'none'` | `{isOpen && <Modal />}` |

**결론**: 상태의 가짓수가 적고 변화가 단순하면 명령형이 더 빠르고 간단하다. 상태 조합이 늘어나는 순간 선언적 방식이 유지보수 비용을 압도적으로 줄인다.

### 크로스 플랫폼

Virtual DOM 트리는 "무엇을 그릴지"만 담고 "어떻게 그릴지"는 담지 않는다. 그래서 트리를 해석하는 렌더러를 바꿔 끼울 수 있다.

```
       컴포넌트 코드 (공통)
              │
      Virtual DOM 트리 (공통)
              │
      ┌───────┴───────┐
      ▼               ▼
   react-dom     react-native
      │               │
   HTML 요소      네이티브 View
```

React Native가 같은 React 문법으로 동작하는 이유가 여기 있다. 재조정 로직은 그대로 두고 커밋 단계의 렌더러만 교체한 것이다.

## 6. Virtual DOM 없는 대안

Virtual DOM은 "선언적 UI"를 구현하는 **한 가지 방법**일 뿐, 유일한 방법이 아니다.

### Svelte: 컴파일 타임에 갱신 코드를 생성

Svelte는 빌드 시점에 컴포넌트를 분석해, "이 변수가 바뀌면 이 DOM 노드의 이 속성을 갱신하라"는 코드를 미리 만들어 둔다. 런타임에 트리를 비교할 필요가 없다.

```
React:  런타임에 [새 트리 생성 → 비교 → 변경점 찾기] 매번 수행
Svelte: 컴파일 타임에 [어디를 갱신할지] 이미 확정, 런타임엔 그 코드만 실행
```

대신 동적으로 컴포넌트 구조를 만들어 내는 유연함에는 제약이 생기고, 런타임 라이브러리 대신 컴포넌트마다 생성된 코드가 번들에 들어간다.

### Solid: 세밀한 반응성

Solid는 컴포넌트 함수를 **최초 한 번만** 실행한다. 이후에는 반응형 값(시그널)을 실제로 사용하는 지점만 추적해 두었다가, 값이 바뀌면 그 지점만 직접 갱신한다. 컴포넌트 전체를 다시 실행하지 않으므로 비교할 트리 자체가 없다.

| 구분 | React (VDOM) | Svelte (컴파일) | Solid (시그널) |
|------|-------------|----------------|---------------|
| 갱신 단위 | 컴포넌트 | DOM 노드 속성 | DOM 노드 속성 |
| 컴포넌트 함수 재실행 | 상태 변경마다 | 없음 | 최초 1회만 |
| 변경점 탐색 시점 | 런타임 (diffing) | 컴파일 타임 | 런타임 (구독 추적) |
| 대가 | diffing 오버헤드 | 컴파일러 의존, 유연성 제약 | 반응성 규칙 학습 필요 |

**결론**: 순수 갱신 성능만 놓고 보면 Solid/Svelte 쪽이 유리하다. React를 선택하는 이유는 성능 수치가 아니라 생태계 규모, 인력 확보, React Native 연계, 검증된 패턴의 축적이다. 면접에서 이 트레이드오프를 언급할 수 있으면 "React만 아는 사람"과 확실히 구분된다.

## 7. 실무에서는

- **React DevTools Profiler**의 "Highlight updates when components render" 옵션을 켜면 어떤 컴포넌트가 리렌더링되는지 화면에 테두리로 표시된다. 최적화는 여기서 병목을 확인한 뒤에 시작한다.
- 대량 리스트(수천 행 테이블 등)에서는 Virtual DOM 비교 비용 자체가 문제가 된다. 이때는 메모이제이션보다 **가상 스크롤**(화면에 보이는 행만 DOM에 만드는 방식)이 근본 해법이다. 비교할 노드 수를 줄이는 것이 비교를 빠르게 하는 것보다 효과적이다.
- 캔버스 기반 차트나 지도 라이브러리처럼 **DOM을 직접 다루는 게 정답인 영역**은 React가 관여하지 않도록 `useRef`로 컨테이너만 넘기고 라이브러리에 맡기는 것이 일반적인 패턴이다. Virtual DOM을 만능으로 쓰려 하면 오히려 손해다.

## 8. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. Virtual DOM이 무엇이고 왜 쓰나요?**

A. Virtual DOM은 UI의 모양을 기술한 메모리상의 JavaScript 객체 트리입니다. 상태가 바뀌면 새 트리를 만들어 이전 트리와 비교하고, 차이가 나는 부분만 실제 DOM에 커밋합니다. 목적은 DOM 조작을 빠르게 하는 게 아니라, 개발자가 "화면이 어떤 모습이어야 하는지"만 선언해도 상태와 화면이 어긋나지 않도록 보장하는 것입니다.

- 꼬리 질문: "그럼 성능 이점은 전혀 없나요?" → 있습니다. 여러 상태 변경을 묶어 DOM 쓰기를 한 번으로 줄이는 배치 처리, 그리고 사람이 수동 최적화를 하지 않아도 최소 변경이 보장된다는 점입니다. 다만 이건 "최악의 경우를 막아 준다"는 의미지 "항상 더 빠르다"는 뜻은 아닙니다.

**Q. "Virtual DOM이 빠르다"는 말이 왜 부정확한가요?**

A. 트리를 새로 만들고 비교하는 작업 자체가 비용이기 때문입니다. 텍스트 하나만 바꾸는 경우라면 `textContent`를 직접 대입하는 쪽이 순수 실행 시간은 더 짧습니다. Virtual DOM의 가치는 성능의 최고점을 올리는 게 아니라 최저점을 보장하는 데 있습니다. 실제로 Svelte나 Solid는 Virtual DOM 없이 컴파일 타임 분석이나 세밀한 구독으로 더 적은 런타임 비용을 달성합니다.

- 꼬리 질문: "그런데도 React를 쓰는 이유는?" → 생태계 성숙도, 인력 확보 용이성, React Native로 이어지는 추상화, 대규모 애플리케이션에서 검증된 패턴입니다. 순수 벤치마크 수치와 프로젝트 선택 기준은 다릅니다.

**Q. Virtual DOM이 있으면 DOM 조작을 신경 안 써도 되나요?**

A. 아닙니다. Virtual DOM은 **필요한 DOM 조작을 정확히 계산해 줄 뿐**, 불필요한 리렌더링 자체를 막아 주지는 않습니다. `key`를 잘못 주면 재사용할 수 있는 노드를 파괴하고 다시 만들고, 부모가 리렌더링되면 자식도 기본적으로 다시 렌더링됩니다. 그래서 재조정 규칙을 알고 코드를 쓰는 것이 여전히 중요합니다.

- 꼬리 질문: "리렌더링이 곧 DOM 업데이트인가요?" → 아닙니다. 리렌더링은 컴포넌트 함수가 다시 실행되어 새 객체 트리를 만드는 것이고, 비교 결과 차이가 없으면 DOM은 건드리지 않습니다.

## 자주 하는 실수

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-----------|
| "DOM이 느려서 Virtual DOM을 쓴다" | DOM API 호출 자체는 느리지 않다. 비싼 건 그로 인해 유발되는 레이아웃·페인트다 | Virtual DOM은 그 유발 횟수를 줄이는 장치다 |
| "리렌더링 = 실제 DOM 재생성" | 렌더 단계는 객체 트리만 만든다 | 비교 결과 차이가 없으면 DOM은 그대로다 |
| "Virtual DOM 덕분에 최적화가 필요 없다" | diffing 비용, 불필요한 리렌더링은 그대로 남는다 | 프로파일링으로 병목을 찾고 대응해야 한다 |
| "React는 바뀐 컴포넌트만 다시 실행한다" | 부모가 리렌더링되면 자식도 기본적으로 함께 실행된다 | 막으려면 `React.memo`나 구조 분리가 필요하다 |
| "JSX가 DOM을 만든다" | JSX는 객체를 만드는 함수 호출로 변환될 뿐이다 | DOM 생성은 커밋 단계에서 일어난다 |

## 한 줄 정리

Virtual DOM은 DOM을 빠르게 만드는 기술이 아니라, **"화면이 이래야 한다"고 선언만 해도 실제 DOM 조작이 최소한으로 유지되도록 보장해 주는 중간 계층**이다.
