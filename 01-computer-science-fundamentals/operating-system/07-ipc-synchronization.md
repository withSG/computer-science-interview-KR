## 1. 왜 필요한가

가상 메모리가 프로세스를 완벽하게 격리한 덕분에 한 프로그램의 버그가 다른 프로그램을 망가뜨리지
않게 됐다. 그런데 격리가 너무 잘돼서 새 문제가 생겼다. **의도적으로 데이터를 주고받고 싶어도 방법이
없다.** 웹 서버가 데이터베이스에 질의하려면, 셸에서 `ls | grep`을 하려면 프로세스끼리 대화해야 한다.

그래서 OS는 "커널을 경유하는 합법적인 통로"를 여러 개 열어준다. 이것이 IPC(Inter-Process
Communication)다. 커널만이 양쪽 주소 공간에 모두 접근할 수 있고 권한 검사를 할 수 있는 위치에 있기
때문에 커널을 거친다.

반대 방향의 문제도 있다. 스레드는 애초에 메모리를 공유하므로 통신은 공짜지만, 그 공유가 데이터를
깨뜨린다. 그래서 "접근을 어떻게 정돈할 것인가"라는 동기화 문제가 따라온다. 이 문서는 두 축을 함께
다룬다. **IPC는 벽을 넘는 방법, 동기화는 벽이 없을 때 질서를 만드는 방법**이다.

## 2. IPC 방식

### 전체 그림

```
          프로세스 A                     프로세스 B
       ┌─────────────┐               ┌─────────────┐
       │  주소 공간   │               │  주소 공간   │
       └──────┬──────┘               └──────┬──────┘
   ═══════════╪═════════════════════════════╪═══════════ 사용자/커널 경계
       ┌──────▼─────────────────────────────▼──────┐
       │                 커널                       │
       │  ┌────────┐ ┌──────────┐ ┌─────────────┐  │
       │  │ 파이프  │ │ 메시지 큐 │ │ 소켓 버퍼    │  │
       │  └────────┘ └──────────┘ └─────────────┘  │
       └────────────────────────────────────────────┘

  단, 공유 메모리만은 예외
       ┌─────────────┐               ┌─────────────┐
       │ 프로세스 A   │               │ 프로세스 B   │
       └──────┬──────┘               └──────┬──────┘
              └───────────┬─────────────────┘
                  ┌───────▼───────┐
                  │ 같은 물리 프레임 │  ← 커널을 거치지 않고 직접 읽고 쓴다
                  └───────────────┘
```

이 그림 하나에 성능 차이의 이유가 다 들어 있다. 대부분의 IPC는 **보내는 쪽 버퍼 → 커널 버퍼 → 받는
쪽 버퍼**로 두 번 복사하는데, 공유 메모리는 매핑만 걸어두면 복사가 아예 없다. 대신 커널이 중간에 없으니
"누가 언제 읽고 쓰는지"를 아무도 조율해주지 않아 별도의 동기화가 필수다.

### 파이프 (Pipe)

가장 오래되고 가장 단순한 방식이다. 커널 안에 바이트 스트림 버퍼를 하나 만들고, 한쪽은 쓰고 한쪽은
읽는다.

```bash
ls -l | grep ".md"          # 익명 파이프: 셸이 두 프로세스를 연결한다

mkfifo /tmp/mypipe          # 이름 있는 파이프(FIFO): 무관한 프로세스끼리도 가능
cat /tmp/mypipe &           # 읽는 쪽
echo "hello" > /tmp/mypipe  # 쓰는 쪽
```

익명 파이프는 `fork()`로 파일 디스크립터를 물려받아야 하므로 부모-자식 같은 혈연 관계가 필요하고,
FIFO는 파일 시스템에 이름을 남기므로 아무 프로세스나 열 수 있다.

기억해 둘 특징이 하나 있다. **버퍼가 가득 차면 쓰는 쪽이, 비어 있으면 읽는 쪽이 블로킹된다.** 이 성질
덕분에 별도 흐름 제어 없이도 생산 속도와 소비 속도가 자동으로 맞춰진다.

### 메시지 큐 (Message Queue)

파이프가 바이트 스트림이라면 메시지 큐는 **메시지 단위**로 주고받는다. 경계가 보존되므로 "어디까지가
한 메시지인지"를 애플리케이션이 직접 파싱할 필요가 없다. 메시지에 타입을 붙여 원하는 것만 골라 받을
수 있고, 받는 쪽이 아직 실행되지 않았어도 커널이 보관해 준다는 점에서 비동기적이다.

이름이 겹치는 개념 하나를 짚어야 한다. 면접에서 "메시지 큐" 하면 대부분 Kafka나 RabbitMQ 같은 분산
메시징 시스템을 떠올리는데, OS의 메시지 큐와는 층위가 다르다. 전자는 네트워크 너머의 여러 서버를 잇고
영속성·재전송·순서 보장을 다루며, 후자는 한 대의 머신 안에서 커널 메모리를 쓴다.

### 공유 메모리 (Shared Memory)

물리 메모리 영역 하나를 두 프로세스의 가상 주소 공간에 각각 매핑한다. 복사가 없어 **가장 빠른 IPC**이며
대용량 데이터를 자주 주고받을 때 유리하다.

```c
// POSIX 공유 메모리 개요 (개념 확인용)
int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0666);
ftruncate(fd, 4096);
void *ptr = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
// 이제 ptr을 일반 포인터처럼 쓰면 상대 프로세스도 같은 내용을 본다
```

대가는 명확하다. 커널이 중간에 없으니 순서를 아무도 보장하지 않아, A가 쓰는 도중에 B가 읽으면 반쪽짜리
데이터를 가져간다. 그래서 **공유 메모리는 거의 언제나 세마포어나 뮤텍스와 짝지어 쓴다.**

### 소켓 (Socket)

유일하게 **다른 머신과도 통신할 수 있는** IPC다. 같은 머신 안에서 쓸 때는 유닉스 도메인 소켓
(Unix Domain Socket)을 쓰면 TCP/IP 스택을 건너뛰어 훨씬 빠르다. 로컬 통신에 소켓을 쓰는 이유는 성능이
아니라 **확장성**이다. 처음부터 소켓으로 짜두면 나중에 두 컴포넌트를 다른 서버로 분리할 때 주소만
바꾸면 된다. Docker 데몬, PostgreSQL, MySQL이 유닉스 도메인 소켓과 TCP 소켓을 함께 지원하는 이유다.

### 시그널 (Signal)

데이터를 옮기는 수단이 아니라 **사건을 알리는 수단**이다. 번호 하나만 전달되고 내용은 없다.

```bash
kill -TERM 1234    # 정상 종료 요청 (프로세스가 정리 후 종료할 기회를 준다)
kill -KILL 1234    # 강제 종료 (프로세스가 가로챌 수 없다)
kill -HUP  1234    # 설정 다시 읽기 (많은 데몬의 관례)
```

시그널이 실무에서 중요한 지점은 **graceful shutdown**이다. 쿠버네티스는 파드를 내릴 때 먼저 SIGTERM을
보내고 유예 시간을 준 뒤 SIGKILL을 보낸다. 애플리케이션이 SIGTERM 핸들러에서 진행 중인 요청을 마무리해야
무중단 배포가 성립하고, 이 핸들러가 없으면 배포할 때마다 처리 중이던 요청이 끊긴다.

### IPC 방식 비교

| 방식 | 데이터 복사 | 속도 | 데이터 크기 | 경계 보존 | 원격 통신 | 동기화 필요 |
|------|-------------|------|-------------|-----------|-----------|-------------|
| 파이프 / FIFO | 2회 | 보통 | 버퍼 제한 | X (바이트 스트림) | X | 불필요 (커널이 처리) |
| 메시지 큐 | 2회 | 보통 | 메시지 크기 제한 | O | X | 불필요 |
| 공유 메모리 | 0회 | 매우 빠름 | 대용량 가능 | 직접 정의 | X | **필수** |
| 소켓 | 2회 이상 | 상대적으로 느림 | 제한 없음 | 프로토콜에 따라 | O | 불필요 |
| 시그널 | 데이터 없음 | 즉시 | 없음 | 해당 없음 | X | 해당 없음 |

**그래서 언제 뭘 쓰나**: 대용량을 초저지연으로 주고받아야 하면 공유 메모리 + 세마포어, 나중에 서버를
분리할 가능성이 있으면 처음부터 소켓, 단순한 단방향 스트림이면 파이프, 제어 신호면 시그널. 대부분의
애플리케이션 개발에서는 소켓으로 시작해 병목이 증명됐을 때만 공유 메모리를 검토하는 편이 현실적이다.

## 3. 임계 구역 문제

### 정의

**임계 구역(Critical Section)** 은 공유 자원에 접근하는 코드 구간이다. 여기에 둘 이상이 동시에 들어가면
데이터가 깨진다. 문제는 "동시에 못 들어가게" 만드는 것 자체가 생각보다 어렵다는 점이다.

```
반복 {
    진입 구역 (entry)   ← 들어가도 되는지 확인하고 표시
        임계 구역 (critical section)  ← 공유 자원 접근
    퇴출 구역 (exit)    ← 나왔다고 표시
        나머지 구역 (remainder)
}
```

### 올바른 해법이 만족해야 할 세 조건

| 조건 | 의미 | 위반하면 |
|------|------|----------|
| 상호 배제 (Mutual Exclusion) | 한 번에 하나만 임계 구역에 있다 | 데이터가 깨진다 (경쟁 상태) |
| 진행 (Progress) | 아무도 임계 구역에 없으면, 들어가려는 것들 중에서 유한 시간 안에 하나가 선택된다 | 아무도 못 들어간다 (교착) |
| 한정 대기 (Bounded Waiting) | 대기 횟수에 상한이 있다 | 특정 스레드만 계속 밀린다 (기아) |

셋 중 하나만 빠뜨려도 실패다. 상호 배제만 신경 쓰다 진행 조건을 놓치는 것이 흔한 실수인데, "양쪽 다
들어가고 싶다고 표시한 뒤 서로 양보"하는 순진한 구현이 그 예다.

### 소프트웨어만으로도 되지만

Peterson 알고리즘 같은 순수 소프트웨어 해법이 존재한다는 것은 특별한 하드웨어 지원 없이 세 조건을
만족시킬 수 있음을 보여줬다는 점에서 이론적으로 중요하다. 하지만 실무에서는 쓰지 않는다. 두 프로세스로
한정되고, 무엇보다 **현대 CPU와 컴파일러의 명령어 재배치** 때문에 코드에 적은 순서가 실행 순서라는
보장이 없기 때문이다. 그래서 실제 시스템은 하드웨어가 제공하는 원자적 명령어(test-and-set,
compare-and-swap)로 락을 만든다. 이 명령어들은 읽고 쓰는 것을 다른 코어가 끼어들 수 없게 한 덩어리로
수행한다.

## 4. 뮤텍스, 세마포어, 모니터

### 뮤텍스 (Mutex)

MUTual EXclusion의 줄임말. 열쇠가 하나뿐인 자물쇠다. 잠근 스레드만 풀 수 있다는 **소유권(ownership)**
개념이 핵심이다.

```java
private final ReentrantLock lock = new ReentrantLock();

public void withdraw(long amount) {
    lock.lock();
    try {
        if (balance >= amount) balance -= amount;
    } finally {
        lock.unlock();   // 반드시 finally에서
    }
}
```

소유권이 있으면 실수로 남이 푸는 것을 막아주고, "지금 락을 쥔 스레드"를 특정할 수 있어 그 스레드의
우선순위를 일시적으로 올려주는 우선순위 상속도 가능해진다.

### 세마포어 (Semaphore)

정수 카운터와 대기 큐를 가진 도구다. `acquire()`(P)는 카운터를 1 줄이고 0 미만이면 대기, `release()`(V)는
1 늘리고 대기자를 깨운다.

```java
// 동시에 최대 10개만 외부 API를 호출하도록 제한
private final Semaphore semaphore = new Semaphore(10);

public Response call() throws InterruptedException {
    semaphore.acquire();
    try {
        return externalApi.request();
    } finally {
        semaphore.release();
    }
}
```

카운터를 1로 두면 뮤텍스처럼 쓸 수 있고(이진 세마포어) 그래서 둘을 같은 것으로 오해하기 쉬운데,
결정적 차이는 **소유권이 없다**는 점이다. A가 `acquire`한 것을 B가 `release`해도 문법상 문제가 없다.

### 카운팅 세마포어의 진짜 용도: 신호 보내기

세마포어를 "N개 제한"으로만 이해하면 절반만 아는 것이다. 소유권이 없다는 성질 덕분에 **한 스레드가
다른 스레드에게 사건을 알리는** 용도로 쓸 수 있다. 생산자-소비자 문제가 대표 예다.

```
버퍼 크기 N인 생산자-소비자
  세마포어 empty = N (빈 칸 수) / full = 0 (채워진 칸 수) / 뮤텍스 mutex (버퍼 보호)

  생산자                          소비자
  ┌──────────────────┐            ┌──────────────────┐
  │ empty.acquire()  │            │ full.acquire()   │  ← 빌 때까지 대기
  │ mutex.lock()     │            │ mutex.lock()     │
  │   버퍼에 넣기      │            │   버퍼에서 꺼내기  │
  │ mutex.unlock()   │            │ mutex.unlock()   │
  │ full.release()   │───알림────►│                  │
  │                  │◄───알림────│ empty.release()  │
  └──────────────────┘            └──────────────────┘
```

여기서 `full`은 생산자가 올리고 소비자가 내린다. 획득자와 해제자가 다르다. 뮤텍스로는 표현할 수 없는
구조이고, 이것이 "세마포어는 뮤텍스의 일반화"가 아니라 별개 도구인 이유다.

주의할 점: `empty.acquire()`와 `mutex.lock()`의 순서를 바꾸면 데드락이 난다. 버퍼가 가득 찬 상태에서
생산자가 mutex를 쥔 채 `empty`를 기다리면 소비자는 mutex를 못 잡아 꺼내지 못하고, 그러면 `empty`는
영원히 올라가지 않는다.

### 모니터 (Monitor)

세마포어는 강력하지만 위험하다. `acquire`/`release` 짝을 잘못 맞추거나 순서를 틀리면 즉시 버그다.
모니터는 **상호 배제를 언어 차원에서 자동화한** 고수준 추상화로, (1) 공유 데이터, (2) 그 데이터를
다루는 프로시저, (3) 자동으로 적용되는 락, (4) 조건 변수를 한 덩어리로 묶는다. 프로시저에 들어가면
자동으로 잠기고 나오면 자동으로 풀린다. Java의 모든 객체는 모니터를 하나씩 갖고 있다.

```java
public class BoundedBuffer<T> {
    private final Queue<T> queue = new LinkedList<>();
    private final int capacity;

    public BoundedBuffer(int capacity) { this.capacity = capacity; }

    public synchronized void put(T item) throws InterruptedException {
        while (queue.size() == capacity) {   // if가 아니라 while
            wait();                          // 락을 놓고 대기
        }
        queue.add(item);
        notifyAll();                         // 기다리던 소비자를 깨운다
    }

    public synchronized T take() throws InterruptedException {
        while (queue.isEmpty()) wait();
        T item = queue.poll();
        notifyAll();
        return item;
    }
}
```

`wait()`는 락을 놓고 대기 큐로 들어가고, `notifyAll()`이 깨우면 락을 다시 잡은 뒤 재개한다. 락을
놓지 않으면 조건을 바꿔줄 상대가 들어올 수 없으니 이 동작은 필수다.

`if`가 아니라 `while`을 쓰는 이유도 중요하다. 깨어나 락을 다시 잡기까지의 틈에 다른 스레드가 먼저
들어와 버퍼를 채워버릴 수 있고, 근거 없는 깨어남(spurious wakeup)도 명세상 허용된다. **조건은 깨어난
뒤 반드시 다시 검사해야 한다.**

### 세 도구 비교

| 구분 | 뮤텍스 | 세마포어 | 모니터 |
|------|--------|----------|--------|
| 동시 진입 허용 수 | 1 | N (카운터) | 1 |
| 소유권 | 있음 | 없음 | 있음 (암묵적) |
| 획득/해제 주체 | 같아야 함 | 달라도 됨 | 같음 (블록 단위) |
| 추상화 수준 | 저수준 | 저수준 | 고수준 (언어 지원) |
| 조건 대기 | 별도 조건 변수 필요 | 카운터로 흉내 | `wait`/`notify` 내장 |
| 실수 위험 | 해제 누락 | 순서·짝 오류 | 상대적으로 낮음 |
| Java 대응 | `ReentrantLock` | `Semaphore` | `synchronized` + `wait`/`notify` |

**그래서 언제 뭘 쓰나**: 일반적인 상호 배제는 가장 안전하고 짧은 모니터(`synchronized`)로 시작하고,
타임아웃·인터럽트·공정성 제어가 필요하면 뮤텍스(`ReentrantLock`), 동시 접근 수를 N으로 제한하거나
스레드 간 신호를 주고받아야 하면 세마포어를 쓴다.

## 5. 스핀락과 busy waiting

### 두 가지 대기 방식

락이 이미 잡혀 있을 때 어떻게 기다릴 것인가. 선택지는 둘이다.

```
블로킹 락 (뮤텍스)
  락 실패 → 스레드를 Waiting 상태로 → CPU를 다른 스레드에 양보
          → 락이 풀리면 커널이 깨움 → Ready → 실행   [컨텍스트 스위칭 2회]

스핀락 (spinlock)
  락 실패 → while (락이 잡혀있음) { 계속 확인 }  ← busy waiting
          → 락이 풀리는 순간 즉시 진입              [기다리는 동안 CPU 100%]
```

직관적으로는 CPU를 태우는 스핀락이 무조건 나빠 보이지만, 컨텍스트 스위칭 왕복 비용을 감안하면
**임계 구역이 그보다 짧을 때는 그냥 기다리는 쪽이 싸다.** 잠깐 기다릴 일에 스레드를 재우고 깨우는
절차를 밟는 것이 더 낭비다.

### 선택 기준

| 조건 | 스핀락 | 블로킹 락 |
|------|--------|-----------|
| 임계 구역 길이 | 매우 짧음 (수백 나노초) | 길거나 예측 불가 |
| CPU 코어 수 | 멀티 코어 필수 | 무관 |
| 임계 구역 내 블로킹 | 절대 불가 | 가능 |
| 대표 사용처 | 커널 내부, 락 구현 내부 | 애플리케이션 코드 대부분 |

**단일 코어에서 스핀락은 최악이다.** 락을 쥔 스레드가 실행돼야 락이 풀리는데 스핀하는 스레드가 CPU를
붙잡고 있으니, 타임 퀀텀이 소진될 때까지 아무 일도 일어나지 않는다. 스핀락은 "락을 쥔 쪽이 다른
코어에서 지금 돌고 있다"는 전제 위에서만 성립한다.

또 하나. **스핀락을 쥔 채로 절대 잠들면 안 된다.** 락을 쥔 스레드가 I/O를 기다리러 가면 다른 코어의
스레드들은 그동안 계속 CPU를 태운다. 리눅스 커널이 스핀락 구간에서 잠들 수 있는 함수 호출을 금지하는
이유다.

### 하이브리드 접근

현실의 구현은 둘을 섞는다. **적응형 뮤텍스(adaptive mutex)** 는 일단 짧게 스핀해 보고, 그 안에 못
잡으면 블로킹으로 전환해 짧은 대기의 이점과 긴 대기의 안전성을 모두 취한다. JVM의 `synchronized`도
경합이 없으면 CAS 한 번으로 끝나고, 경합이 생기면 잠시 스핀하다가, 그래도 안 되면 OS 수준 블로킹으로
넘어간다. 그래서 "synchronized는 무겁다"는 통념은 현재 JVM에서는 정확하지 않다. CAS 기반 lock-free
자료구조도 넓게 보면 스핀 계열이라, 경합이 낮을 때는 가장 빠르지만 심해지면 재시도로 CPU를 태운다.

## 6. 실무에서는

**컨테이너 간 통신**: 같은 파드 안의 컨테이너들은 유닉스 도메인 소켓이나 공유 볼륨으로 통신하고,
파드가 다르면 TCP 소켓밖에 답이 없다. 사이드카 패턴이 전자의 사례다.

**세마포어로 하는 부하 제어**: 외부 API 호출을 제한 없이 날리면 상대 서비스를 무너뜨리거나 요청
한도에 걸린다. `Semaphore(N)`으로 동시 호출 수를 묶어두면 간단한 벌크헤드가 된다. DB 커넥션 풀도
같은 개념의 실물이다. 풀 크기가 곧 카운터이고, 풀 고갈로 요청이 쌓이다 타임아웃되는 장애는 세마포어
대기가 길어진 것과 같은 현상이다.

**graceful shutdown**: 앞서 말한 SIGTERM 처리는 무중단 배포의 전제 조건이다. Spring Boot는
`server.shutdown=graceful` 설정으로 진행 중인 요청을 마무리한 뒤 종료할 수 있고, 이 설정과 쿠버네티스의
`terminationGracePeriodSeconds`를 함께 맞춰야 실제로 무중단이 된다. 한편 로그 수집기가 느려지면
애플리케이션이 함께 느려지는 현상도 파이프의 블로킹 성질에서 나온다.

## 7. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. 뮤텍스와 세마포어의 차이는 무엇인가요?**

A. 뮤텍스는 임계 구역에 한 번에 하나만 들어가게 하는 도구이고 소유권 개념이 있어서 잠근 스레드만
풀 수 있습니다. 세마포어는 정수 카운터를 두고 N개까지 동시 접근을 허용하며 소유권이 없어서 획득한
스레드와 해제하는 스레드가 달라도 됩니다. 이 소유권 유무가 용도를 가릅니다. 세마포어는 소유권이 없어
생산자-소비자처럼 한 스레드가 다른 스레드에게 신호를 보내는 용도로 쓸 수 있습니다.

- 꼬리 질문: "그럼 이진 세마포어로 뮤텍스를 대신하면 안 되나요?" → 동작은 비슷하지만 소유권이 없어
  실수로 남이 해제하는 것을 막지 못하고, 우선순위 상속 같은 최적화도 적용할 수 없다.

**Q. 임계 구역 문제의 해결 조건 세 가지를 말해보세요.**

A. 상호 배제, 진행, 한정 대기입니다. 상호 배제는 한 번에 하나만 임계 구역에 있어야 한다는 것, 진행은
임계 구역이 비어 있는데도 아무도 못 들어가는 상황이 없어야 한다는 것, 한정 대기는 어떤 스레드가
무한정 밀리지 않도록 대기 횟수에 상한이 있어야 한다는 것입니다. 진행 조건이 깨지면 교착이 되고
한정 대기가 깨지면 기아가 발생합니다.

- 꼬리 질문: "실무에서 한정 대기는 어떻게 보장하나요?" → 락에 공정성 옵션을 켜거나 대기 큐를 FIFO로
  운영한다. 다만 공정성은 처리량을 희생하므로 기본값은 보통 비공정이다.

**Q. 공유 메모리가 다른 IPC보다 빠른 이유는 무엇인가요?**

A. 다른 방식은 보내는 프로세스의 버퍼에서 커널 버퍼로, 다시 받는 프로세스의 버퍼로 두 번 복사가
일어나고 그때마다 시스템 콜로 모드 전환 비용도 듭니다. 공유 메모리는 물리 프레임 하나를 양쪽 가상
주소 공간에 매핑하므로 복사도 시스템 콜도 없이 일반 메모리 접근처럼 동작합니다. 대신 커널이 순서를
조율해주지 않아 세마포어 같은 동기화 수단이 반드시 필요합니다.

- 꼬리 질문: "그럼 항상 공유 메모리를 쓰면 되지 않나요?" → 동기화를 직접 설계해야 해서 버그 위험이
  크고, 같은 머신 안에서만 쓸 수 있어 확장성이 없다.

**Q. 스핀락은 언제 쓰나요?**

A. 임계 구역이 매우 짧고 멀티 코어 환경일 때 씁니다. 블로킹 락은 대기 시 컨텍스트 스위칭이 두 번
일어나는데, 임계 구역이 그 비용보다 짧다면 그냥 기다리는 편이 저렴합니다. 다만 단일 코어에서는 락을
쥔 스레드가 실행돼야 락이 풀리는데 스핀하는 쪽이 CPU를 붙잡고 있어 최악이 되고, 스핀락을 쥔 채
블로킹 작업을 하면 다른 코어들이 계속 CPU를 태웁니다. 그래서 주로 커널 내부에서 쓰이고, 애플리케이션
코드에서는 적응형 뮤텍스가 이 판단을 대신 해줍니다.

- 꼬리 질문: "CAS 기반 Atomic 클래스도 같은 성질인가요?" → 그렇다. 실패 시 재시도 루프라 경합이 낮으면
  빠르고 높으면 CPU를 낭비하므로, 고경합에는 `LongAdder` 같은 분산 구조를 쓴다.

## 자주 하는 실수

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-------------|
| "이진 세마포어 = 뮤텍스" | 소유권 유무가 다르다 | 세마포어는 획득자와 해제자가 달라도 된다 |
| "`wait()`은 `if`로 감싸도 된다" | 깨어난 뒤 조건이 바뀌었을 수 있다 | 반드시 `while`로 재검사 |
| "스핀락이 항상 빠르다" | 단일 코어나 긴 임계 구역에서는 최악 | 임계 구역 길이와 코어 수를 함께 본다 |
| "`synchronized`는 무거우니 피한다" | 현대 JVM은 무경합 시 매우 저렴하다 | 측정 없이 `ReentrantLock`으로 바꿀 이유는 없다 |
| "SIGKILL 핸들러를 등록하면 된다" | SIGKILL은 가로챌 수 없다 | 정리 작업은 SIGTERM 핸들러에서 |

## 한 줄 정리

IPC는 격리된 프로세스가 커널을 경유해 데이터를 주고받는 통로이고 동기화는 공유된 자원의 접근 순서를
정하는 규칙인데, 둘 다 "복사 비용을 줄일수록 직접 관리할 것이 늘어난다"는 같은 트레이드오프 위에 있다.
