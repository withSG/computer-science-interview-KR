## 1. 왜 필요한가

Ready 큐에 프로세스가 하나뿐이면 스케줄링은 고민할 것이 없다. 문제는 언제나 여럿이라는 것이고,
그들이 원하는 것이 서로 다르다는 것이다.

- 동영상 인코딩: 응답 속도는 상관없다. 전체가 빨리 끝나기만 하면 된다.
- 텍스트 편집기: 총 CPU 사용량은 미미하지만 키를 누르면 즉시 반응해야 한다.
- 백업 스크립트: 언제 끝나도 상관없지만 언젠가는 끝나야 한다.

이 셋을 한 CPU에 올려두고 "가장 좋은 순서"를 정하라고 하면 정답이 없다. 인코딩을 먼저 끝내면 편집기가
버벅이고, 편집기에 우선권을 계속 주면 인코딩이 하염없이 밀린다. **스케줄링은 최적해를 찾는 문제가
아니라 무엇을 포기할지 정하는 문제**다.

여기에 제약이 하나 더 있다. 스케줄러 자신도 CPU를 쓴다. 완벽한 결정을 내리기 위해 매번 복잡한 계산을
하면 정작 일할 시간이 줄어든다. 그래서 실제 스케줄러는 "충분히 좋은 결정을 아주 싸게" 내리는 쪽으로
설계된다.

**비유**: 병원 응급실의 환자 분류(triage)다. 도착 순서대로 받으면 공정해 보이지만 위독한 환자가
죽는다. 위중도만 보면 경증 환자가 하루 종일 밀린다. 그래서 실제 응급실은 위중도로 우선순위를 매기되
오래 기다린 환자의 순위를 조금씩 올린다. 이것이 그대로 우선순위 스케줄링과 에이징이다.

**비유의 한계**: 의사는 환자를 보면 위중도를 판단할 수 있지만, OS는 프로세스가 앞으로 CPU를 얼마나
쓸지 알 수 없다. 이 "미래를 모른다"는 제약이 스케줄링 알고리즘의 난이도를 결정한다.

## 2. 선점형 vs 비선점형

### 정의

- **비선점(Non-preemptive)**: 한 번 CPU를 받은 프로세스는 스스로 놓을 때까지 계속 쓴다. 종료하거나
  I/O를 기다리러 갈 때만 CPU가 넘어간다.
- **선점(Preemptive)**: OS가 실행 중인 프로세스에게서 CPU를 강제로 회수할 수 있다.

### 선점은 어떻게 가능한가

CPU를 쓰고 있는 것은 프로세스인데 OS가 어떻게 뺏을까? 답은 **타이머 인터럽트**다. OS는 부팅 시
하드웨어 타이머에 "일정 주기마다 인터럽트를 걸어라"고 설정해 둔다. 인터럽트가 걸리면 제어권이 강제로
커널로 넘어오고, 그 틈에 스케줄러가 개입한다.

타이머 인터럽트가 없으면 선점형 스케줄링은 원리적으로 불가능하다. 무한 루프에 빠진 프로그램 하나가
시스템 전체를 정지시키던 옛 협력형 멀티태스킹의 문제가 바로 이것이었다.

### 비교

| 구분 | 비선점형 | 선점형 |
|------|---------|--------|
| CPU 회수 | 프로세스가 자발적으로 반납 | OS가 강제로 회수 |
| 응답성 | 낮음 (긴 작업이 앞을 막음) | 높음 |
| 컨텍스트 스위칭 | 적음 | 많음 (오버헤드 발생) |
| 공유 자원 일관성 | 관리 쉬움 | 임계 구역 보호 필수 |
| 대표 알고리즘 | FCFS, SJF, HRN | RR, SRTF, 선점 우선순위, MLFQ |

**그래서 언제 뭘 쓰나**: 사용자와 상호작용하는 시스템은 선점형이 사실상 필수다. 응답성을 포기할 수
없기 때문이다. 반대로 배치 처리 전용 시스템은 비선점형으로 스위칭 오버헤드를 아끼는 선택이 합리적일
수 있다.

## 3. 주요 알고리즘

아래 예시는 모두 이 작업 집합을 기준으로 한다.

```
작업   도착시각   CPU 버스트
 P1      0          7
 P2      2          4
 P3      4          1
 P4      5          4
```

### FCFS (First Come First Served) — 비선점

도착 순서대로 처리한다. 큐 하나면 구현이 끝난다.

```
 0        7      11   12       16
 ├───P1───┼──P2──┼─P3─┼───P4───┤

 대기 시간: P1=0, P2=7-2=5, P3=11-4=7, P4=12-5=7
 평균 대기 시간 = (0+5+7+7)/4 = 4.75
```

문제는 **호위 효과(Convoy Effect)** 다. 위에서 P3는 1만 쓰면 되는데 앞의 긴 작업들 때문에 7을 기다렸다.
마트에서 카트 가득 채운 사람 뒤에 껌 하나 든 사람이 서 있는 상황이다. 짧은 작업이 많은 시스템에서는
평균 대기 시간이 급격히 나빠진다.

### SJF (Shortest Job First) — 비선점

CPU 버스트가 가장 짧은 작업을 먼저 실행한다.

```
 0        7    8       12      16
 ├───P1───┼─P3─┼──P2───┼───P4──┤
 (0시점엔 P1만 있어 P1부터. 이후 남은 것 중 짧은 순)

 대기 시간: P1=0, P3=7-4=3, P2=8-2=6, P4=12-5=7
 평균 대기 시간 = (0+3+6+7)/4 = 4.0
```

SJF는 **평균 대기 시간을 최소화한다는 것이 수학적으로 증명된** 알고리즘이다. 그런데 두 가지 치명적
문제가 있다.

1. **실행 시간을 미리 알 수 없다.** 프로세스가 CPU를 얼마나 쓸지는 실행해 봐야 안다. 실무에서는 과거
   버스트의 지수 이동 평균으로 예측하지만 어디까지나 추정이다.
2. **기아가 발생한다.** 짧은 작업이 계속 들어오면 긴 작업은 영원히 순서가 오지 않는다.

### SRTF (Shortest Remaining Time First) — 선점

SJF의 선점 버전이다. 새 작업이 도착했을 때 그 작업의 버스트가 현재 실행 중인 작업의 **남은 시간**보다
짧으면 즉시 교체한다.

```
 0    2      4  5   7        11         16
 ├─P1─┼──P2──┼P3┼P2─┼───P4───┼────P1────┤

 t=2 : P2(4) < P1 남은시간(5) → P1 선점
 t=4 : P3(1) < P2 남은시간(2) → P2 선점
 t=5 : P3 종료, 남은 것 P2(2) P4(4) P1(5) → P2
 t=7 : P2 종료 → P4(4)
 t=11: P4 종료 → P1(5)

 대기 시간: P1=(16-0)-7=9, P2=(7-2)-4=1, P3=(5-4)-1=0, P4=(11-5)-4=2
 평균 대기 시간 = (9+1+0+2)/4 = 3.0
```

평균 대기 시간은 SJF의 4.0보다 더 줄어들지만, 선점이 잦아 컨텍스트 스위칭 비용이 붙고 기아 문제는
오히려 심해진다. 긴 작업은 짧은 작업이 도착할 때마다 밀려난다. 위 결과에서도 P1은 첫 번째로 도착하고도
가장 늦게 끝났다.

### Round Robin (RR) — 선점

각 프로세스에 동일한 **타임 퀀텀(Time Quantum)** 을 주고, 다 쓰면 큐 맨 뒤로 보낸다.

```
타임 퀀텀 = 2 인 경우

 0   2   4   6  7   9   11  13  15 16
 ├P1─┼P2─┼P1─┼P3┼P2─┼P4─┼P1─┼P4─┼P1┤

 t=0  P1 실행 → 퀀텀 소진, 그사이 도착한 P2 뒤로 [P2 P1]
 t=2  P2 실행 → 퀀텀 소진, t=4에 P3 도착      [P1 P3 P2]
 t=4  P1 실행 → 퀀텀 소진, t=5에 P4 도착      [P3 P2 P4 P1]
 t=6  P3 실행 → 1만 쓰고 종료(t=7)            [P2 P4 P1]
 t=7  P2 실행 → 남은 2를 다 쓰고 종료(t=9)     [P4 P1]
 t=9  P4 실행 → 퀀텀 소진                     [P1 P4]
 t=11 P1 실행 → 퀀텀 소진                     [P4 P1]
 t=13 P4 실행 → 종료(t=15) / t=15 P1이 남은 1 소진 후 종료

 Ready 큐가 원형으로 돈다
   ┌──────────────────────────┐
   │                          │
   ▼                          │
 ┌────┐   ┌────┐   ┌────┐   ┌────┐
 │ P1 │──►│ P2 │──►│ P3 │──►│ P4 │
 └────┘   └────┘   └────┘   └────┘
   │                          ▲
   │  퀀텀 소진 → 맨 뒤로       │
   └──────────────────────────┘
```

RR은 평균 대기 시간이 좋은 편은 아니지만 **응답 시간이 예측 가능하다**는 결정적 장점이 있다.
프로세스가 n개면 아무리 늦어도 (n-1) × 퀀텀 안에는 내 차례가 온다. 대화형 시스템에서 RR 계열이
기본이 되는 이유다.

### 우선순위 스케줄링 (Priority) — 선점/비선점 모두 가능

각 프로세스에 우선순위를 매기고 높은 쪽부터 실행한다. 우선순위는 외부에서 지정할 수도 있고(리눅스의
nice 값), 시스템이 계산할 수도 있다(I/O 위주 프로세스에 가산점).

문제는 역시 기아다. 낮은 우선순위 작업은 높은 것들이 계속 들어오는 한 실행되지 않는다. 해결책이
**에이징(Aging)** 이다.

### MLFQ (다단계 피드백 큐) — 선점

우선순위 큐를 여러 개 두고, 프로세스를 그 사이에서 **이동시킨다**. "피드백"은 실행 결과를 보고
우선순위를 조정한다는 뜻이다.

```
 새 프로세스는 언제나 최상위 큐로 들어온다
        │
        ▼
 ┌──────────────────────────────┐
 │ Q0 (우선순위 高, 퀀텀 8ms)     │  퀀텀 다 씀 ─┐
 └──────────────────────────────┘             │
        ▲                                     ▼
        │                       ┌──────────────────────────────┐
        │                       │ Q1 (중간, 퀀텀 16ms)          │  퀀텀 다 씀 ─┐
   에이징으로                    └──────────────────────────────┘             │
   주기적 승격                          ▲                                    ▼
        │                              │                  ┌──────────────────────────┐
        └──────────────────────────────┴──────────────────│ Q2 (低, FCFS)            │
                                                          └──────────────────────────┘
 규칙
  1. 상위 큐에 프로세스가 있으면 하위 큐는 실행되지 않는다
  2. 같은 큐 안에서는 RR
  3. 퀀텀을 다 쓰면 한 단계 아래로 내려간다
  4. 퀀텀을 다 쓰기 전에 I/O로 양보하면 현재 큐를 유지한다
  5. 일정 주기마다 모든 프로세스를 최상위 큐로 올린다 (에이징)
```

규칙 3과 4의 조합이 MLFQ의 핵심이다. **CPU를 오래 붙잡는 프로세스는 스스로 아래로 내려가고, 잠깐
쓰고 I/O를 기다리러 가는 프로세스는 높은 자리를 유지한다.** 실행 시간을 미리 몰라도 관찰만으로
"짧은 작업 우선"과 비슷한 효과를 얻는 셈이다.

규칙 5가 없으면 CPU 집약 작업이 최하위에서 영원히 굶는다. 또 규칙 4를 악용해 퀀텀 만료 직전에
일부러 짧은 I/O를 넣는 꼼수를 쓸 수 있어서, 현대 구현은 "큐에 머문 총 CPU 사용 시간"으로 강등을
판단한다.

### 알고리즘 비교

| 알고리즘 | 선점 | 평균 대기 | 응답성 | 기아 | 실행시간 사전 지식 |
|----------|------|-----------|--------|------|--------------------|
| FCFS | X | 나쁨(호위 효과) | 나쁨 | 없음 | 불필요 |
| SJF | X | 최적 | 보통 | 있음 | 필요 |
| SRTF | O | 최적 이하 | 좋음 | 심함 | 필요 |
| RR | O | 보통 | 매우 좋음 | 없음 | 불필요 |
| 우선순위 | 선택 | 정책 나름 | 정책 나름 | 있음 | 불필요 |
| MLFQ | O | 좋음 | 좋음 | 에이징으로 방지 | 불필요 |

**그래서 언제 뭘 쓰나**: 범용 OS는 MLFQ 계열이 사실상 표준이다. 실행 시간을 몰라도 되고, 대화형
작업의 응답성과 배치 작업의 처리량을 동시에 어느 정도 챙기기 때문이다. FCFS나 SJF는 실제 OS보다
디스크 I/O 스케줄링, 작업 큐 설계 같은 응용 영역에서 더 자주 만난다.

## 4. 기아와 에이징

**기아(Starvation)** 는 특정 프로세스가 CPU를 계속 배정받지 못해 무한정 대기하는 상태다. 데드락과
달리 시스템 전체는 잘 돌아가고, 굶는 쪽도 언제든 실행될 수 **있는** 상태다. 단지 순서가 오지 않을
뿐이다. 이 차이 때문에 발견도 늦다. 시스템 지표는 정상인데 특정 배치 작업만 며칠째 안 끝나는 식이다.

**에이징(Aging)** 은 대기 시간에 비례해 우선순위를 올려주는 기법이다. 아무리 낮은 우선순위여도
기다리다 보면 언젠가 최상위에 도달하므로 **유한 시간 안에 실행이 보장된다**.

```
에이징 예 (숫자가 낮을수록 높은 우선순위, 5초마다 1 상승)

  t=0    P_low: 우선순위 10  ← 계속 밀림
  t=5    P_low: 우선순위 9
  t=10   P_low: 우선순위 8
  ...
  t=45   P_low: 우선순위 1   ← 드디어 실행
```

HRN(Highest Response Ratio Next)은 같은 아이디어를 공식 하나로 표현한 것이다.

```
우선순위 = (대기 시간 + 서비스 시간) / 서비스 시간
```

서비스 시간이 짧으면 값이 커지므로 SJF의 장점을 가져오고, 대기 시간이 길어져도 값이 커지므로 기아를
막는다. 두 목표를 하나의 식으로 절충한 사례다.

같은 문제는 락에서도 나타난다. 락 대기 큐가 불공정하면 특정 스레드가 계속 락을 못 잡는데, Java의
`ReentrantLock(true)` 공정 모드가 이를 막아준다. 대신 처리량은 떨어진다. 자세한 내용은
[04-deadlock-race-condition.md](./04-deadlock-race-condition.md)를 참고한다.

## 5. 타임 퀀텀 설정의 트레이드오프

RR과 MLFQ에서 타임 퀀텀 크기는 단순한 숫자가 아니라 **응답성과 처리량 사이의 다이얼**이다.

```
퀀텀이 매우 작을 때 (전환 비용을 5μs로 잡고 퀀텀을 50μs로 준 경우)
 ├─작업─┼전환┼─작업─┼전환┼─작업─┼전환┼─작업─┤
   50μs   5    50μs   5    50μs   5    50μs
 → 전체 시간의 약 9%를 전환에 쓴다. 응답은 빠르지만 처리량 손실.

퀀텀이 매우 클 때 (예: 1초)
 ├──────────────── 작업 ────────────────┼전환┤
 → 오버헤드는 무시할 수준이지만, 앞 작업이 끝날 때까지
   뒤 작업은 최대 1초를 기다린다. 사실상 FCFS.
```

전환 비용의 절대값은 CPU와 워크로드에 따라 달라지므로 위 숫자는 비율 감각을 잡기 위한 예시로만
본다. 중요한 것은 **퀀텀이 전환 비용에 가까워질수록 오버헤드 비율이 급격히 커진다**는 관계다.

정리하면 이런 관계다.

| 퀀텀 | 컨텍스트 스위칭 | 응답 시간 | 처리량 | 성격 |
|------|------------------|-----------|--------|------|
| 너무 작음 | 폭증 | 매우 좋음 | 나쁨 | 오버헤드가 지배 |
| 적정 | 적당 | 좋음 | 좋음 | 균형점 |
| 너무 큼 | 최소 | 나쁨 | 좋음 | FCFS에 수렴 |

경험칙은 **CPU 버스트 대부분이 퀀텀 안에 끝나도록** 잡는 것이다. 그러면 대다수 프로세스는 퀀텀을
다 쓰지 않고 I/O로 자진 양보하므로 강제 선점이 드물어진다. 강제로 잘리는 경우가 많다면 퀀텀이 짧다는
신호다.

또 하나 중요한 관점은 [03-context-switching.md](./03-context-switching.md)에서 다룬 **간접 비용**이다.
퀀텀을 줄이면 스위칭 횟수가 늘어나는데, 스위칭 한 번의 진짜 비용은 레지스터 저장이 아니라 캐시가
식는 것이다. 그래서 퀀텀을 절반으로 줄였을 때 오버헤드가 두 배가 아니라 그 이상으로 늘어날 수 있다.

MLFQ가 큐마다 퀀텀을 다르게 두는 이유도 여기 있다. 상위 큐(대화형)는 짧게 줘서 응답성을 확보하고,
하위 큐(CPU 집약)는 길게 줘서 스위칭 비용을 아낀다. 하나의 값으로 모두를 만족시킬 수 없으니 작업
성격별로 다른 값을 주는 것이다.

## 6. 성능 지표

무엇을 "좋다"고 할지 정하지 않으면 알고리즘을 비교할 수 없다.

| 지표 | 정의 | 방향 | 누가 신경 쓰나 |
|------|------|------|----------------|
| CPU 이용률 (Utilization) | CPU가 일한 시간 비율 | 높을수록 | 시스템 운영자 |
| 처리량 (Throughput) | 단위 시간당 완료 작업 수 | 높을수록 | 배치 시스템 |
| 반환 시간 (Turnaround) | 제출부터 완료까지 | 낮을수록 | 작업 제출자 |
| 대기 시간 (Waiting) | Ready 큐에서 기다린 총 시간 | 낮을수록 | 알고리즘 비교용 |
| 응답 시간 (Response) | 제출부터 **첫 반응**까지 | 낮을수록 | 대화형 사용자 |

반환 시간과 응답 시간의 구분이 중요하다. 편집기에서 키를 눌렀을 때 사용자가 체감하는 것은 응답
시간이지 반환 시간이 아니다. RR이 평균 대기 시간에서는 SJF에 지지만 대화형 환경에서 선택되는
이유가 이 지표의 차이다.

**그래서 무엇을 볼 것인가**: 배치·데이터 처리 시스템이면 처리량과 반환 시간, 사용자 대면 서비스면
응답 시간, 특히 평균이 아니라 p99 같은 꼬리 지연을 본다. 평균 응답 시간이 좋아도 100번에 한 번
몇 초씩 걸리면 사용자는 그 한 번을 기억한다.

## 7. 실무에서는

**리눅스 스케줄러**: 오랫동안 CFS(Completely Fair Scheduler)가 기본이었다. CFS는 고정 타임 퀀텀
대신 "각 프로세스가 지금까지 받은 CPU 시간(vruntime)"을 추적해 가장 적게 받은 쪽에게 CPU를 준다.
공정성을 시간 누적으로 정의한 접근이다. 커널 6.6에서 EEVDF(Earliest Eligible Virtual Deadline First)
스케줄러로 대체되면서 지연 시간 요구가 다른 작업들을 더 잘 다루도록 개선됐다. 두 스케줄러 모두
"고정 퀀텀 RR"과는 다른 계열이지만, 짧게 쓰고 양보하는 대화형 작업을 우대한다는 큰 방향은 같다.

**nice 값**: 리눅스에서 `nice -n 10 ./batch.sh`로 실행하면 그 프로세스의 우선순위가 낮아진다. 범위는
-20(가장 높음)부터 19(가장 낮음)이고, 음수 값을 주려면 관리자 권한이 필요하다. 백업이나 인덱싱처럼
"언제 끝나도 되지만 다른 작업을 방해하면 안 되는" 작업에 쓴다.

**cgroup을 통한 자원 제한**: 컨테이너 환경에서는 `cpu.max` 같은 설정으로 CPU 사용량 상한을 건다.
쿠버네티스의 CPU limit이 이 위에 올라가 있다. 여기서 흔히 겪는 문제가 CPU 스로틀링이다. limit에
닿으면 남은 주기 동안 아예 실행이 정지되므로, 평균 사용률은 낮은데 특정 요청만 수백 밀리초씩 튀는
현상이 생긴다. 평균 CPU 사용률만 보고 "여유 있다"고 판단하면 원인을 못 찾는다.

**애플리케이션 레벨 스케줄링**: 스레드 풀도 결국 스케줄러다. `ThreadPoolExecutor`에 어떤 큐를 주느냐가
정책을 결정한다. `LinkedBlockingQueue`는 FCFS이고, `PriorityBlockingQueue`를 쓰면 우선순위 스케줄링이
된다. 우선순위 큐를 쓸 때 낮은 우선순위 작업이 굶는 문제까지 OS와 똑같이 반복되므로, 에이징에 해당하는
장치를 직접 넣어야 한다.

## 8. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. 선점형과 비선점형 스케줄링의 차이는 무엇인가요?**

A. 비선점형은 프로세스가 CPU를 받으면 종료하거나 I/O를 기다리러 갈 때까지 계속 사용하고, 선점형은
OS가 실행 중인 프로세스에게서 CPU를 강제로 회수할 수 있습니다. 선점은 타이머 인터럽트로 커널이
주기적으로 제어권을 되찾기 때문에 가능합니다. 선점형은 응답성이 좋아 대화형 시스템에 적합하지만
컨텍스트 스위칭이 늘어나고, 공유 자원 접근 중에 끊길 수 있어 임계 구역 보호가 필수입니다.

- 꼬리 질문: "선점형에서 커널 자료구조는 어떻게 보호하나요?" → 임계 구역에서는 인터럽트를 잠시
  막거나 락을 사용한다. 최근 커널은 커널 코드 자체도 선점 가능하도록 설계돼 있어 락 사용이 필수다.

**Q. Round Robin의 타임 퀀텀은 어떻게 정하나요?**

A. 퀀텀이 너무 작으면 컨텍스트 스위칭 횟수가 늘어 오버헤드가 실제 작업 시간을 잠식하고, 너무 크면
앞선 작업이 끝날 때까지 뒤가 기다려야 해서 FCFS와 다를 바 없어집니다. 기준은 대부분의 CPU 버스트가
퀀텀 안에서 끝나도록 잡는 것입니다. 그러면 프로세스들이 강제로 잘리기 전에 I/O로 자진 양보하므로
불필요한 선점이 줄어듭니다. 강제 선점 비율이 높다면 퀀텀이 짧다는 신호로 해석합니다.

- 꼬리 질문: "MLFQ는 왜 큐마다 퀀텀이 다른가요?" → 대화형 작업은 짧은 퀀텀으로 응답성을 챙기고
  CPU 집약 작업은 긴 퀀텀으로 스위칭 비용을 아끼기 위해서다.

**Q. 기아 현상이 무엇이고 어떻게 해결하나요?**

A. 특정 프로세스가 계속 CPU를 배정받지 못해 무한정 대기하는 상태입니다. SJF나 우선순위 스케줄링처럼
특정 기준으로만 선택하는 알고리즘에서 발생하는데, 짧은 작업이나 높은 우선순위 작업이 계속 들어오면
반대편은 순서가 오지 않습니다. 해결책은 에이징으로, 대기 시간이 길어질수록 우선순위를 올려 유한
시간 안에 실행을 보장합니다. HRN은 이를 대기 시간과 서비스 시간의 비율 공식으로 표현한 알고리즘입니다.

- 꼬리 질문: "기아와 데드락의 차이는?" → 데드락은 서로의 자원을 기다리며 아무도 진행하지 못하는
  상태이고, 기아는 시스템은 정상 진행하는데 특정 대상만 순서가 오지 않는 상태다.

**Q. MLFQ가 실행 시간을 모르면서도 짧은 작업을 우대할 수 있는 이유는 무엇인가요?**

A. 미래를 예측하는 대신 과거 행동을 관찰하기 때문입니다. 모든 프로세스를 최상위 큐에서 시작시키고,
할당된 퀀텀을 다 쓰면 한 단계 아래로 내립니다. CPU를 오래 붙잡는 프로세스는 자연스럽게 하위 큐로
내려가고, 짧게 쓰고 I/O를 기다리러 가는 대화형 프로세스는 상위 큐에 남습니다. 여기에 주기적으로
모든 프로세스를 최상위로 올리는 에이징을 더해 하위 큐의 기아를 막습니다.

- 꼬리 질문: "규칙을 악용할 여지는 없나요?" → 퀀텀 만료 직전에 짧은 I/O를 넣어 강등을 피하는 꼼수가
  가능하다. 그래서 현대 구현은 한 번의 퀀텀이 아니라 큐에서 사용한 누적 CPU 시간으로 강등을 판단한다.

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-------------|
| "SJF가 가장 좋은 알고리즘" | 실행 시간을 알아야 하고 기아를 유발한다 | 평균 대기 시간만 최적일 뿐 실용성은 별개 |
| "응답 시간 = 반환 시간" | 응답은 첫 반응까지, 반환은 완료까지 | 대화형 시스템에서 중요한 것은 응답 시간 |
| "퀀텀을 줄이면 항상 빨라진다" | 스위칭 오버헤드가 늘어난다 | 응답성은 좋아지지만 처리량은 떨어진다 |
| "우선순위를 높이면 항상 빨리 끝난다" | I/O 대기 시간은 우선순위와 무관 | I/O 병목이면 우선순위를 올려도 소용없다 |
| "기아는 데드락의 일종" | 진행 가능성이 남아있다는 점에서 다르다 | 기아는 에이징으로, 데드락은 락 순서로 해결 |
| "컨테이너 CPU 사용률이 낮으면 여유롭다" | limit 스로틀링은 평균에 안 잡힌다 | 스로틀 발생 횟수를 별도로 확인해야 한다 |

현대 OS는 관찰 기반의 다단계 피드백 구조와 에이징으로 세 목표를 절충한다.
