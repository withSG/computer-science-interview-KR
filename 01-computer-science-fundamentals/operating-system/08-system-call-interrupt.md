# 시스템 콜과 인터럽트 (System Call & Interrupt)

> 사용자 프로그램이 파일 하나를 읽을 때 CPU 안에서 무슨 일이 벌어지는지 — 모드가 어떻게 바뀌고, 인터럽트가 어떻게 끼어들고, DMA가 어디를 대신하는지 — 를 설명할 수 있게 된다.

## 학습 목표

- [ ] 이중 모드(User/Kernel)가 왜 필요한지 설명할 수 있다
- [ ] 시스템 콜의 동작 절차와 비용을 설명할 수 있다
- [ ] 하드웨어 인터럽트와 소프트웨어 인터럽트를 구분할 수 있다
- [ ] 인터럽트 처리 과정을 단계별로 설명할 수 있다
- [ ] 폴링과 인터럽트의 트레이드오프, DMA의 역할을 설명할 수 있다

## 1. 왜 필요한가

프로그램이 디스크에 직접 명령을 내릴 수 있다고 상상해 보자. 버그 하나가 파일 시스템 전체를 날리고,
악성 프로그램은 다른 프로세스의 메모리를 마음대로 읽는다. 실제로 초기 개인용 컴퓨터가 그랬다.

해결책은 **권한을 나누는 것**이다. 위험한 작업(I/O 명령, 페이지 테이블 변경, 인터럽트 설정)은 신뢰할
수 있는 코드, 즉 커널만 할 수 있게 한다. 그런데 여기서 딜레마가 생긴다. 응용 프로그램도 파일은
읽어야 한다. 금지하면 아무것도 못 하고, 허용하면 보호가 무너진다.

답은 **"직접 하지 말고 부탁하게 하는 것"** 이다. 응용 프로그램은 "이 파일을 읽어 주세요"라고 요청만
하고 실제 작업은 커널이 대신 하되, 커널은 요청이 정당한지 검사한 뒤에만 수행한다. 이 요청 창구가
**시스템 콜**이다. 그리고 이 창구를 안전하게 만들려면 하드웨어의 도움이 필요하다. CPU에 "지금 어떤
권한 수준인가"를 나타내는 비트를 두고, 그 비트를 바꾸는 것 자체를 커널만 할 수 있게 해야 한다.
이것이 **이중 모드**다.

**비유**: 은행 창구다. 고객은 금고에 직접 들어갈 수 없고 출금 신청서를 낸다. 직원이 신분과 잔액을
확인한 뒤 대신 꺼내 준다. 고객이 금고 문을 직접 열 수 있다면 은행은 성립하지 않는다.

**비유의 한계**: 은행 직원은 별도의 사람이지만, 시스템 콜을 처리하는 동안 커널 코드를 실행하는 것은
**요청한 그 스레드 자신**이다. 같은 스레드가 권한만 올려서 계속 실행하므로, 시스템 콜과 컨텍스트
스위칭은 별개 개념이다.

## 2. 이중 모드 (Dual Mode)

### 모드 비트

CPU 안에 모드를 나타내는 비트가 있다. x86에서는 특권 레벨(ring 0~3)로 구현되며, 실질적으로 커널이
ring 0, 사용자 프로그램이 ring 3을 쓴다.

```
┌───────────────────────────────────────────────────────┐
│  사용자 모드 (User Mode, ring 3)                       │
│   할 수 있는 것: 일반 연산, 자기 주소 공간 읽고 쓰기      │
│   할 수 없는 것: I/O 명령, 페이지 테이블 변경,           │
│                 인터럽트 마스킹, 다른 프로세스 메모리 접근 │
└───────────────────────┬───────────────────────────────┘
      시스템 콜 / 인터럽트 / 예외  ▲  처리 완료 후 복귀
                        ▼        │
┌───────────────────────┴───────────────────────────────┐
│  커널 모드 (Kernel Mode, ring 0)                       │
│   모든 명령어 실행 가능, 전체 물리 메모리 접근 가능       │
└───────────────────────────────────────────────────────┘
```

핵심은 **사용자 모드에서 커널 모드로 가는 경로가 정해진 몇 개뿐**이라는 점이다. 임의의 커널 주소로
점프할 수 없고 반드시 미리 등록된 진입점을 통해서만 들어간다. 이 제약이 없으면 이중 모드는 무의미하다.

### 특권 명령어

커널 모드에서만 실행 가능한 명령어들이다. 사용자 모드에서 시도하면 CPU가 예외를 발생시킨다.

| 종류 | 예 | 허용하면 생기는 일 |
|------|-----|--------------------|
| I/O 명령 | 디스크 컨트롤러 레지스터 직접 조작 | 남의 파일을 마음대로 읽고 쓴다 |
| 메모리 관리 | 페이지 테이블 베이스 레지스터 변경 | 다른 프로세스 메모리에 접근한다 |
| 인터럽트 제어 | 인터럽트 비활성화 | CPU를 영원히 붙잡아 시스템을 정지시킨다 |
| 모드 전환 | 모드 비트 직접 변경 | 이중 모드 자체가 무력화된다 |

### 왜 이 구분이 성능 이야기로 이어지는가

모드를 오가는 데에는 비용이 든다. 레지스터를 저장하고, 커널 스택으로 갈아타고, 돌아올 때 되돌려야
한다. 여기에 최근 CPU 취약점(Meltdown, Spectre) 대응으로 커널과 사용자 페이지 테이블을 분리하는
완화책이 들어가면서 전환 비용이 더 커졌다. 그래서 "시스템 콜을 적게 부르는 것"이 실제 최적화 기법이
된다. 뒤에서 다룰 버퍼링, `sendfile`, `io_uring`이 모두 이 방향이다.

## 3. 시스템 콜 (System Call)

### 동작 절차

사용자 코드에서 `read()`를 부르면 실제로는 이런 일이 일어난다.

```
[사용자 모드]
 1. 애플리케이션이 라이브러리 함수 호출
        FileInputStream.read()  →  libc의 read()
 2. libc가 시스템 콜 번호를 레지스터에 넣고
    인자(파일 디스크립터, 버퍼 주소, 길이)도 레지스터에 배치
 3. 트랩 명령어 실행 (x86-64 리눅스에서는 syscall 명령어)
        │
════════╪══════════════════════════════════════════ 모드 경계
        ▼
[커널 모드]
 4. CPU가 자동으로 모드 비트를 커널로 바꾸고
    미리 등록된 진입점으로 점프, 사용자 컨텍스트 저장
 5. 시스템 콜 번호로 시스템 콜 테이블을 조회해 핸들러 결정
 6. 인자 검증
      - 파일 디스크립터가 이 프로세스의 것이 맞는가
      - 버퍼 주소가 이 프로세스의 유효한 쓰기 가능 영역인가
      ※ 검증을 건너뛰면 커널 임의 메모리 덮어쓰기 취약점이 된다
 7. 실제 작업 수행
      - 페이지 캐시에 있으면 즉시 복사하고 반환
      - 없으면 디스크 I/O 요청 후 이 스레드를 Waiting 상태로
        (여기서 비로소 컨텍스트 스위칭 발생)
 8. 반환값을 레지스터에 넣고 사용자 컨텍스트 복원
        │
════════╪══════════════════════════════════════════
        ▼
[사용자 모드]
 9. libc가 반환값을 확인하고 필요시 errno 설정 후 호출자에게 리턴
```

7번 단계가 중요하다. **모든 시스템 콜이 컨텍스트 스위칭을 유발하는 것은 아니다.** 데이터가 이미 페이지
캐시에 있으면 커널 모드에 잠깐 들렀다 바로 돌아오고, 실제로 블로킹이 필요할 때만 스케줄러가 개입한다.

### 시스템 콜 분류

| 분류 | 예시 (POSIX) | 하는 일 |
|------|--------------|---------|
| 프로세스 제어 | `fork`, `execve`, `exit`, `waitpid` | 프로세스 생성·교체·종료 |
| 파일 관리 | `open`, `read`, `write`, `close` | 파일 열고 읽고 쓰기 |
| 장치 관리 | `ioctl`, `mmap` | 장치 제어, 메모리 매핑 |
| 정보 유지 | `getpid`, `clock_gettime` | 시스템·프로세스 정보 조회 |
| 통신 | `pipe`, `socket`, `sendto`, `recvfrom` | IPC와 네트워크 |

### 함수 호출과 무엇이 다른가

| 구분 | 일반 함수 호출 | 시스템 콜 |
|------|----------------|-----------|
| 모드 | 사용자 모드 유지 | 커널 모드로 전환 |
| 진입 방식 | 주소로 직접 점프 | 트랩 명령어 + 번호로 간접 진입 |
| 인자 전달 | 스택 또는 레지스터 | 레지스터 (규약 고정) |
| 검증 | 없음 | 커널이 모든 인자를 검증 |
| 비용 | 수 나노초 | 수백 나노초 이상 |

같은 `printf()`라도 문자열을 내부 버퍼에 모으는 동안은 일반 함수 호출이고, 버퍼가 차서 실제로 `write`
시스템 콜을 부르는 순간에만 커널로 넘어간다. 표준 라이브러리의 버퍼링이 곧 시스템 콜 절감 최적화다.

### 시스템 콜 비용을 줄이는 실제 기법

**vDSO**: `clock_gettime` 같은 일부 호출은 커널에 갈 필요가 없다. 커널이 시간 정보가 담긴 페이지를
사용자 공간에 읽기 전용으로 매핑해 두면 라이브러리가 그 메모리를 읽는 것만으로 답이 나와, 모드 전환이
아예 사라진다.

**배치 처리**: 1바이트씩 1000번 쓰는 대신 1000바이트를 한 번에 쓰면 시스템 콜이 1000분의 1이 된다.
버퍼드 I/O가 존재하는 이유다.

**`sendfile`**: 파일을 읽어 소켓으로 보내는 패턴은 원래 커널→사용자→커널로 두 번 복사하고 시스템 콜도
두 번 부른다. `sendfile`은 커널 안에서 바로 옮겨 복사와 호출을 함께 줄인다.

**`epoll` / `io_uring`**: 연결 수천 개를 각각 확인하면 시스템 콜이 수천 번이다. `epoll`은 준비된
것만 한 번에 알려주고, `io_uring`은 요청과 완료를 공유 링 버퍼로 주고받아 호출 자체를 크게 줄인다.

### 디버깅

```bash
# 프로세스가 어떤 시스템 콜을 얼마나 부르는지 본다
strace -c -p <PID>

# 특정 시스템 콜만 추적
strace -e trace=openat,read ./myprogram
```

CPU 사용률에서 `sy`(시스템) 비중이 높다면 시스템 콜이 과도한 것이고, `strace -c`의 호출 횟수 순위가
곧 개선 지점이 된다.

## 4. 인터럽트 (Interrupt)

### 정의

바깥에서 무슨 일이 벌어졌을 때 CPU의 어깨를 두드려 하던 일을 잠시 내려놓게 만드는 신호다. 인터럽트가
없다면 OS가 키보드 입력이나 디스크 완료를 알아채는 방법은 끊임없이 되묻는 것뿐이다.

### 종류

| 구분 | 발생 원인 | 예 | 동기/비동기 |
|------|-----------|-----|-------------|
| 하드웨어 인터럽트 | 외부 장치가 신호를 보냄 | 키보드 입력, 타이머 만료, 네트워크 패킷 도착, 디스크 I/O 완료 | 비동기 (언제든 발생) |
| 소프트웨어 인터럽트 (트랩) | 실행 중인 명령어가 유발 | 시스템 콜, 0으로 나누기, 페이지 폴트, 잘못된 메모리 접근 | 동기 (특정 명령어에서 발생) |

용어가 자료마다 조금씩 다르지만 이 구분만 잡으면 된다. **하드웨어 인터럽트는 지금 실행 중인 코드와
무관하게 밖에서 들어오고, 트랩은 지금 실행 중인 그 명령어 때문에 발생한다.** 그래서 트랩은 재현
가능하고 하드웨어 인터럽트는 타이밍에 따라 달라진다.

트랩은 다시 시스템 콜처럼 **의도한** 것과 0으로 나누기처럼 **사고**인 것(예외)으로 나뉜다. 페이지
폴트는 사고처럼 보이지만 커널이 처리한 뒤 정상 재개되는 특이한 경우로, 자세한 과정은
[05-virtual-memory.md](./05-virtual-memory.md)에 있다.

### 처리 과정

```
CPU: 명령어 실행 중
      │
      │  ◄──── 장치가 인터럽트 신호 발생
      ▼
1. 현재 명령어를 끝까지 완료  ← 명령어 도중에 끊지 않는다
      │
      ▼
2. PC와 상태 레지스터를 저장, 커널 모드 진입
      │
      ▼
3. 인터럽트 번호로 인터럽트 벡터 테이블 조회
      (x86에서는 IDT: Interrupt Descriptor Table)
      │
      ▼
4. ISR(Interrupt Service Routine) 실행
      - 같은 종류의 인터럽트는 잠시 막아둔다
      - 최소한의 일만 하고 빨리 끝낸다
      │
      ▼
5. 인터럽트 처리 완료를 컨트롤러에 알림
      │
      ▼
6. 저장했던 상태 복원, 원래 모드로 복귀
      │
      ▼
7. 중단됐던 지점부터 실행 재개
   (단, 스케줄러가 개입해 다른 프로세스가 선택될 수도 있다)
```

1번이 중요하다. 명령어 중간에 끊으면 반쪽만 적용된 상태가 남는다. 그래서 CPU는 **명령어 경계**에서만
인터럽트를 받는다.

### 왜 ISR은 짧아야 하는가

ISR이 도는 동안 같은 종류의 인터럽트는 막혀 있다. 여기서 오래 머물면 그동안 도착한 신호를 놓치고,
다른 모든 작업도 지연된다. 그래서 리눅스는 인터럽트 처리를 둘로 나눈다.

```
장치 인터럽트 발생
      ▼
┌──────────────────────────────────────┐
│ 상반부 (top half) — ISR              │
│  - 인터럽트를 받았다고 장치에 응답      │
│  - 데이터를 커널 버퍼로 옮기는 등 최소 작업 │
│  - "나머지 일은 나중에" 예약           │
│  → 매우 짧게, 인터럽트 막힌 상태        │
└──────────────┬───────────────────────┘
               ▼
┌──────────────────────────────────────────────────┐
│ 하반부 (bottom half) — softirq/tasklet/workqueue │
│  - 프로토콜 처리, 상위 계층 전달 등 무거운 작업     │
│  → 인터럽트가 열린 상태에서 처리                  │
└──────────────────────────────────────────────────┘
```

네트워크 카드를 예로 들면 상반부는 "패킷이 도착했다"는 사실만 기록하고 즉시 빠지고, TCP/IP 헤더를
파싱해 소켓 버퍼에 넣는 작업은 하반부가 한다. 이 분리 덕분에 초당 수십만 패킷이 들어와도 버틴다.

---

## 5. 폴링 vs 인터럽트

### 두 방식

**폴링(Polling)** 은 CPU가 주기적으로 장치에 "준비됐니?"를 묻는 방식이다. **인터럽트**는 장치가
준비되면 알려주는 방식이다.

```
폴링
  CPU: 준비됐니? → 아니
  CPU: 준비됐니? → 아니
  CPU: 준비됐니? → 아니        ← 묻는 동안 다른 일을 못 한다
  CPU: 준비됐니? → 응! 데이터 받기

인터럽트
  CPU: (다른 작업 수행 중)
  CPU: (다른 작업 수행 중)
  장치: 준비됐어!  ──인터럽트──► CPU: 하던 일 저장하고 처리
  CPU: (하던 작업 재개)
```

### 비교

| 구분 | 폴링 | 인터럽트 |
|------|------|----------|
| CPU 낭비 | 대기 중 계속 소모 | 사건이 없으면 0 |
| 지연 시간 | 폴링 주기만큼 늦을 수 있음 | 즉시 |
| 사건이 잦을 때 | 유리 (오버헤드가 상수) | 불리 (처리 비용이 사건 수에 비례) |
| 사건이 드물 때 | 불리 | 유리 |
| 구현 복잡도 | 단순 | 벡터 테이블·핸들러 필요 |

**그래서 언제 뭘 쓰나**: 사건이 드물면 인터럽트, 사건이 폭발적으로 잦으면 폴링. 직관과 반대라
헷갈리기 쉬운데, 인터럽트 한 번의 처리 비용이 고정이므로 초당 수십만 번 발생하면 그 비용만으로
CPU가 마비된다. 이것을 **인터럽트 폭풍(interrupt storm)** 이라 부른다.

리눅스 네트워크 드라이버의 NAPI가 실제 해법이다. 평소에는 인터럽트로 대기하다가 패킷이 쏟아지면
인터럽트를 끄고 폴링 모드로 전환해 한꺼번에 처리하고, 트래픽이 잦아들면 다시 인터럽트로 돌아간다.
**둘 중 하나를 고르는 게 아니라 상황에 따라 갈아타는 것**이 실제 답이다. 애플리케이션 층에서도 같은
판단이 반복된다. 이벤트가 드물면 웹훅, 데이터가 끊임없이 흐르면 배치 폴링이 낫다.

## 6. DMA (Direct Memory Access)

### 왜 필요한가

DMA가 없던 시절 방식(PIO, Programmed I/O)에서는 CPU가 데이터를 한 덩어리씩 장치에서 읽어 메모리에
옮기는 일을 직접 했다. 계산할 줄 아는 CPU에게 짐 나르는 일을 시킨 셈이다. DMA 컨트롤러는 이 복사만
전담하는 별도 하드웨어이고, CPU는 "어디서 어디로 얼마나"만 지시하고 다른 일을 하러 간다.

```
PIO 방식
  ┌────────┐  ① 읽기  ┌─────┐  ② 쓰기  ┌────────┐
  │ 디스크  │ ───────► │ CPU │ ───────► │ 메모리  │
  └────────┘          └─────┘          └────────┘
   모든 바이트가 CPU 레지스터를 한 번씩 거쳐 간다

DMA 방식
  ┌─────┐  1. "이만큼 옮겨줘"   ┌──────────┐
  │ CPU │ ────────────────────►│ DMA 컨트롤러│
  │     │                      └─────┬─────┘
  │     │                            │ 2. 직접 전송
  │     │  4. 완료 인터럽트           ▼
  │     │ ◄───────────────  ┌────────┐    ┌────────┐
  └─────┘                   │ 디스크  │───►│ 메모리  │
   3. CPU는 그동안 다른 작업   └────────┘    └────────┘
```

### 동작 절차

1. CPU가 DMA 컨트롤러에 소스 주소, 목적지 주소, 전송 크기를 설정한다
2. DMA 컨트롤러가 버스 제어권을 확보한다
3. 데이터 블록을 CPU 개입 없이 전송한다
4. 전송이 끝나면 인터럽트로 CPU에 알린다

### 알아둘 두 가지

**버스 사이클 훔치기(cycle stealing)**: DMA가 전송하는 동안 메모리 버스를 쓰므로 CPU도 같은 순간 메모리에
접근하려 하면 잠시 양보해야 한다. "CPU가 완전히 자유롭다"기보다 "명령어 실행은 계속하되 메모리 접근에서
약간 경쟁한다"가 정확한 표현이다.

**캐시 일관성**: DMA는 CPU 캐시를 거치지 않고 메모리에 직접 쓴다. CPU 캐시에 그 영역의 옛 데이터가
남아 있으면 CPU는 낡은 값을 읽게 되므로, 드라이버는 DMA 전후로 캐시를 무효화하거나 비워야 한다.
"CPU를 건너뛴다"는 성질이 그대로 위험 요소가 되는 지점이다.

이 개념의 연장선에 **zero-copy** 가 있다. `sendfile`이 빠른 이유는 시스템 콜을 줄일 뿐 아니라 데이터가
사용자 공간을 경유하지 않고 DMA로 직접 오가기 때문이다. Kafka의 성능 근거로 자주 언급된다.

## 7. 실무에서는

**시스템 콜 횟수가 성능을 가른다**: 로그를 한 줄씩 `flush`하면 줄마다 `write` 시스템 콜이 나간다.
버퍼링을 켜면 호출이 크게 줄지만, 프로세스가 비정상 종료하면 버퍼에 남은 로그가 사라지므로 장애
분석에 필요한 로그는 즉시 내보내는 절충이 필요하다.

**컨테이너 보안과 시스템 콜**: Docker의 기본 seccomp 프로파일은 위험한 시스템 콜을 차단한다. 컨테이너가
호스트 커널을 공유하는 구조라 시스템 콜이 사실상 공격 표면 전체이기 때문이다. 특정 기능이 컨테이너
안에서만 안 되는 문제는 대개 여기서 비롯된다.

**인터럽트 분산**: 특정 코어에만 네트워크 인터럽트가 몰리면 그 코어가 포화된다. `/proc/interrupts`로
분포를 확인하고 IRQ 친화도를 조정해 여러 코어로 분산한다.

**타이머 인터럽트와 스케줄링**: 선점형 스케줄링은 타이머 인터럽트가 있어야 성립한다. 다만 인터럽트가
잦으면 그 자체가 오버헤드이고 절전에도 불리해서, 최근 커널은 할 일이 없으면 주기적 틱을 멈추는
tickless(NO_HZ) 모드를 지원한다. 이 인터럽트 위에서 스케줄러가 무엇을 판단하는지는
[06-cpu-scheduling.md](./06-cpu-scheduling.md)에서 다룬다.

## 8. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. 사용자 모드와 커널 모드는 왜 나누나요?**

A. 보호와 안정성 때문입니다. I/O 명령이나 페이지 테이블 변경 같은 특권 명령을 아무 프로그램이나
실행할 수 있으면 버그 하나로 시스템 전체가 무너지고 다른 프로세스의 메모리도 마음대로 읽을 수
있습니다. 그래서 CPU에 모드 비트를 두고 특권 명령은 커널 모드에서만 허용하며, 커널 모드로 들어가는
경로는 커널이 미리 등록해 둔 진입점으로만 제한합니다. 응용 프로그램은 직접 하지 않고 커널에 요청하며
커널은 정당성을 검사한 뒤 대신 수행합니다.

- 꼬리 질문: "그럼 모드 전환 비용은 어느 정도인가요?" → 레지스터 저장·복원과 스택 전환이 필요해
  일반 함수 호출보다 훨씬 비싸고, 최근에는 CPU 취약점 완화책 때문에 더 커졌다.

**Q. 시스템 콜이 호출되면 어떤 일이 일어나나요?**

A. 라이브러리 함수가 시스템 콜 번호와 인자를 레지스터에 배치하고 트랩 명령어를 실행합니다. CPU가
모드를 커널로 바꾸고 미리 등록된 진입점으로 점프하면, 커널이 번호로 핸들러를 찾고 인자를 검증합니다.
파일 디스크립터가 이 프로세스 것인지, 버퍼 주소가 유효한지 확인하는 단계인데, 이 검증이 없으면 커널
메모리를 임의로 덮어쓰는 취약점이 됩니다. 이후 실제 작업을 수행하고 반환값을 레지스터에 넣은 뒤
사용자 모드로 복귀합니다.

- 꼬리 질문: "시스템 콜은 항상 컨텍스트 스위칭을 유발하나요?" → 아니다. 데이터가 페이지 캐시에
  있으면 커널에 잠깐 들렀다 바로 돌아온다. 실제로 블로킹될 때만 스케줄러가 개입한다.

**Q. 폴링과 인터럽트는 각각 언제 유리한가요?**

A. 사건이 드물면 인터럽트가 유리합니다. 사건이 없을 때 CPU를 전혀 쓰지 않기 때문입니다. 반대로
사건이 매우 잦으면 폴링이 유리한데, 인터럽트는 한 번 처리할 때마다 컨텍스트 저장과 핸들러 진입 비용이
고정으로 들어서 초당 수십만 번 발생하면 그 비용만으로 CPU가 마비되는 인터럽트 폭풍이 생기기 때문입니다.
리눅스의 NAPI는 평소 인터럽트로 있다가 트래픽이 몰리면 폴링으로 전환해 두 장점을 모두 취합니다.

- 꼬리 질문: "인터럽트 핸들러는 왜 짧아야 하나요?" → 실행 중에는 같은 종류의 인터럽트가 막혀 있어
  신호를 놓칠 수 있다. 그래서 상반부는 최소한만 하고 무거운 일은 하반부로 미룬다.

**Q. DMA가 없으면 어떤 문제가 생기나요?**

A. CPU가 장치와 메모리 사이의 모든 데이터 복사를 직접 수행해야 합니다. 대용량 파일 하나를 읽는 데
CPU가 단순 복사만 수백, 수천 번 반복하게 되어 다른 작업을 전혀 못 합니다. DMA 컨트롤러가 있으면 CPU는
소스·목적지·크기만 지정하고 다른 일을 하다가 완료 인터럽트만 받으면 됩니다. 다만 DMA는 CPU 캐시를
거치지 않아 낡은 캐시 데이터를 무효화해야 하고, 전송 중에는 메모리 버스를 두고 CPU와 경쟁합니다.

- 꼬리 질문: "zero-copy와 어떤 관계인가요?" → `sendfile` 같은 zero-copy는 데이터가 사용자 공간을
  경유하지 않고 DMA로 직접 오가게 해서 복사 횟수와 시스템 콜을 함께 줄인다.

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-------------|
| "시스템 콜 = 컨텍스트 스위칭" | 시스템 콜은 모드 전환이다 | 블로킹될 때만 실행 주체가 바뀐다 |
| "인터럽트는 모두 하드웨어에서 온다" | 시스템 콜·예외는 소프트웨어 트랩 | 발생 주체로 하드웨어/소프트웨어를 나눈다 |
| "인터럽트가 폴링보다 항상 낫다" | 사건이 잦으면 인터럽트 폭풍이 난다 | 발생 빈도에 따라 선택하거나 전환한다 |
| "DMA를 쓰면 CPU가 완전히 자유롭다" | 메모리 버스를 두고 경쟁한다 | 명령어 실행은 계속하되 메모리 접근에서 양보한다 |

## 한 줄 정리

이중 모드는 위험한 작업을 커널에만 허용하는 하드웨어 장치이고, 시스템 콜과 인터럽트는 그 벽을 넘는
유일하게 허가된 두 통로이며, DMA와 하반부 처리는 그 통로를 지나는 비용을 줄이기 위한 장치다.
