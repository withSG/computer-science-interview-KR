## 1. 왜 필요한가 — 평문 회선의 세 가지 위협

내 노트북에서 서버까지 데이터는 공유기, ISP 장비, 해저 케이블, 여러 라우터를 거친다.
이 경로 위 어디에서든 세 가지 일이 가능하다.

- **도청(Eavesdropping)** — 지나가는 패킷을 그대로 읽는다. 로그인 비밀번호가 그냥 보인다.
- **변조(Tampering)** — 응답 HTML에 광고 스크립트를 끼워 넣는다. 상대는 알아채지 못한다.
- **위장(Impersonation)** — 중간에서 "내가 그 서버다"라며 응답한다. 중간자 공격(MITM)이다.

TLS(Transport Layer Security)는 셋을 각각 **기밀성 · 무결성 · 인증**으로 막는다.
SSL은 TLS의 전신인 옛 이름인데, SSL 3.0까지 나온 뒤 TLS로 이름이 바뀌었다.
지금 "SSL 인증서"라 부르는 것도 실제로는 TLS를 쓴다.

여기서 중요한 건 **인증이 없으면 암호화도 무의미하다**는 점이다.
공격자와 안전하게 암호화된 통신을 하는 건 아무 의미가 없기 때문이다.
그래서 TLS의 절반은 "이 서버가 진짜 그 도메인의 주인인가"를 증명하는 데 쓰인다.

## 2. 대칭키와 비대칭키, 왜 둘 다 쓰나

| 구분 | 대칭키 (AES 등) | 비대칭키 (RSA, ECDSA 등) |
|------|----------------|-------------------------|
| 키 구성 | 하나의 키로 암·복호화 | 공개키 / 개인키 쌍 |
| 속도 | 매우 빠름 (하드웨어 가속 지원) | 수백~수천 배 느림 |
| 핵심 문제 | 첫 키를 어떻게 안전하게 나눠 갖나 | 느려서 대량 데이터에 못 씀 |
| TLS에서의 역할 | 실제 데이터 암호화 | 키 합의와 신원 증명 |

정확히 서로의 약점을 상대가 메운다. 그래서 TLS는 **핸드셰이크에서만 비대칭 연산을 쓰고,
그 결과로 대칭키를 만든 뒤 실제 데이터는 전부 대칭키로 암호화**한다.
수백 MB 파일을 RSA로 암호화하면 실용성이 없지만, 32바이트짜리 키 합의에만 쓰면 부담이 없다.

> **비유** — 무거운 금고(대칭키 암호화)는 아주 튼튼하지만 열쇠를 상대에게 전달할 방법이 없다.
> 그래서 상대가 보낸 "누구나 잠글 수 있지만 자기만 열 수 있는 작은 상자"(공개키)에 열쇠를 넣어 보낸다.
>
> **비유의 한계** — 현대 TLS는 실제로 열쇠를 "보내지" 않는다. 바로 아래에서 설명할 ECDHE 방식은
> 양쪽이 각자 정보를 교환한 뒤 **각자 계산해서 같은 값에 도달**한다. 키 자체는 회선을 지나가지 않는다.

### 키 교환 방식이 바뀐 이유 — 전방 비밀성

예전 RSA 키 교환은 클라이언트가 만든 비밀값을 서버 공개키로 암호화해 보내는 방식이었다.
문제는 **서버 개인키가 나중에 유출되면**, 공격자가 몇 년 전에 저장해 둔 트래픽까지
전부 소급해서 복호화할 수 있다는 것이다.

**ECDHE(Elliptic Curve Diffie-Hellman Ephemeral)** 는 매 연결마다 **임시(ephemeral) 키 쌍**을 만들고
핸드셰이크가 끝나면 버린다. 서버의 장기 개인키는 "내가 그 서버다"를 서명하는 데만 쓰이고
키 합의에는 관여하지 않는다. 그래서 개인키가 유출돼도 **과거 세션은 복호화되지 않는다.**
이것이 **전방 비밀성(Forward Secrecy)** 이고, TLS 1.3은 아예 이 방식만 허용한다.

## 3. TLS 1.2 핸드셰이크

```
Client                                              Server
  │                                                    │
  │  (TCP 3-way 핸드셰이크가 이미 끝난 상태)             │
  │                                                    │
  │ ── ClientHello ──────────────────────────────────► │  ┐
  │    · 지원 TLS 버전                                  │  │
  │    · Cipher Suite 목록                              │  │ 1 RTT
  │    · 클라이언트 랜덤                                 │  │
  │    · SNI(접속하려는 도메인) ← 평문                   │  │
  │                                                    │  │
  │ ◄── ServerHello ────────────────────────────────── │  │
  │    · 선택한 버전 / Cipher Suite                     │  │
  │    · 서버 랜덤                                       │  │
  │ ◄── Certificate (인증서 체인)                       │  │
  │ ◄── ServerKeyExchange (ECDHE 공개값 + 서명)         │  │
  │ ◄── ServerHelloDone                                │  ┘
  │                                                    │
  │  [인증서 검증: 서명 · 유효기간 · 도메인 · 폐기 여부]   │
  │                                                    │
  │ ── ClientKeyExchange (ECDHE 공개값) ──────────────► │  ┐
  │ ── ChangeCipherSpec ─────────────────────────────► │  │ 2 RTT
  │ ── Finished (암호화됨) ──────────────────────────► │  │
  │                                                    │  │
  │ ◄── ChangeCipherSpec ───────────────────────────── │  │
  │ ◄── Finished (암호화됨) ───────────────────────────│  ┘
  │                                                    │
  │ ◄══════ 이후 대칭키로 암호화된 통신 ══════════════► │
```

### 단계별로 무슨 일이 일어나는가

**ClientHello** — "나는 TLS 1.2와 1.3을 지원하고, 이런 암호 알고리즘들을 쓸 수 있다"는 목록을 보낸다.
여기에 클라이언트 랜덤 값과 SNI가 함께 들어간다.

**ServerHello + Certificate** — 서버가 목록 중 하나를 고르고, 자기 인증서를 보낸다.
인증서에는 도메인 이름, 서버의 공개키, CA의 서명이 들어 있다.

**인증서 검증** — 클라이언트가 하는 일이 네 가지다.
① CA 서명이 유효한가(체인을 따라 신뢰하는 루트까지 올라가며 확인), ② 유효기간이 지나지 않았나,
③ 인증서의 도메인이 내가 접속하려는 도메인과 일치하나, ④ 폐기되지 않았나.
하나라도 실패하면 브라우저가 경고를 띄운다.

**키 합의** — 양쪽이 ECDHE 공개값을 교환한다. 각자 자기 개인값과 상대 공개값으로 계산하면
**같은 Pre-Master Secret**이 나온다. 여기에 클라이언트 랜덤 + 서버 랜덤을 섞어 마스터 시크릿을 만들고,
거기서 실제 암호화/무결성 키들을 파생시킨다. 랜덤 값을 섞는 이유는 매 연결마다 다른 키가 나오게 하기 위해서다.

**Finished** — 지금까지 주고받은 모든 메시지의 해시를 새 키로 암호화해 보낸다.
상대가 이걸 제대로 풀어 검증하면, 중간에 누가 메시지를 조작하지 않았다는 것까지 확인된다.

핸드셰이크에만 **2 RTT**가 든다. TCP 핸드셰이크 1 RTT까지 합치면 데이터 한 바이트 보내기 전에 3 RTT다.
왕복 100ms 회선이면 0.3초를 그냥 쓴다.

### Cipher Suite 읽는 법

```
TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
     ─┬── ─┬─      ─────┬───── ──┬───
      │    │            │        └─ 해시: SHA-256 (키 파생·무결성)
      │    │            └────────── 대칭 암호: AES 128비트 GCM 모드
      │    └─────────────────────── 인증: RSA 서명으로 서버 신원 증명
      └──────────────────────────── 키 교환: ECDHE (전방 비밀성 O)
```

## 4. TLS 1.3 — 한 왕복 줄이고, 위험한 선택지를 없앴다

TLS 1.3의 설계 방향은 두 가지다. **더 빠르게**, 그리고 **잘못 고를 여지를 없애기**.

```
Client                                              Server
  │ ── ClientHello ──────────────────────────────────► │  ┐
  │    · Cipher Suite 목록                              │  │
  │    · key_share ← 서버가 고를 것 같은 곡선의          │  │ 1 RTT
  │      ECDHE 공개값을 미리 넣어 보낸다                 │  │
  │    · SNI                                           │  │
  │                                                    │  │
  │ ◄── ServerHello (key_share) ──────────────────────  │  │
  │ ◄── {EncryptedExtensions}                          │  │  ← 여기부터
  │ ◄── {Certificate}                                  │  │    이미 암호화
  │ ◄── {CertificateVerify}                            │  │
  │ ◄── {Finished}                                     │  ┘
  │                                                    │
  │ ── {Finished} ───────────────────────────────────► │
  │ ══════ 암호화 통신 (클라이언트는 Finished와 함께      │
  │        바로 데이터를 실어 보낼 수 있다) ═══════════► │
```

핵심 변화:

- **1-RTT 핸드셰이크** — 클라이언트가 "서버가 어떤 키 교환 방식을 고를지" 추측해 첫 메시지에 ECDHE 공개값을 미리 넣는다. 추측이 맞으면 왕복 한 번으로 끝난다. 틀리면 HelloRetryRequest로 한 번 더 왕복한다.
- **인증서도 암호화된다** — TLS 1.2에서는 인증서가 평문으로 오갔지만 1.3에서는 ServerHello 직후부터 암호화된다. 어떤 사이트에 접속했는지 알아내기가 더 어려워진다.
- **취약한 선택지 제거** — RSA 키 교환(전방 비밀성 없음), 정적 DH, CBC 모드, RC4, SHA-1, 압축, 재협상이 전부 빠졌다. "설정을 잘못해서 취약해지는" 경우 자체를 줄인 것이다.
- **Cipher Suite 표기 단순화** — 키 교환·인증이 분리되어 `TLS_AES_128_GCM_SHA256`처럼 대칭 암호와 해시만 남았다.

| 항목 | TLS 1.2 | TLS 1.3 |
|------|---------|---------|
| 핸드셰이크 왕복 | 2-RTT | 1-RTT (재개 시 0-RTT) |
| 키 교환 | RSA / DHE / ECDHE 중 선택 | (EC)DHE만 |
| 전방 비밀성 | 설정에 따라 다름 | 항상 보장 |
| 인증서 전송 | 평문 | 암호화 |
| 지원 암호 알고리즘 | 수십 종 (약한 것 포함) | 소수의 AEAD만 |

**그래서 뭘 쓰나** — 새 서비스는 TLS 1.3을 기본으로 켜고 1.2를 호환용으로 남긴다.
1.0/1.1은 주요 브라우저가 이미 지원을 중단했다.

## 5. 인증서 체인과 CA

브라우저가 세상 모든 서버의 공개키를 알 수는 없다.
그래서 **신뢰할 수 있는 제3자(CA, Certificate Authority)** 가 "이 공개키는 이 도메인 주인의 것이 맞다"고 서명해 준다.

```
┌──────────────────────────────────────┐
│ 루트 CA 인증서 (self-signed)          │  ← OS/브라우저에 미리 내장되어 있다
│  주체: Example Root CA                │     (신뢰 저장소, Trust Store)
│  서명: 자기 자신                       │
└────────────────┬─────────────────────┘
                 │ 서명
                 ▼
┌──────────────────────────────────────┐
│ 중간 CA 인증서                        │  ← 서버가 함께 보내줘야 한다
│  주체: Example Intermediate CA        │
│  서명: 루트 CA의 개인키                │
└────────────────┬─────────────────────┘
                 │ 서명
                 ▼
┌──────────────────────────────────────┐
│ 서버 인증서 (leaf)                    │  ← 서버가 보낸다
│  주체(SAN): www.example.com           │
│  공개키: (서버의 공개키)               │
│  유효기간: 2026-01-01 ~ 2026-04-01    │
│  서명: 중간 CA의 개인키                │
└──────────────────────────────────────┘
```

검증은 **아래에서 위로** 올라간다. 서버 인증서의 서명을 중간 CA 공개키로 검증하고,
중간 CA 인증서의 서명을 루트 CA 공개키로 검증하고, 루트 CA가 내 신뢰 저장소에 있으면 통과다.
루트에 도달하지 못하면 실패한다.

**중간 CA를 두는 이유**는 루트 개인키를 보호하기 위해서다.
루트 개인키는 오프라인 금고에 두고 거의 꺼내지 않는다. 유출되면 그 루트를 신뢰하는
전 세계 모든 브라우저를 업데이트해야 하는 재앙이기 때문이다.
중간 CA는 유출돼도 그것만 폐기하면 된다.

실무에서 흔한 사고가 **중간 인증서 누락**이다. 서버가 leaf만 보내면
클라이언트가 체인을 이어 붙일 수 없어 검증에 실패한다. 브라우저는 캐시된 중간 인증서로
어찌어찌 통과하는데 모바일 앱이나 서버 간 통신에서만 실패하는 식으로 나타나 원인 찾기가 까다롭다.

### 인증서 검증 항목

| 검증 항목 | 실패하면 |
|-----------|---------|
| 서명 유효성 (체인이 신뢰 루트까지 닿는가) | 신뢰할 수 없는 발급자 오류 |
| 유효기간 | 만료 오류. 갱신 자동화를 안 해두면 반드시 겪는다 |
| 도메인 일치 (SAN 필드) | 도메인 불일치 오류 |
| 폐기 여부 (CRL / OCSP) | 폐기된 인증서 오류 |

과거에는 CN(Common Name) 필드에 도메인을 적었지만, 현재 브라우저는 **SAN(Subject Alternative Name)** 만 본다.
SAN 하나에 여러 도메인을 넣을 수 있어 멀티 도메인 인증서가 가능하다.

**OCSP Stapling** — 폐기 여부를 클라이언트가 CA에 직접 물으면 지연이 생기고
"누가 어떤 사이트에 접속하는지"가 CA에 노출된다. 그래서 서버가 미리 CA에서 받아둔
서명된 응답을 핸드셰이크에 끼워(staple) 보내는 방식을 쓴다.

## 6. SNI — 한 IP에 여러 도메인이 있을 때

IPv4 주소가 부족해 하나의 IP에 수십, 수백 개 사이트가 올라간다.
HTTP라면 `Host` 헤더로 구분하면 되는데, **문제는 TLS 핸드셰이크가 HTTP보다 먼저 일어난다**는 것이다.
서버는 인증서를 보내야 하는데, 어느 도메인의 인증서를 보내야 할지 알 방법이 없다.

**SNI(Server Name Indication)** 는 ClientHello에 "나는 www.example.com에 접속하려 한다"를
확장 필드로 실어 보내 이 문제를 푼다. 서버는 그걸 보고 해당 도메인 인증서를 고른다.

```
[SNI 없이]                         [SNI 사용]
Client: (TLS 시작)                  Client: ClientHello
Server: 어떤 인증서를? 알 수 없음     └ server_name = shop.example.com
        → IP당 도메인 하나만 가능     Server: shop.example.com용 인증서 선택
```

주의할 점은 **SNI가 평문**이라는 것이다. TLS 1.3에서 인증서까지 암호화됐지만
SNI는 여전히 첫 메시지에 그대로 실린다. 암호화 자체가 시작되기 전이라 어쩔 수 없다.
그래서 중간에서 "이 사용자가 어느 도메인에 접속했는지"는 관측 가능하다.
이를 가리려는 **ECH(Encrypted Client Hello)** 가 표준화 막바지에 있고 일부 브라우저·CDN이 지원을 시작했지만,
양쪽이 모두 지원해야 동작하는 데다 아직 기본값으로 켜져 있지 않은 곳이 많다.

이것이 [02-http-https.md](./02-http-https.md)에서 "HTTPS가 접속 사실은 숨기지 못한다"고 한 이유다.

## 7. 세션 재개 — 매번 전체 핸드셰이크를 할 순 없다

한 페이지를 여는 데 여러 연결이 필요하고, 사용자는 같은 사이트를 계속 드나든다.
매번 인증서 검증과 키 합의를 처음부터 하면 낭비다.

| 방식 | 어디에 상태를 두나 | 특징 |
|------|-------------------|------|
| Session ID (TLS 1.2) | **서버**가 세션 정보를 보관, 클라이언트는 ID만 | 서버 메모리 소비. 서버가 여러 대면 공유가 필요 |
| Session Ticket (TLS 1.2) | **클라이언트**가 암호화된 티켓을 보관 | 서버 무상태로 운영 가능. 티켓 암호화 키 관리가 관건 |
| PSK (TLS 1.3) | 이전 세션에서 파생한 사전 공유 키 | 위 둘을 하나로 통합. `NewSessionTicket`으로 발급 |

TLS 1.3의 **0-RTT(Early Data)** 는 재개 시 클라이언트가 첫 메시지에 아예 애플리케이션 데이터를
실어 보내는 기능이다. 왕복 대기 없이 요청이 나가니 체감 속도가 크게 좋아진다.

하지만 **재전송 공격(Replay Attack)에 취약하다.**
0-RTT 데이터는 서버가 아직 살아 있는 세션인지 확인하기 전에 도착하므로,
공격자가 그 패킷을 복사해 여러 번 보내면 서버가 같은 요청을 여러 번 처리할 수 있다.
그래서 **0-RTT에는 멱등한 요청만 실어야 한다.** GET은 괜찮지만 "결제하기" POST를 여기 실으면 안 된다.
멱등성 개념은 [02-http-https.md](./02-http-https.md)의 3절과 이어진다.

## 8. 직접 확인하기

```bash
# 핸드셰이크 전 과정과 인증서 체인 출력
openssl s_client -connect example.com:443 -servername example.com

# 체인만 보기
openssl s_client -connect example.com:443 -servername example.com -showcerts

# 협상된 프로토콜 버전과 Cipher Suite만 확인
curl -v https://example.com 2>&1 | findstr /i "SSL TLS"   # Windows
curl -v https://example.com 2>&1 | grep -i "SSL\|TLS"      # Linux/macOS

# 특정 버전 강제 — 서버가 어디까지 지원하는지 확인할 때
openssl s_client -connect example.com:443 -servername example.com -tls1_2
openssl s_client -connect example.com:443 -servername example.com -tls1_3

# 인증서 만료일 확인
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates -subject
```

`-servername` 옵션이 바로 SNI다. OpenSSL 1.1.1부터는 `-connect`에 적은 호스트명이 자동으로 SNI에 실리고
`-noservername`으로 끌 수 있지만, IP로 직접 접속하거나 SNI만 다른 값으로 바꿔 시험할 때는 명시해야 한다.
SNI 없이 접속하면 서버가 기본 인증서를 주기 때문에 "인증서가 왜 다른 도메인 거지?" 하고 헷갈리게 된다.

출력에서 볼 것: `Protocol` 과 `Cipher` 줄에서 협상 결과, `Verify return code: 0 (ok)` 면 체인 검증 성공,
`Certificate chain` 아래 `s:`(주체)와 `i:`(발급자)가 사슬처럼 이어지는지 확인한다.

## 9. 실무에서는

- **인증서 자동 갱신** — Let's Encrypt는 무료 인증서를 발급하는 대신 유효기간이 90일로 짧다. 짧은 만큼 자동 갱신이 전제이고, certbot 같은 클라이언트가 주기적으로 갱신한다. 인증서 만료 장애는 여전히 흔한 사고이므로 만료 모니터링을 반드시 걸어둔다.
- **TLS 종료(Termination)** — 로드밸런서나 리버스 프록시에서 TLS를 풀고 내부는 평문 HTTP로 보내는 구성이 일반적이다. 인증서 관리 지점이 하나로 모이고 백엔드 CPU 부담이 줄어든다. 다만 내부망도 못 믿는 환경이라면 백엔드까지 TLS를 유지한다(종단 간 암호화).
- **mTLS(상호 TLS)** — 서버뿐 아니라 클라이언트도 인증서를 제시해 서로를 검증한다. 서비스 메시나 사내 시스템 간 통신에서 쓰인다.
- **HSTS** — `Strict-Transport-Security` 헤더로 "이 도메인은 앞으로 무조건 HTTPS"를 브라우저에 각인시킨다. http로 시작하는 첫 요청이 가로채이는 틈을 막는다.
- **인증서 유형** — DV(도메인 소유만 확인), OV(조직 실재 확인), EV(가장 엄격) 세 등급이 있다. 암호학적 강도는 동일하고 검증 절차만 다르다. 브라우저가 EV를 특별 표시하던 UI를 없앤 뒤로는 DV가 사실상 표준이 됐다.

## 10. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. HTTPS에서 대칭키와 비대칭키를 함께 쓰는 이유는 뭔가요?**

A. 서로의 약점을 보완하기 때문이다. 대칭키는 빠르지만 첫 키를 안전하게 나눠 가질 방법이 없고,
비대칭키는 키 교환이 안전하지만 느려서 대량 데이터에 못 쓴다.
그래서 핸드셰이크에서만 비대칭 연산으로 세션 키를 합의하고, 이후 실제 데이터는 대칭키로 암호화한다.
- 꼬리 질문: "요즘은 키를 전달하지 않는다던데요?" → 맞다. 현대 TLS는 ECDHE로 양쪽이 공개값만 교환하고 각자 같은 값을 계산해낸다. 세션 키 자체는 회선을 지나가지 않으며, 이 덕분에 전방 비밀성이 확보된다.

**Q. TLS 핸드셰이크 과정을 설명해 주세요.**

A. TCP 연결 후 ClientHello로 지원 버전·Cipher Suite·랜덤 값·SNI를 보내면,
서버가 ServerHello로 선택 결과와 자기 랜덤 값, 그리고 인증서를 보낸다.
클라이언트는 인증서의 CA 서명·유효기간·도메인 일치·폐기 여부를 검증하고,
ECDHE 공개값을 교환해 양쪽이 같은 세션 키를 도출한다. 마지막으로 Finished 메시지를 주고받아
지금까지 오간 메시지가 변조되지 않았음을 확인하고 암호화 통신을 시작한다.
- 꼬리 질문: "TLS 1.3은 뭐가 달라졌나요?" → 클라이언트가 첫 메시지에 키 공유값을 미리 넣어 1-RTT로 줄였고, 인증서도 암호화되며, RSA 키 교환이나 CBC 같은 취약한 선택지를 아예 제거해 전방 비밀성이 항상 보장된다.

**Q. 인증서 체인이 뭔가요? 왜 중간 CA가 필요하죠?**

A. 서버 인증서는 중간 CA가, 중간 CA 인증서는 루트 CA가 서명하는 사슬 구조다.
클라이언트는 아래에서 위로 서명을 검증해 OS/브라우저에 내장된 신뢰 루트에 닿으면 통과시킨다.
중간 CA를 두는 이유는 루트 개인키를 오프라인에 격리해 보호하기 위해서다.
중간 CA 키가 유출되면 그것만 폐기하면 되지만, 루트가 뚫리면 전 세계 브라우저를 갱신해야 한다.
- 꼬리 질문: "체인 문제로 겪을 수 있는 장애는?" → 서버가 중간 인증서를 함께 보내지 않으면 클라이언트가 체인을 잇지 못해 검증에 실패한다. 브라우저는 캐시된 중간 인증서로 통과해도 모바일이나 서버 간 통신에서만 실패하는 형태로 나타난다.

**Q. SNI는 왜 필요하고 어떤 한계가 있나요?**

A. 하나의 IP에 여러 도메인이 올라가 있을 때 서버가 어느 인증서를 보낼지 정해야 하는데,
TLS 핸드셰이크는 HTTP `Host` 헤더보다 먼저 일어나 알 방법이 없다.
SNI는 ClientHello에 접속 도메인을 실어 이 문제를 해결한다.
한계는 SNI가 평문이라는 점이다. 암호화 이전 단계라 어쩔 수 없고, 그래서 접속 도메인은 관측 가능하다.
- 꼬리 질문: "그럼 HTTPS를 써도 어디 접속했는지 다 보이나요?" → 내용은 보호되지만 목적지 IP와 SNI 도메인은 드러난다. 이를 가리려는 ECH 표준화가 진행 중이다.

**Q. TLS 1.3의 0-RTT는 왜 위험한가요?**

A. 재개 시 첫 메시지에 애플리케이션 데이터를 실어 보내는 기능인데,
서버가 세션의 신선도를 확인하기 전에 데이터가 처리되므로 공격자가 그 패킷을 복사해
여러 번 재전송할 수 있다. 그래서 0-RTT에는 멱등한 요청만 실어야 하고,
결제 같은 상태 변경 요청은 정상적인 1-RTT 경로로 보내야 한다.
- 꼬리 질문: "그럼 0-RTT를 끄는 게 낫나요?" → 정적 콘텐츠 전달처럼 GET이 대부분인 서비스에서는 이득이 크다. 서버가 비멱등 요청을 0-RTT로 받지 않도록 처리할 수 있으면 켜도 된다.

## 자주 하는 실수

| 실수 | 왜 틀렸나 | 올바른 이해 |
|------|----------|-----------|
| "서버 공개키로 세션 키를 암호화해 보낸다" | 현대 TLS의 기본 방식이 아니다 | ECDHE로 양쪽이 각자 계산해 같은 값에 도달한다. RSA 키 교환은 TLS 1.3에서 제거됐다 |
| "HTTPS면 어디 접속했는지도 숨겨진다" | SNI와 목적지 IP는 노출된다 | 내용은 보호되지만 접속 대상은 대체로 드러난다 |
| "인증서가 데이터를 암호화한다" | 인증서는 신원 증명 수단이다 | 인증서는 공개키가 그 도메인 것임을 CA가 보증하는 문서다. 암호화는 세션 키가 한다 |
| "SSL과 TLS는 다른 것" | SSL은 TLS의 옛 이름이다 | 지금 쓰이는 건 전부 TLS다. "SSL 인증서"는 관용 표현 |
| 중간 인증서를 서버에 안 올림 | 클라이언트가 체인을 못 잇는다 | leaf + 중간 인증서를 함께 제공해야 한다 |
| "EV 인증서가 더 안전하다" | 암호 강도는 동일하다 | 조직 실재 확인 절차만 엄격할 뿐, 보안 수준 차이는 없다 |
| 0-RTT에 결제 요청을 실음 | 재전송 공격에 노출된다 | 0-RTT는 멱등 요청 전용 |

## 한 줄 정리

TLS는 CA 서명으로 상대가 진짜임을 확인한 뒤, 회선에 흘리지 않은 채 양쪽이 같은 대칭키를 계산해내고,
그 키로 나머지 대화를 전부 암호화하는 절차다.
