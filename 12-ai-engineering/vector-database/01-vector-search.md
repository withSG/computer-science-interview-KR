## 1. 왜 필요한가

문서 검색을 만든다고 해보자. 처음 떠오르는 건 `LIKE '%환불%'`이다. 그런데 사용자는 이렇게 검색한다.

```
사용자 질문: "돈 돌려받으려면 어떻게 해요?"
문서 제목:   "구매 취소 및 대금 반환 절차"

공통 단어: 없음
LIKE 검색 결과: 0건
```

사람은 두 문장이 같은 이야기라는 걸 안다. 컴퓨터는 글자만 본다. 형태소 분석과 동의어 사전으로 어느 정도 메울 수 있지만, 동의어 사전은 사람이 계속 관리해야 하고 "돈 돌려받다"와 "대금 반환" 같은 표현 변형까지 다 담을 수는 없다.

**의미가 비슷한 것을 찾으려면, 의미를 비교 가능한 형태로 바꿔야 한다.** 그 형태가 벡터다.

## 2. 임베딩: 의미를 좌표로

### 정의

임베딩(Embedding)은 텍스트를 **고정 길이 실수 배열**로 바꾸는 것이다. 핵심은 아무 배열이나가 아니라, **의미가 비슷한 텍스트가 가까운 좌표에 놓이도록** 훈련된 모델이 만든 배열이라는 점이다.

```
"돈 돌려받으려면 어떻게 해요?"  → [ 0.21, -0.08,  0.55, ... ]  (예: 1024개)
"구매 취소 및 대금 반환 절차"    → [ 0.19, -0.11,  0.52, ... ]  ← 가깝다
"신규 회원 가입 이벤트 안내"     → [-0.42,  0.33, -0.07, ... ]  ← 멀다
```

### 비유: 지도 위의 도시

지도에서 서울과 인천은 가깝고 서울과 부산은 멀다. 두 도시의 "가까움"이 위도·경도라는 두 숫자만으로 표현되듯이, 임베딩은 문장의 "의미적 가까움"을 수백~수천 개 숫자로 표현한다. 검색은 "내 위치에서 가장 가까운 도시 10곳 찾기"와 같은 문제가 된다.

> **비유의 한계**: 지도의 축은 위도와 경도라는 뜻이 있지만, 임베딩의 각 차원에는 사람이 읽을 수 있는 의미가 없다. "3번째 숫자는 긍정도" 같은 해석은 불가능하다. 또 지도는 2차원이지만 임베딩은 수백 차원이라, 우리 직관과 다르게 동작하는 지점들이 생긴다.

### 흔한 오해와 실전 함정

**"임베딩 모델은 아무거나 써도 된다."** 아니다. 세 가지가 걸린다.

1. **인덱싱과 질의에 같은 모델을 써야 한다.** 모델마다 벡터 공간이 다르다. 다른 모델로 만든 벡터끼리 거리를 재면 숫자는 나오지만 아무 의미가 없다. 모델을 바꾸려면 **전체 문서를 다시 임베딩**해야 하므로, 초기 선택이 생각보다 무거운 결정이다.
2. **한국어 성능이 모델마다 크게 다르다.** 영어 벤치마크가 좋아도 한국어에서 형편없는 모델이 있다. 실제 서비스 질문 샘플로 직접 재보는 것 외에 방법이 없다.
3. **질의용과 문서용 접두사를 요구하는 모델이 있다.** 일부 임베딩 모델은 질문에는 `query: `, 문서에는 `passage: ` 같은 접두사를 붙여 학습됐다. 이걸 빼먹으면 성능이 눈에 띄게 떨어진다. 모델 카드를 반드시 확인해야 한다.

**"임베딩은 의미를 완벽히 담는다."** 아니다. 임베딩은 문장 전체를 하나의 벡터로 압축하므로 세부가 뭉개진다. 특히 **부정문, 숫자, 고유명사**에 약하다. "환불 가능"과 "환불 불가"의 벡터가 상당히 가까울 수 있다. 이것이 [RAG 문서](../rag-pipeline/01-rag-pipeline.md)에서 하이브리드 검색이 필요한 이유다.

## 3. 유사도를 재는 세 가지 방법

### 무엇이 다른가

```
        내적(Dot Product)              코사인(Cosine)              L2 거리(Euclidean)
      크기 × 크기 × cos θ                  cos θ                    두 점 사이 직선거리

           B                              B                          B
          ↗                              ↗                          ↗
         /                              /                          /·
        /  θ                           /  θ                       /   ·
       O───────▶ A                    O───────▶ A                O─────·──▶ A
                                                                        └ 이 길이

     길이가 길수록 큰 값             각도만 본다                 좌표 차이 그대로
     → 긴 문서가 유리해질 수 있음    → 문서 길이에 중립          → 크기 차이에 민감
```

| 측정 | 범위 | 크기 영향 | 주로 쓰는 곳 |
|------|------|----------|------------|
| 코사인 유사도 | -1 ~ 1 (클수록 유사) | 무시 | 텍스트 임베딩의 사실상 기본값 |
| 내적 | -∞ ~ ∞ (클수록 유사) | 반영 | 정규화된 벡터, 추천에서 인기도를 크기로 인코딩할 때 |
| L2 거리 | 0 ~ ∞ (작을수록 유사) | 반영 | 이미지 임베딩 등 절대 거리가 의미 있는 경우 |

> 표 요약: **텍스트라면 코사인으로 시작한다.** 문서 길이가 유사도에 영향을 주면 안 되기 때문이다.

### 정규화하면 셋이 하나가 된다

이게 면접에서 자주 나오는 포인트다. 벡터를 L2 정규화(길이를 1로 만드는 것)하면 세 측정이 서로 단조 관계가 된다.

```python
import numpy as np

def l2_normalize(v):
    return v / np.linalg.norm(v)

a, b = l2_normalize(np.random.randn(768)), l2_normalize(np.random.randn(768))

cos = float(a @ b)                    # 정규화했으므로 내적 == 코사인
l2  = float(np.linalg.norm(a - b))

print(cos, l2)
print(np.isclose(l2 ** 2, 2 - 2 * cos))   # True — L2와 코사인이 직접 연결된다
```

정규화된 벡터에서는 `‖a-b‖² = 2 - 2·(a·b)`가 성립한다. 코사인이 클수록 L2 거리가 작다. **즉 순위가 완전히 같다.** 그래서 정규화만 되어 있으면 내적으로 계산해도 코사인과 결과가 같고, 나눗셈이 빠지니 더 빠르다. 많은 벡터 DB가 내적 인덱스를 권하는 이유다.

### 안티패턴: 정규화하지 않고 내적 쓰기

```python
# 안티패턴
index = faiss.IndexFlatIP(768)   # 내적 인덱스
index.add(raw_embeddings)        # 정규화 안 한 원본 벡터
```

**왜 문제인가**: 내적은 벡터 길이에 비례한다. 임베딩 모델이 길이를 1로 맞춰주지 않는다면 **내용과 무관하게 벡터가 긴 문서가 상위를 차지하는 편향이 생긴다.** 검색 결과에 특정 문서만 계속 나오는데 이유를 못 찾는 전형적인 상황이 이것이다.

```python
# 개선 — 정규화 후 내적 = 코사인
faiss.normalize_L2(raw_embeddings)   # 제자리에서 정규화 (float32 2차원 배열이어야 한다)
index = faiss.IndexFlatIP(768)
index.add(raw_embeddings)

# 질의 벡터도 같은 경로로 정규화한다 (점수를 코사인 값으로 읽으려면 필요)
faiss.normalize_L2(query_vec)
D, I = index.search(query_vec, k=5)
```

정규화가 필요한 쪽이 문서와 질의 중 어디인지는 구분해서 알아두는 편이 좋다. **망가지는 것은 문서 벡터를 정규화하지 않았을 때다.** 반대로 문서가 전부 정규화돼 있으면 질의 벡터를 빼먹어도 순위 자체는 바뀌지 않는다. 모든 문서 점수에 `‖q‖`라는 같은 상수가 곱해질 뿐이기 때문이다. 대신 점수의 절대값이 달라지므로 "유사도 0.8 이상만 채택" 같은 **임계값 기준이 통째로 어긋난다.** 임계값을 쓰지 않는 시스템에서는 증상이 안 보이다가, 나중에 컷오프를 도입하는 순간 원인 모를 문제가 된다.

## 4. 완전 탐색의 한계와 ANN

### 계산량

가장 정직한 방법은 쿼리 벡터와 모든 벡터의 거리를 재는 것이다(brute force, 완전 탐색). 결과는 100% 정확하다. 문제는 비용이다.

```
벡터 1,000만 개 × 1,024 차원

거리 계산 1회 = 곱셈·덧셈 약 1,024회
전체 1회 검색 = 1,000만 × 1,024 ≈ 100억 회 연산

초당 100건의 검색 요청이 들어온다면?
→ 초당 1조 회. 이 규모에서는 감당할 방법이 없다
```

메모리도 만만치 않다. 1,024차원 float32 벡터 하나가 4KB다. 1,000만 개면 벡터 데이터만 40GB다.

### ANN의 발상

ANN(Approximate Nearest Neighbor, 근사 최근접 이웃)의 아이디어는 단순하다. **정확한 1등을 보장하지 않는 대신, 거의 확실히 상위권인 것들을 훨씬 빠르게 찾는다.** 전부 비교하는 대신 인덱스 구조로 후보 수천 개만 추리고 그 안에서만 정밀 비교하므로 수백~수천 배 빨라진다.

여기서 핵심 지표가 **재현율(Recall)**이다. "완전 탐색이 찾아냈을 진짜 Top-K 중 몇 개를 ANN이 찾아냈는가"의 비율이다. Recall 0.95는 진짜 10개 중 9~10개를 맞혔다는 뜻이다.

**RAG에서 이 정도 손실은 대개 문제가 되지 않는다.** 어차피 검색 결과를 리랭커가 다시 정렬하고 LLM이 읽으므로, 10등이 11등과 바뀌는 것은 최종 답변에 거의 영향이 없다. 반대로 중복 탐지나 정확 매칭이 목적이라면 손실이 치명적일 수 있다. **무엇을 위한 검색인가에 따라 허용 Recall이 달라진다.**

## 5. HNSW: 그래프를 타고 이동한다

### 동작 원리

HNSW(Hierarchical Navigable Small World)는 벡터들을 **서로 연결한 그래프**를 만들고, 그 위를 걸어서 목적지에 접근한다. 여기에 계층을 얹어 처음엔 성큼성큼, 나중엔 촘촘히 움직인다.

```
Layer 2 (희소)   [A]───────────────────[H]        먼 거리 점프
                  │                     │
Layer 1          [A]──────[D]──────────[H]        중간 이동
                  │        │            │
Layer 0 (전체)   [A][B][C][D][E][F][G][H]         이웃끼리만 연결
                  ↑                              모든 벡터가 여기 있다

검색 과정:
1. 최상위 레이어 진입점에서 시작
2. 이웃 중 쿼리에 더 가까운 노드로 이동, 더 가까운 이웃이 없으면 아래 레이어로
3. Layer 0에서 정밀 탐색 → Top-K 반환
```

비유하자면 **고속도로 → 국도 → 골목길** 순으로 내려가는 것과 같다. 전국을 다 훑지 않고 고속도로로 대략 근처까지 간 다음 좁혀 들어간다.

### 파라미터

| 파라미터 | 시점 | 올리면 | 내리면 |
|---------|------|--------|--------|
| `M` | 인덱스 구축 | 노드당 연결 수 증가 → Recall 상승, **메모리 증가** | 메모리 절약, Recall 하락 |
| `ef_construction` | 인덱스 구축 | 그래프 품질 향상 → Recall 상승, **빌드 시간 증가** | 빌드 빠름, 그래프 품질 하락 |
| `ef_search` | 검색 | 탐색 후보 폭 증가 → Recall 상승, **검색 느려짐** | 검색 빠름, Recall 하락 |

가장 중요한 실무 포인트는 **`ef_search`만 런타임에 바꿀 수 있다**는 것이다. `M`과 `ef_construction`을 바꾸려면 인덱스를 다시 만들어야 한다. 그래서 튜닝은 이렇게 한다.

```
1. M, ef_construction은 무난한 기본값으로 인덱스를 만든다
2. ef_search를 올려가며 Recall과 지연을 측정한다
3. 목표 Recall을 만족하는 최소 ef_search를 고른다
4. 그래도 Recall이 부족하면 그때 M을 올려 재구축한다
```

### 특징

- **장점**: 같은 Recall 기준에서 가장 빠른 편에 속한다. 데이터를 하나씩 추가하기 쉽다
- **단점**: 그래프 전체를 메모리에 올려야 해서 메모리를 많이 쓴다. 벡터 데이터에 더해 연결 정보 저장 공간이 추가로 필요하다
- 삭제가 까다롭다. 대부분 구현이 즉시 제거가 아니라 표시만 해두고(soft delete) 나중에 정리하므로, 삭제가 잦으면 인덱스가 비대해진다

## 6. IVF: 구역을 나눠 일부만 본다

### 동작 원리

IVF(Inverted File Index)는 벡터 공간을 **미리 구역으로 나눠두고, 쿼리가 속한 구역 몇 개만 검색**한다.

```
구축: k-means로 전체 벡터를 nlist개 클러스터로 나눈다

     C1 ●●●        C2 ●●
      ▲            ●●●●
     ●●●                    C3 ●●●●
                             ●●●
        C4 ●●●
        ●●●●●●     ▲ = centroid(대표점)

검색 (nprobe=2):
  1. 쿼리와 가장 가까운 centroid 2개를 고른다 → C2, C3
  2. C2와 C3에 속한 벡터들만 비교한다
  3. C1, C4는 아예 보지 않는다 → 여기가 절약되는 부분
```

### 클러스터 경계 문제

IVF의 근본적인 약점이 여기 있다.

```
        C2 구역        │        C3 구역
                       │
              ●정답    │  ★쿼리
                       │
                    경계선

쿼리는 C3에 속한다고 판정됐다.
그런데 진짜 정답은 경계 바로 건너편 C2에 있다.
nprobe=1이면 C2를 아예 안 보므로 정답을 영원히 못 찾는다.
```

이걸 완화하는 손잡이가 `nprobe`다. 여러 구역을 함께 보면 경계에 걸친 정답을 찾을 확률이 오른다. 대신 본 만큼 느려진다.

| 파라미터 | 시점 | 역할 |
|---------|------|------|
| `nlist` | 구축 | 클러스터 개수. 많을수록 구역이 잘게 나뉘어 한 구역이 작아진다(빠름). 대신 경계 문제가 심해진다 |
| `nprobe` | **검색** | 탐색할 구역 수. 올리면 Recall 상승, 속도 하락. `nprobe = nlist`면 완전 탐색과 같아진다 |

HNSW의 `ef_search`처럼 **`nprobe`도 런타임 조절이 가능**하다. Recall과 지연을 맞바꾸는 손잡이가 각 알고리즘마다 하나씩 있다고 기억하면 된다.

### PQ를 얹으면

IVF-PQ는 여기에 곱 양자화(Product Quantization)를 더해 **벡터 자체를 압축**한다. 1,024차원 벡터를 여러 조각으로 나누고 각 조각을 코드북의 번호로 대체하면, 원본보다 훨씬 적은 바이트로 표현된다. 메모리를 극적으로 줄이는 대신 벡터가 근사값이 되므로 정확도가 떨어진다. 수억~수십억 규모에서 메모리가 병목일 때 선택한다.

### 비교

| | Flat (완전 탐색) | HNSW | IVF | IVF-PQ |
|---|---|---|---|---|
| Recall | 100% | 매우 높음 | 중~높음 (nprobe 의존) | 중간 |
| 검색 속도 | 느림 | 매우 빠름 | 빠름 | 매우 빠름 |
| 메모리 | 벡터 크기만큼 | 벡터 + 그래프 (가장 큼) | 벡터 + 소량 | 압축되어 가장 작음 |
| 빌드 시간 | 없음 | 김 | 중간 (k-means 학습 필요) | 중간 |
| 런타임 튜닝 | 해당 없음 | `ef_search` | `nprobe` | `nprobe` |
| 적합 규모 | ~수만 | 수만 ~ 수천만 | 수백만 ~ 수억 | 수억 이상 |

> 표 요약: **수만 건이면 Flat으로 충분하고 정확하다. 대부분의 서비스 규모에서는 HNSW가 기본 선택이며, 메모리가 병목이 되기 시작하면 IVF 계열로 넘어간다.** 처음부터 IVF-PQ를 고르는 것은 대개 시기상조다.

## 7. 메타데이터 필터링의 함정

실무 검색에는 거의 항상 조건이 붙는다. "이 사용자가 접근 가능한 문서 중에서", "2024년 이후 문서 중에서". 문제는 **필터와 ANN 인덱스가 서로 잘 맞지 않는다**는 것이다.

```
Post-filtering (검색 먼저, 필터 나중)

  전체 100만 ──[ANN Top-10]──▶ 10개 ──[필터]──▶ 1개
                                              ↑
                          9개가 필터에서 탈락 → 결과가 텅 빈다


Pre-filtering (필터 먼저, 검색 나중)

  전체 100만 ──[필터]──▶ 5,000개 ──[검색]──▶ 10개
                            ↑
              ANN 인덱스는 100만 개 기준으로 만들어졌다.
              5,000개 부분집합 안에서 그래프를 타면 길이 끊겨
              엉뚱한 곳에 갇히거나, 결국 5,000개를 다 비교하게 된다
```

### 안티패턴

```python
# 안티패턴 — top_k만큼 뽑아서 애플리케이션에서 필터링
results = index.query(vector=q, top_k=10)
visible = [r for r in results if r.metadata["owner"] == user_id]
# 사용자가 소유한 문서가 전체의 1%라면, 10개 중 평균 0.1개만 남는다
# 대부분의 요청에서 결과가 0건이 되고, 사용자는 "검색이 안 된다"고 느낀다
```

**왜 문제인가**: ANN은 필터를 모른 채 전체에서 가장 가까운 10개를 골랐다. 그 10개가 우연히 필터를 통과할 확률은 필터의 선택도에 비례한다. 조건이 빡빡할수록 결과가 비는데, **에러가 나는 게 아니라 조용히 빈 결과가 나오므로** 문제를 인지하기까지 오래 걸린다.

```python
# 개선 1 — 벡터 DB의 필터 기능을 사용한다 (엔진이 내부적으로 최적화한다)
results = index.query(
    vector=q,
    top_k=10,
    filter={"owner": {"$eq": user_id}, "year": {"$gte": 2024}},
)

# 개선 2 — 엔진 필터를 못 쓰는 상황이면 과다 조회 후 필터링하고, 부족하면 확장한다
def search_with_filter(q, need=10, factor=10, max_k=1000):
    k, hits = need * factor, []
    while k <= max_k:
        hits = [r for r in raw_search(q, top_k=k) if passes(r)]
        if len(hits) >= need:
            return hits[:need]
        k *= 4          # 부족하면 후보를 넓혀 다시 시도
    return hits         # 상한까지 갔는데도 부족하면 있는 만큼 반환
```

### 선택 기준

| 필터 선택도 | 권장 | 이유 |
|-----------|------|------|
| 느슨함 (대부분 통과, 예: 언어=ko) | Post-filtering | ANN 인덱스를 온전히 쓰면서 결과도 충분히 남는다 |
| 매우 빡빡함 (1% 미만 통과, 예: 특정 사용자 소유) | Pre-filtering 또는 파티셔닝 | ANN을 돌려봐야 대부분 탈락한다. 아예 후보를 좁혀 완전 탐색이 나을 수 있다 |
| 중간 | 엔진의 필터링 기능에 위임 | 최신 벡터 DB는 그래프 탐색 중 필터를 함께 평가하는 방식을 지원한다 |

**권한 필터는 특히 조심해야 한다.** 선택도가 극단적으로 높은 데다, 잘못되면 다른 사람 문서가 노출되는 보안 사고다. 테넌트나 사용자 그룹별로 인덱스(또는 네임스페이스)를 아예 분리하는 편이 성능과 안전 양쪽에서 낫다.

## 8. 벡터 DB 선택 기준

제품별 우열이 아니라 **어느 축에서 결정되는가**를 아는 것이 중요하다.

| 축 | 질문 | 영향 |
|----|------|------|
| 규모 | 벡터가 수만인가 수억인가 | 수만이면 전용 DB 없이 pgvector나 라이브러리로 충분하다 |
| 운영 | 인프라를 직접 운영할 사람이 있나 | 없으면 관리형(SaaS). 있으면 오픈소스로 비용 절감 |
| 기존 스택 | 이미 PostgreSQL을 쓰나 | 쓴다면 pgvector가 트랜잭션·조인·백업을 그대로 재사용 |
| 필터링 | 복잡한 메타데이터 조건이 자주 쓰이나 | 필터링 최적화가 강한 엔진이 유리 |
| 갱신 빈도 | 문서가 계속 바뀌나 | 삽입·삭제 성능과 인덱스 재구축 비용을 확인 |

가장 흔한 실수는 **규모 대비 과한 도입**이다. 문서 수만 건이면 인덱스 없이 완전 탐색으로도 밀리초 단위로 끝난다. 그 단계에서는 청킹과 임베딩 모델 같은 검색 품질을 개선하는 편이 훨씬 이득이다.

## 9. 실무에서는

이미 PostgreSQL을 쓰는 팀이라면 pgvector가 가장 저항이 적은 출발점이다. 문법으로 보면 앞의 개념들이 그대로 드러난다.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE doc_chunks (
    id        bigserial PRIMARY KEY,
    doc_id    text NOT NULL,
    content   text NOT NULL,
    owner_id  text NOT NULL,        -- 필터용 메타데이터
    embedding vector(1024)
);

-- HNSW 인덱스. 연산자 클래스로 거리 함수를 고정한다
CREATE INDEX ON doc_chunks
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- 검색: <=> 코사인 거리, <-> L2 거리, <#> 음의 내적
SET hnsw.ef_search = 100;          -- 런타임 Recall/속도 손잡이

SELECT id, content, embedding <=> $1 AS distance
FROM doc_chunks
WHERE owner_id = $2                -- 필터. 플래너가 인덱스 사용 여부를 결정한다
ORDER BY embedding <=> $1
LIMIT 10;
```

여기서 챙길 것들.

- **인덱스의 연산자 클래스와 쿼리의 연산자가 일치해야 한다.** `vector_cosine_ops`로 인덱스를 만들어놓고 `<->`(L2)로 정렬하면 인덱스를 타지 못하고 전체 스캔이 된다. `EXPLAIN`으로 확인한다
- **필터가 있는 쿼리는 실행 계획이 달라진다.** `owner_id` 조건의 선택도에 따라 플래너가 인덱스 스캔 대신 필터 후 정렬을 택할 수 있다. 데이터가 늘어난 뒤 다시 봐야 한다
- 벡터는 정규화해서 저장하고 질의 벡터도 같은 방식으로 정규화한다. 이 규칙을 코드 한 곳에 모아두지 않으면 반드시 어긋난다
- 임베딩 모델 이름과 버전을 메타데이터에 남긴다. 재임베딩이 필요할 때 무엇이 어떤 모델로 만들어졌는지 알아야 한다
- 완전 탐색 결과를 정답으로 두고 ANN 결과와 비교하면 Recall을 직접 계산할 수 있다. 튜닝의 기준선이 된다

## 10. 면접 포인트

> 면접에서 이 주제가 나오면 이렇게 답한다

**Q. 코사인 유사도와 내적, L2 거리의 차이는 무엇인가요?**
A. 내적은 벡터의 크기와 방향을 모두 반영하고, 코사인은 크기를 나눠 없애 각도만 봅니다. L2는 두 점 사이 직선거리라 좌표 차이를 그대로 반영합니다. 텍스트 임베딩에서는 문서 길이가 유사도에 영향을 주면 안 되므로 코사인이 기본입니다. 다만 벡터를 L2 정규화하면 내적이 곧 코사인이 되고, L2 거리 제곱이 2에서 코사인의 2배를 뺀 값이 되어 세 측정의 순위가 완전히 같아집니다. 그래서 정규화만 되어 있으면 나눗셈이 없는 내적으로 계산하는 것이 더 빠릅니다.
- 꼬리 질문: "정규화를 안 하고 내적을 쓰면요?" → 문서 벡터가 정규화되지 않으면 내용과 무관하게 길이가 긴 문서가 상위를 차지한다. 반대로 문서만 정규화돼 있고 질의 벡터를 빼먹은 경우에는 모든 점수에 같은 상수가 곱해지므로 순위는 유지되지만 점수 절대값이 달라져 유사도 임계값 기준이 어긋난다고 답한다.

**Q. HNSW와 IVF의 차이를 설명해주세요.**
A. HNSW는 벡터들을 그래프로 연결하고 계층을 얹어, 상위 레이어에서 성큼성큼 이동한 뒤 하위로 내려가며 정밀 탐색합니다. 고속도로에서 국도, 골목길로 내려가는 방식이라 같은 Recall 기준에서 가장 빠른 편이지만 그래프를 메모리에 올려야 해서 메모리를 많이 씁니다. IVF는 k-means로 공간을 구역으로 나누고 쿼리와 가까운 구역 몇 개만 검색합니다. 메모리는 적게 쓰지만 정답이 경계 건너편 구역에 있으면 놓치는 클러스터 경계 문제가 있고, nprobe를 올려 완화하는 대신 느려집니다.
- 꼬리 질문: "둘 다 Recall이 부족하면 어떻게 올리나요?" → HNSW는 ef_search, IVF는 nprobe를 올린다. 둘 다 런타임에 조절 가능한 손잡이라 재구축 없이 Recall과 지연을 맞바꿀 수 있다. 그래도 부족하면 HNSW의 M을 올려 재구축한다.

**Q. 메타데이터 필터링이 왜 까다로운가요?**
A. ANN 인덱스가 필터를 모른 채 전체 기준으로 만들어져 있기 때문입니다. 검색을 먼저 하고 필터를 걸면(post-filtering), 조건이 빡빡할 때 Top-10 중 대부분이 탈락해 결과가 거의 비게 됩니다. 에러가 아니라 조용히 빈 결과라 문제를 늦게 발견합니다. 반대로 필터를 먼저 걸면(pre-filtering) 결과 수는 보장되지만 좁혀진 부분집합에서는 그래프나 클러스터 인덱스를 제대로 활용하기 어렵습니다. 그래서 필터 선택도로 판단합니다. 느슨하면 post, 매우 빡빡하면 pre나 파티션 분리, 중간이면 엔진의 필터링 기능에 맡깁니다.
- 꼬리 질문: "권한 필터는 어떻게 하시겠어요?" → 선택도가 극단적으로 높고 잘못되면 정보 노출 사고이므로, 테넌트나 그룹별로 인덱스·네임스페이스를 분리하는 편이 성능과 안전 양쪽에서 낫다고 답한다.

**Q. 어떤 벡터 DB를 쓰시겠어요?**
A. 규모와 운영 여력, 기존 스택으로 결정합니다. 벡터가 수만 건 수준이면 전용 DB 없이도 되고, 이미 PostgreSQL을 쓰고 있다면 pgvector로 트랜잭션과 백업을 그대로 재사용하는 게 합리적입니다. 운영 인력이 없으면 관리형, 규모가 수억 이상으로 커지고 인프라 인력이 있으면 오픈소스 분산 엔진을 봅니다. 다만 초기에 흔한 실수가 규모 대비 과한 도입인데, 수만 건이면 완전 탐색으로도 밀리초 안에 끝나므로 그 단계에서는 청킹이나 임베딩 모델 같은 검색 품질을 개선하는 편이 이득이 큽니다.
- 꼬리 질문: "FAISS와 벡터 DB의 차이는요?" → FAISS는 인덱스 라이브러리라 영속성, 메타데이터 필터링, 분산, 백업을 직접 만들어야 한다. 벡터 DB는 같은 알고리즘 위에 운영 기능을 얹은 것이라고 답한다.

| 질의 벡터 정규화를 빼먹음 | 문서가 정규화돼 있으면 순위는 유지되지만 점수 절대값이 달라진다 | 유사도 임계값 기준이 어긋난다. 정규화 로직을 한 곳에 모아 저장과 질의가 같은 경로를 타게 한다 |
| 검색 결과를 애플리케이션에서 필터링 | 조건이 빡빡하면 결과가 조용히 0건이 된다 | 엔진 필터를 쓰거나 과다 조회 후 부족하면 확장한다 |
| 인덱스 파라미터를 전부 런타임에 바꿀 수 있다고 생각 | `M`, `ef_construction`, `nlist`는 재구축이 필요하다 | 런타임 손잡이는 `ef_search`와 `nprobe`뿐이다 |
| 임베딩 모델을 중간에 교체 | 벡터 공간이 달라 기존 벡터와 비교가 무의미해진다 | 전체 재임베딩이 필요하다. 초기 선택을 신중히 한다 |

---

## 한 줄 정리

임베딩은 의미를 좌표로 옮기는 일이고 벡터 검색은 그 좌표계에서 이웃을 찾는 일인데, 전부 비교할 수 없어 ANN을 쓰고 그 순간부터 **Recall·속도·메모리·필터링**이라는 네 개의 저울을 동시에 맞추는 문제가 된다.
